Unit 2 · Lessons 5–7

Registers, programs & execution contexts

Unit 1 ended with a machine that works but chokes on its single accumulator. This unit gives it many registers and moves to a real instruction set (RISC-V). Then it separates three things that are easy to blur: the contract software relies on, the hardware that implements it, and the conventions that let pieces of software cooperate and be paused and resumed.

You'll be able to
Trace where every value lives in a register machine, show that one instruction set can have very different hardware, and explain exactly what must be saved to return from a function or to resume a paused thread.
Carries over
Everything from Unit 1: state, clock edges, fetch–decode–execute, PC, and the idea of a saved context.

Lesson 5

Keep working values in registers

LimitationWith one accumulator, every intermediate result has to detour through memory.
New mechanismA register file, plus a load/store instruction set where arithmetic only touches registers.
New state32 architectural registers (x0 is always 0), named by number in each instruction.
CostStorage, read/write ports, wiring, and instruction bits to name registers. Registers are still finite, so values sometimes spill to memory.

The accumulator bottleneck, measured

Take a small calculation with values a = 10, b = 6, c = 3:

y = (a + b) + (a − c) = 16 + 7 = 23

On NIB-8, the moment we compute a − c, the accumulator overwrites a + b. So we must store it to a temporary memory location and add it back later. Everything goes through memory:

0LOAD aACC = 10
1ADD bACC = 16
2STORE tsave the first partial result, or it's lost
3LOAD are-read a, which we just had
4SUB cACC = 7
5ADD tACC = 7 + 16 = 23
6STORE ywrite the answer

That's seven instructions with five data reads and two data writes. Three of those accesses (STORE t, the re-read of a, and ADD t) exist only because there was nowhere else to keep a value. A clever programmer could reorder this particular sum as a + b + a − c and avoid the temporary. We keep the expression's structure fixed so the storage difference is visible. For most real calculations, such rearranging isn't possible.

A register file

A register file is a small array of registers selected by number, built for speed. The common arrangement has two read ports and one write port, so one instruction can read two operands and write one result in the same cycle. An instruction like add x28, x5, x6 means "read registers 5 and 6, add them, write register 28". Every operand and the destination are named explicitly.

More registers aren't free. Each one costs storage and wiring, and every instruction needs more bits to name them: 32 registers need 5 bits per register field. The register file's delay also grows with its size and port count. That's why real instruction sets settle on 16 to 32 general-purpose registers.

Stepping onto a real instruction set: RV32I

From here on we use RISC-V, specifically its 32-bit base integer set, RV32I. It's a real, openly documented ISA, and it's clean enough to learn from. What changes from NIB-8:

FeatureNIB-8RV32I
Working registers1 (ACC)32, named x0–x31. x0 always reads 0 and ignores writes.
Register width8 bits32 bits
An address names…one 8-bit wordone byte. A 32-bit word takes 4 consecutive addresses.
Instruction size1 byte4 bytes (so PC advances by 4)
Arithmetic operandsACC and one memory wordregisters only (load/store design)

We'll use just a few instructions:

InstructionMeaning
add rd, rs1, rs2rd ← rs1 + rs2
sub rd, rs1, rs2rd ← rs1 − rs2

Four different kinds of number in one instruction

A load instruction mixes several kinds of number, and they must be kept apart. Take lw x6, 4(x10) with x10 = 0x100:

Because addresses name bytes, that 32-bit word occupies four addresses. RISC-V is little-endian: the lowest address holds the least significant byte.

Try it: the same calculation, two machines

Step through both versions and watch the memory-traffic counters. The register version keeps a in x5 the whole time, so it's never re-read, and both partial results stay in registers.

Registers are not variables

The ISA knows nothing about the names in your source code. The compiler decides where each value lives at each moment. A variable might sit in a register for a while, be stored to memory, be kept in two places, or vanish entirely if it's optimized away. One register holds many different variables over a program's life. When a program needs more live values than there are registers, the compiler must spill some to memory and reload them later.

PredictUse the stepper only to check.
  1. In the RV32I version, what are x5, x28, x29 and M[0x10C] immediately after the instruction at 0x50?
    Show answer

    x5 = 10, x28 = 16, x29 = 7, and M[0x10C] is still 0. The add x30 and the sw still have to run before y is written.

  2. What happens to x0 after addi x0, x0, 9? What does addi x5, x0, 9 put in x5?
    Show answer

    x0 stays 0, because writes to it are discarded. The second instruction puts 9 in x5: 0 + 9. This is how RISC-V loads small constants without a special instruction.

  3. With x10 = 0x100, which byte addresses does lw x6, 4(x10) read? If they hold 06, 00, 00, 00 (lowest address first), what arrives in x6?
    Show answer

    0x104, 0x105, 0x106 and 0x107. Little-endian means the lowest address is the least significant byte, so the value is 0x00000006 = 6.

  4. The data accesses dropped from 7 to 4. Why doesn't that mean the register version runs 7/4 = 1.75× faster?
    Show answer

    Run time depends on instruction count, cycles per instruction and clock period, not just data accesses. Instruction fetches still happen, the machines have different clocks and widths, and how much each access costs depends on the memory system (caches can make some nearly free). Counting accesses isolates one effect. It isn't a timing model.

  5. A calculation needs 10 values alive at once but only 4 registers are free. Why does having registers still leave memory traffic?
    Show answer

    The six values that don't fit must be spilled: stored to memory and reloaded when needed. Registers remove traffic only for the values they can actually hold. Reducing how many values are live at once (register pressure) matters as much as the register count.

For any instruction, point at each number and say which it is: a register number, an immediate constant, a byte address, or the contents at that address.

Lesson 6

One contract, different hardware

LimitationIf every instruction must finish in one clock cycle, the whole machine runs at the speed of its slowest instruction.
New mechanismSeparate the contract (ISA) from its implementation. For example, a multicycle design reuses hardware across short phases.
New stateInternal latches (instruction, operands, ALU result, loaded data) that software can't see.
CostMore latches, muxes and control. The per-cycle overhead can erase the gain.

What the ISA promises, and what it doesn't

An instruction set architecture is a contract. It specifies the instructions, the registers, and the precise effect of each instruction on that visible state. It deliberately says nothing about how or how fast. A microarchitecture is one particular hardware design that honours the contract.

Design 1: single-cycle

Do everything for an instruction in one clock cycle: fetch it, decode it, read registers, use the ALU, access data memory and write a register. The trouble is that the clock period must fit the longest chain, which is a load. An add finishes its real work sooner, but it still waits for the next clock edge.

Design 2: multicycle

Instead, split each instruction into short phases, one per clock cycle, and let each instruction use only the phases it needs. Values that must survive from one phase to the next are captured in internal latches: registers that exist only inside the implementation.

InstructionPhases usedCyclesWhy it skips some
lwF D E M W5Uses everything: address in E, read in M, write register in W
add / sub / addiF D E W4No data-memory access
swF D E M4No register to write
beqF D E3E compares and updates the PC if taken

Watch the latches during lw x6, 4(x10) with x10 = 0x100 and M[0x104] = 6:

F: IR ← the instruction. D: A ← x10 = 0x100. E: ALUout ← 0x100 + 4 = 0x104 (an address, not data!). M: MDR ← M[0x104] = 6. W: x6 ← 6. Apart from PC += 4 back in F, only W changes visible state: x6 receives its value only there.

Compare elapsed time, not cycle counts

Which design is faster? It depends on the instruction mix and on the clock period each design achieves. Build a sequence and adjust the periods. The bars are drawn to scale.

Multicycle is not pipelining. Here one instruction still finishes completely before the next begins: we split one instruction's work across time. Pipelining (Unit 3) overlaps different instructions. Also, "F, D, E, M, W" is a teaching decomposition, not a claim that every real CPU has exactly these five steps.
PredictCalculate first, then use the comparator.
  1. After phase E of lw x6, 4(x10) (x10 = 0x100), does ALUout hold 0x104 or 6? Has x6 changed yet?
    Show answer

    ALUout holds the address 0x104. The data (6) arrives in M, and x6 changes only in W. Confusing the address with the data is the classic mistake here.

  2. For the sequence lw, add, add, sw, beq, compute each design's total time and average CPI (single 5 ns, multicycle 1 ns).
    Show answer

    Single-cycle: 5 instructions × 5 ns = 25 ns, CPI 1. Multicycle: 5 + 4 + 4 + 4 + 3 = 20 cycles × 1 ns = 20 ns, CPI 20/5 = 4. The design with four times the CPI is faster, because its cycle is five times shorter.

  3. For five loads, does the multicycle design's 5× faster clock give a 5× speedup?
    Show answer

    No, there's no speedup at all: single-cycle 5 × 5 = 25 ns, multicycle 5 × 5 × 1 = 25 ns. Loads use every phase, so there's nothing to skip.

  4. If the extra latches and muxes push the multicycle period to 1.3 ns, how long does the mixed sequence take?
    Show answer

    20 × 1.3 = 26 ns, now slower than single-cycle's 25 ns. The overhead of adding state and control is real.

  5. A CPU's documentation says it uses F–D–E–M–W internally. Does that prove it's pipelined? What would?
    Show answer

    No. A multicycle machine uses those phases one instruction at a time. Pipelining is shown by overlap: a second instruction being fetched while the first is still in a later phase, so instructions complete more often than one per full phase sequence.

Describe lw x6, 4(x10) in three separate ways: as an architectural state change, as an internal sequence of micro-operations, and as an elapsed-time cost on each design.

Lesson 7

Calls, stacks & saved contexts

LimitationA jump forgets where it came from, and an interrupted program would lose the values in its registers.
New mechanismLink registers for returning, a stack by convention, trap entry into privileged handlers, and saved thread contexts.
New statera and sp, stack frames in ordinary memory, the OS's saved contexts (one per thread), and trap/privilege registers.
CostSaving and restoring takes instructions and memory traffic. Every context switch has overhead.

A call must remember the way back

A plain jump says where to go but not where to come back to. RISC-V's jal rd, target ("jump and link") does both: it writes the address of the next instruction (PC + 4) into rd, then jumps. To return, jalr x0, 0(ra) jumps to the address held in ra, and writing the link to x0 throws it away. (The assembler shorthand for this is ret.)

The calling convention: a software agreement

Separately compiled pieces of code can only cooperate if they agree on which registers carry arguments, which hold the return address and stack pointer, and which a called function may freely overwrite. That agreement is part of the ABI (application binary interface), and it's layered on top of the ISA:

NameRegisterRole by conventionPreserved across a call?
rax1return addressNo: each call overwrites it
spx2stack pointerYes: restored before returning
a0–a7x10–x17arguments; a0 (and a1) also carry return valuesNo
t0–t6x5–7, x28–31temporaries: the caller saves them if it still needs themNo
s0–s11x8–9, x18–27saved: the callee must restore them if it uses themYes

The stack also follows conventions: it grows toward lower addresses, sp stays 16-byte aligned, and each function call that needs storage reserves a stack frame. To the hardware, the stack is just ordinary memory plus a register the software agrees to treat as a pointer.

Nested calls overwrite ra, so save it

Our example computes f(5) = double(double(5)) + 1 = 21. Here's the problem. When f calls double, that jal overwrites ra, and ra held main's return address. So f first saves ra in its own stack frame and restores it just before returning.

Try it: trace the calls, then break them

Step through and watch ra, sp and the stack. Then switch on Remove save/restore, which turns sw ra and lw ra into no-ops, and step again to see exactly where things go wrong.

Releasing a frame (addi sp, sp, 16) just moves the boundary. It doesn't erase anything. The old 0x48 is still sitting at 0x1FC afterwards, and it will be overwritten by whoever uses that stack space next.

Interrupts: when the running code didn't agree to stop

A function call is planned. The caller follows the convention, so it knows which registers the callee may clobber. An interrupt is different. A timer or a device can demand attention between any two instructions, and the interrupted code has made no arrangements at all. Related events:

  • Synchronous exception: caused by the current instruction, for example an illegal instruction or a bad memory access.
  • Interrupt: asynchronous, caused by something outside the instruction stream, such as a timer tick or a network packet.
  • System call: an intentional request for OS service. On RISC-V that's the ecall instruction.

All of these cause a trap. The hardware records a small amount of control information (on RISC-V, the interrupted PC goes into a special register and the cause into another), switches to a privileged mode (from user code, a higher privilege level), and jumps to a handler. The hardware does not automatically save all 31 registers. The handler's software must save any registers it will use and restore them before returning, so the interrupted code never notices.

Program, process, thread, hardware context

TermWhat it is in our model
ProgramCode and data definitions: a description of work, e.g. a file on disk.
ProcessA running instance of a program: an address space plus OS resources. It contains one or more threads.
Software threadOne sequence of execution: its own PC, register values, stack and continuation.
Hardware contextThe live architectural state the processor provides to run one instruction stream.
Physical coreThe hardware that executes instructions. It provides one hardware context, or several with SMT.
Two threads in one process have separate stacks, but the hardware doesn't protect one thread's stack from the other. They share the address space, so a thread with a valid pointer into another's stack can read or write it. Separate stacks are a software discipline, not isolation.

Try it: two threads, one hardware context

Thread A counts up by 2 and thread B counts down by 1. Both use register x5. There's only one real x5, so every switch must save the running thread's value and restore the other's. The switch below is summarized as one action. A real one executes hundreds to thousands of kernel instructions, plus indirect costs such as cold caches.

EventWhy control movesDoes the running thread change?

PredictTrace addresses, not intentions.
  1. Right after the first jal ra, double at 0x88 enters double, what are ra, sp and the word at 0x1FC? Why do we need two different return addresses?
    Show answer

    ra = 0x8C, sp = 0x1F0, M[0x1FC] = 0x48. double must return to 0x8C inside f, and later f must return to 0x48 inside main. One ra can hold only one of them, so the outer one waits in memory.

  2. At the end of the correct run, what are a0, PC and sp? Is the saved 0x48 gone from 0x1FC?
    Show answer

    a0 = 21, PC = 0x48, sp = 0x200. The value 0x48 is still at 0x1FC: releasing the frame moved sp and erased nothing.

  3. With the save and restore removed, where does f's final jalr jump, and why?
    Show answer

    To 0x90. The second jal ra, double (at 0x8C) set ra = 0x90, and nothing restored main's 0x48. At 0x90 it adds 1 again, bumps sp by another 16, returns to 0x90 again, and loops forever.

  4. Does every interrupt cause a thread switch? How can the same thread resume?
    Show answer

    No. The handler saves the registers it will use, handles the event (say, a key press), restores them, and returns to the saved PC with a trap-return instruction. The same thread continues, unaware anything happened. A switch occurs only if the OS decides another thread should run. Try "Interrupt, same thread resumes" in the explorer.

  5. In the two-thread explorer: run one instruction of A, switch, run one of B, switch back. What are the live PC and x5, and what does A execute next?
    Show answer

    After A's addi, A has x5 = 2 and PC = 0x44. After the switch, B runs one addi (x5 50 → 49). Switching back restores PC = 0x44, x5 = 2, so A executes its jal x0, 0x40 next. Its pending instruction is neither skipped nor replaced.

  6. Two threads in one process have different sp values. Does that mean two cores, two protected address spaces, or two isolated stacks?
    Show answer

    None of these. They may share one core by taking turns, they share one address space, and their stacks are just different regions of it that either thread could access. What's truly distinct is each thread's register state and continuation.

Draw a function return and a thread resumption side by side as two different uses of saved state. For each, say what lives in registers, what lives in memory, and which software convention gives the saved bits their meaning.
