Unit 3 · Lessons 8–15

Make one CPU core faster

The instruction contract stays exactly the same. Everything in this unit is hidden machinery that makes a single core finish the same program sooner: overlapping instructions, keeping data close, guessing ahead, and doing ready work out of order. Every new mechanism must still leave the program seeing the results it was promised.

You'll be able to
Trace overlapping instructions through a small core, explain what makes each one wait (a value, a resource, or a decision), and tell apart a result that has been computed from one that may safely become official.
Study plan
Three passes, each its own session: overlap and hazards (8–9), memory and prediction (10–12), then width, scheduling and precise completion (13–15).
A note on models
Every explorer states its own model. The in-order five-stage pipeline of Lessons 8–9 is not the out-of-order core of 14–15. Cache sizes, latencies and widths are invented teaching numbers, not any real product's.
One distinction runs through the whole unit. Architectural state is what the instruction contract makes visible: registers, memory, PC. Microarchitectural state is everything the hardware keeps to go faster: pipeline registers, cache contents, predictor tables, rename maps, queues. It can change timing, but it must never change the program's architecturally defined results for the same inputs. (Timing can still matter in other ways: it can change how threads interleave and when a program interacts with the outside world.)

Lesson 8

Overlap instructions with a pipeline

LimitationOne instruction at a time leaves most of the hardware idle in any given cycle.
New mechanismSplit the datapath into stages separated by registers, and start a new instruction every cycle.
New statePipeline registers (with valid bits) holding several partly finished instructions at once.
CostRegister overhead per stage, a clock set by the slowest stage, fill and drain time, and hazards (Lesson 9).

Idle hardware

In the multicycle machine from Unit 2, the fetch hardware sits idle while the ALU works, and the ALU sits idle while memory is read. Colour in which unit is busy each cycle and the waste is obvious:

Five stages, and the registers between them

StageWorkWhat it passes forward
F · fetchRead the instruction at PCinstruction bits, its PC
D · decodeWork out the operation, read registersoperand values, destination, control bits
E · executeALU result or memory addressresult/address, control
M · memoryLoad or store, if neededloaded data or the carried result
W · writebackWrite the destination register, if any—

Between stages sit pipeline registers. At every clock edge, each stage hands its instruction's intermediate values and control bits to the next. A valid bit marks whether a slot holds a real instruction or a bubble. The key mental shift is that there is no single "current instruction" any more. There are up to five, each in a different stage, each carrying its own identity.

An add still passes through M even though it doesn't touch memory, and a store passes through W without writing a register. A stage is a position in the hardware, not a job every instruction must do.

Latency, throughput, and the empty ends

Two measures that everyday language blurs:

  • Latency: how long one instruction takes from start to finish. Here that's 5 × 1.1 = 5.5 ns, longer than the unpipelined 5 ns because of the stage registers.
  • Throughput: how much work completes per unit time. Once the pipe is full, one instruction per 1.1 ns.

For N independent instructions in an ideal K-stage pipeline, the total is N + K − 1 cycles: K − 1 cycles to fill, then one completion per cycle. That formula already includes draining, so don't add it twice. A short program never gets near the ideal K× speedup:

In steady state, pipelining raises the machine's throughput without making any instruction faster. In fact each instruction takes a little longer, and a short fragment can finish later than on the unpipelined machine because of the fill time and register overhead. That's worth remembering whenever someone confuses latency with throughput, which happens again with caches, GPUs and networks.
PredictDraw the diagram on paper first.
  1. With 4 independent instructions, which stage holds each instruction in cycle 4? How many have completed?
    Show answer

    I1 is in M, I2 in E, I3 in D, I4 in F. None have completed: I1 finishes W in cycle 5.

  2. Using 1 ns stages and 0.1 ns overhead, how long do 100 independent instructions take pipelined and unpipelined? What's the speedup?
    Show answer

    Pipelined: (100 + 4) × 1.1 = 114.4 ns. Unpipelined: 100 × 5 = 500 ns. Speedup ≈ 4.37×, close to the 4.55× ceiling because the fill cost is spread over many instructions.

  3. E's logic grows to 2 ns while the others stay at 1 ns. What is the minimum clock period? Does adding more pipeline registers somewhere else help?
    Show answer

    2 + 0.1 = 2.1 ns. Registers elsewhere don't help, because the clock is set by the slowest stage. You'd have to split E itself into two stages, which adds a stage, more overhead and more hazard cost.

  4. Four instructions are in flight at once. Are they four software threads?
    Show answer

    No. They're consecutive instructions of one thread, each partly done. The extra state is the pipeline registers holding each one's intermediate values, not extra PCs or register files for other threads.

Lesson 9

Hazards, stalls & forwarding

LimitationOverlap lets an instruction read a register before the instruction ahead of it has produced the value.
New mechanismHazard detection that stalls when needed, plus forwarding paths that deliver fresh results early.
New stateComparators on register numbers, bypass muxes, and stall/bubble control bits.
CostBubbles waste cycles, and bypass wiring adds area and timing pressure. Nothing can deliver a value before it exists.

A dependency is in the program; a hazard is in the schedule

A dependency is a fact about the program: instruction 2 needs the value instruction 1 produces. A hazard is what happens when a hardware schedule would violate that fact, or needs something that isn't available. There are three kinds, each a different thing to wait for:

HazardWaiting for…ExampleUsual fix
Dataa valueadd x6, x5, x9 right after the load of x5forward it, stall if it doesn't exist yet
Structurala resourcefetch and a load both need the only memory portmore hardware (separate instruction/data caches)
Controla decisionwhich instruction comes after a branch?stall, or predict (Lesson 12)

When is a value ready, and when is it needed?

Every data-hazard question comes down to comparing two moments. In our model, an ALU result exists at the end of E and loaded data at the end of M. A consumer needs its operands at the start of its own E. Without forwarding, the value must first be written to the register file in W. We assume W writes early in the cycle, so D can read the new value in that same cycle.

Try it: stalls and forwarding paths

Structural hazards

Suppose instruction fetch and data access shared one single-ported memory. A load reaching M in cycle 4 would collide with a later instruction trying to fetch in cycle 4. Someone has to wait, and no amount of forwarding helps, because the problem is a missing resource, not a missing value. That's why real cores have separate L1 instruction and data caches.

There's a recurring question behind every performance problem from here on: is the machine waiting for a value, a resource, or a decision? Each has different fixes.

PredictMark "value ready" and "value needed" first.
  1. In the load → add → add program, why can't the loaded value reach the first add's E in cycle 4, even with forwarding? When can that add execute?
    Show answer

    The data exists only at the end of the load's M stage (cycle 4), but the add would need it at the start of cycle 4. The add stalls one cycle and executes in cycle 5, with the value forwarded from the M/W register.

  2. How many cycles does that three-instruction program take with and without forwarding (first F to last W)?
    Show answer

    With forwarding: 8 cycles (the ideal 7 plus one load-use bubble). Without: 11 cycles, since each dependent instruction waits two extra cycles to read the register file after W.

  3. Replace the load with an add that produces x5 at the end of E. How many stalls remain with forwarding?
    Show answer

    Zero. Each result is forwarded from the end of E straight into the next instruction's E. That's the "ALU chain" case.

  4. A load in M and a younger instruction's fetch both need the only memory port. What kind of hazard is it, and why doesn't forwarding fix it?
    Show answer

    A structural hazard: two requests, one port. Forwarding moves existing values around, but it can't create a second port. Only more hardware (or waiting) helps.

Before inserting a stall, mark when the producer creates the value and when the consumer needs it. The stall count is the gap, minus whatever forwarding can bridge.

Lesson 10

Keep reused data close: caches

LimitationOur pipeline assumed memory answers in one stage. Real main memory takes around a hundred times longer than a cycle.
New mechanismSmall, fast caches that keep copies of recently used memory in fixed-size lines.
New stateCached lines, plus tags, valid and dirty bits, and replacement (LRU) information.
CostArea and energy, tag metadata, and write policies. Misses still stall, and more capacity or associativity is slower to search.

Why a hierarchy

Fast memory is small and expensive per bit, and big memory is slow. No single technology is both, so machines stack several: registers, then one or more levels of cache, then DRAM, then storage. The names L1, L2 and L3 are just levels. Their sizes and policies differ between designs.

Locality: the bet caches make

Caches bet on two habits real programs have. Temporal locality: something used now will probably be used again soon. Spatial locality: something near what was just used will probably be used soon. That's why a cache moves a whole line (typically 64 bytes) at a time: one miss fetches the neighbours too.

How a cache finds a line

We'll use a tiny, fully traceable cache: 8-bit addresses, 16-byte lines, 64 bytes of data (4 lines). Every address splits into three fields:

  • offset: which byte within the 16-byte line (4 bits).
  • index: which set the line must live in.
  • tag: the rest of the address, stored alongside the line to identify which block is there.

How many index bits there are depends on the organization. Direct-mapped has 4 sets of 1 line, so 2 index bits: each block has exactly one possible home. 2-way set-associative has 2 sets of 2 lines, so 1 index bit: two possible homes. Fully associative has 1 set of 4 lines and no index bits: a block can go anywhere. The capacity is the same in every case. What changes is the placement flexibility, which costs extra tag comparisons.

Try it: a cache you can trace by hand

Try "3 blocks, 1 set" in all three organizations. Direct-mapped and 2-way both miss every time. Two ways can't hold three blocks that all compete for one set, and LRU always evicts exactly the block needed next. Fully associative has room for all three. Now try "scan ×2 (too big)": 128 bytes can't fit in 64, so no organization saves the second pass. Those are capacity misses.

Writes

Stores add two separate policy choices:

QuestionOptionWhat happens
When does the next level see the write?Write-throughUpdate the cache and send the write onward. Simple, but lots of traffic.
Write-backUpdate only the cache and set the line's dirty bit. Write it back when evicted.
A store misses. Bring the line in?Write-allocateFetch the line, then modify it in the cache.
No-write-allocateSend the write onward without caching it.

Hardware can also prefetch, fetching lines it predicts you'll need. Good prefetches hide waiting. Wrong ones waste bandwidth and evict useful data.

A first cache performance model

For a simple blocking, one-level cache, the average memory access time is AMAT = hit time + miss rate × miss penalty, where the penalty is the additional time a miss costs.

PredictSplit the address into fields before deciding.
  1. In the direct-mapped cache, what are the block number, set, tag and offset of address 0x4C?
    Show answer

    0x4C = 0100 1100. Offset = low 4 bits = 0xC. Block = 0x4C / 16 = 4. Set = 4 mod 4 = 0. Tag = 4 / 4 = 1 (binary 01). So bits 01 | 00 | 1100.

  2. For the "ping-pong" trace (08, 48, 08, 48, 0C, 4C), how many hits does direct-mapped get? 2-way?
    Show answer

    Blocks 0 and 4 both map to set 0. Direct-mapped: they evict each other every time, so 0 hits (2 compulsory, 4 conflict misses). 2-way: both fit in set 0's two ways, so 2 compulsory misses, then 4 hits. Same capacity, different placement.

  3. A cache with a 1 ns hit time, 5% miss rate and 60 ns miss penalty: what's the AMAT? Is that the CPU's time per instruction?
    Show answer

    1 + 0.05 × 60 = 4 ns. No: it's an average per memory access under a serial model. Instruction time depends on how many instructions access memory and how much of the miss time overlaps with other work.

  4. Why might bigger lines or aggressive prefetching slow a program down? What extra state does a write-back cache need?
    Show answer

    They move bytes that might never be used, which consumes bandwidth and evicts useful lines. A problem if the program is bandwidth-limited or has poor spatial locality. A write-back cache needs a dirty bit per line, to know which lines must be written back when evicted.

Never call an access a hit until you've found its set and compared the valid tags there. Explain the difference between capacity and placement flexibility.

Lesson 11

Translate and protect addresses

LimitationWith raw physical addresses, any program can read or overwrite any other's memory, and programs can't be placed flexibly.
New mechanismVirtual addresses translated page by page through per-process page tables, with a TLB caching recent translations.
New statePage tables in memory (owned by the OS), TLB entries (tagged by address space), and a page-table base register.
CostTranslation work on every access, TLB misses (page walks), page faults, and memory used by the tables.

Every program gets its own view of memory

With virtual memory, the addresses a program uses are virtual. Hardware translates each one to a physical address using a table the operating system controls. Memory is divided into fixed-size pages (virtual) and frames (physical). Two processes can use the identical virtual address and reach completely different bytes, and a process has no virtual address that leads to memory the OS hasn't mapped for it. (It can form any address it likes, but accessing an unmapped one faults.) Virtual memory is valuable even when nothing is ever swapped to disk. Isolation alone justifies it.

Splitting an address: page number + offset

Our teaching system uses 16-bit virtual addresses and 256-byte pages. The top 8 bits are the virtual page number (VPN) and the bottom 8 bits are the offset within the page. Translation replaces only the page number. The offset passes through unchanged.

Page-table entries also hold permission bits (readable, writable, executable, user-accessible) and a present bit. (In the explorer below, every mapped page is readable, and only write permission is checked.) The page table lives in ordinary memory, so walking it on every access would double the memory traffic or worse. The TLB (translation lookaside buffer) is a small cache of recent translations and their permissions. It holds mappings, never the program's data.

Try it: follow one access through translation

Pick a scenario, or type any virtual address and choose Read or Write. The highlighted path shows which decisions were made. The TLB fills as you go, so repeating an address that just missed now hits.

Three different events, three different questions

EventThe question that failedWho handles itIllustrative cost
TLB miss"Do I have this translation cached?"Hardware walks the page table (some ISAs trap to software)tens of cycles
Cache miss"Do I have a copy of these data bytes nearby?"Hardware fetches the linetens to hundreds of cycles
Page fault"Is this access allowed and backed by memory at all?"An exception into the OSfrom microseconds (a minor fault, no disk I/O) to milliseconds (reading from storage)

They're independent. An access can miss the TLB and hit the cache, hit the TLB and miss the cache, or neither or both. A page fault doesn't always mean disk I/O. The OS might allocate a fresh zero-filled page, set up a copy-on-write copy, load data from storage, or decide the access is invalid and kill the process (a "segmentation fault"). And a TLB hit is not permission: the cached entry carries permission bits that are checked on every access.

Page tables belong to an address space (a process), not a thread. Threads of one process share them. When the OS switches processes, it points the MMU at another page table, and the TLB must not serve the old process's translations. Tagging entries with an address-space ID avoids flushing the whole TLB. And real caches often start their lookup using offset bits while translation proceeds in parallel, so the serial diagram shows logic, not timing.
PredictAnswer "which bytes?", "allowed?", and "cached where?" separately.
  1. Translate virtual 0x12E8 given VPN 0x12 → frame 0xA0. Which part is unchanged?
    Show answer

    VPN 0x12, offset 0xE8, so the physical address is 0xA0E8. The offset 0xE8 passes through unchanged.

  2. Can an access miss in the TLB and still hit in the data cache? Trace a read of 0x1344 right after a TLB reset.
    Show answer

    Yes. VPN 0x13 isn't in the TLB (miss), so the page walk finds frame 0xA1 and fills the TLB. The physical address is 0xA144, whose line 0xA140 is present: a cache hit. The TLB caches translations and the data cache caches bytes, so they hit and miss independently.

  3. A write hits in the TLB, but the entry says read-only. May it proceed? Is a missing cache line the problem?
    Show answer

    No, it raises a permission fault. The translation was found, but the check failed. The cache isn't consulted at all for the target data, because the access isn't allowed.

  4. Does every page fault mean reading from disk? Give two different OS responses.
    Show answer

    No. For the "page on disk" scenario the OS loads the page and installs a mapping, then the instruction retries. For the "unmapped page" scenario there's nothing valid there, so the OS terminates the process (segmentation fault). Other responses include zero-filling a newly touched page and copy-on-write.

For any access, answer three questions separately: which physical bytes? (translation), is it allowed? (permissions), and where is a copy? (caches).

Lesson 12

Predict the next instruction address

LimitationFetch needs the next PC every cycle, but a branch doesn't know its direction until E.
New mechanismPredict the direction (and target), fetch down the guessed path, and squash the wrong-path work if the guess was wrong.
New statePrediction counters and history, target buffers, and recovery information.
CostWasted wrong-path work, predictor area and energy, and a misprediction penalty that grows with pipeline depth.

The problem: fetch can't wait

A conditional branch depends on a value computed by earlier instructions. In our five-stage pipeline it's resolved at the end of E, by which point two younger instructions have already been fetched. If fetch waited for every branch, and roughly one instruction in five is a branch, each branch would cost two bubbles: CPI ≈ 1 + 0.2 × 2 = 1.4, so about 30% of all cycles would be wasted.

So the processor guesses. A direction predictor guesses taken or not taken, and target structures supply the destination address. Fetching then continues speculatively. The guess is only a hypothesis. The branch still executes and decides the truth, and if the guess was wrong the younger instructions are squashed.

Try it: a 2-bit saturating counter

The classic simplest predictor keeps a 2-bit counter per branch. States 0–1 predict not taken and 2–3 predict taken. After each branch resolves, count up (towards 3) if it was taken and down (towards 0) if not. From a strong state it takes two surprises in a row to flip the prediction, so one odd outcome, like a loop exit, doesn't derail it.

How much does accuracy matter?

A simple long-run estimate: CPI ≈ base CPI + (branches per instruction) × (misprediction rate) × (penalty in cycles). It assumes penalties don't overlap and ignores fill and drain.

Squashing wrong-path work restores the architectural state. It doesn't promise to undo microarchitectural side effects: a wrong-path load may already have brought a line into the cache. That gap is exactly what the Spectre family of attacks exploits. Correctness and side-channel security are separate questions.
PredictKeep "predicted", "actual" and "accepted" separate.
  1. Starting at state 1, trace T, T, T, N. What are the predictions, how many are wrong, and what is the final state?
    Show answer

    States 1 → 2 → 3 → 3 → 2. Predictions: N, T, T, T. Wrong: the first T and the final N, so 2 misses. Final state 2 (weakly taken), so the next prediction is still T.

  2. In the five-stage model, a branch predicted not taken is actually taken, resolved at the end of cycle 3. Which instructions are squashed? When does target fetch begin?
    Show answer

    The two fall-through instructions fetched in cycles 2 and 3 (in D and F during cycle 3). Target fetch begins in cycle 4.

  3. Base CPI 1, 25% branches, 8% mispredicted, 5-cycle penalty. What's the estimated CPI? What does the estimate ignore?
    Show answer

    1 + 0.25 × 0.08 × 5 = 1.10. It ignores overlap between penalties and other stalls, the fill and drain of short programs, and the fact that the penalty depends on where each branch resolves.

  4. A wrong-path load was squashed. Did it necessarily leave no trace in the cache? May its value ever reach an architectural register?
    Show answer

    It may have changed the cache, which is a microarchitectural side effect. Its value must never become architectural state. Squashing guarantees the second, not the first.

Keep four things distinct: the predicted direction, the actual direction, speculative execution, and architectural acceptance.

Lesson 13

More than one instruction per cycle

LimitationA scalar pipeline starts at most one instruction per cycle, even when neighbouring instructions are independent.
New mechanismA superscalar core fetches, decodes and issues several instructions per cycle to several execution ports.
New stateWider pipeline registers, more register-file ports, and dependency checks within each group.
CostComparisons grow roughly with width², plus bypass wiring and energy. It only helps if the program has independent work.

Superscalar means one core processing several instructions per cycle. It doesn't mean several cores, and it doesn't require several threads: this lesson's explorer uses a single thread. (A core with simultaneous multithreading, Unit 4, is superscalar and can fill those slots with instructions from more than one hardware thread.) A core actually has several different widths:

Try it: width meets dependencies

All four instructions are already decoded and waiting. The model issues in program order, up to W per cycle. An add takes 1 cycle and its result is usable the next cycle. Instructions issued in the same cycle can't use each other's results. There are W ALU ports and one load port, and loads take 3 cycles.

The amount of ILP isn't a fixed property of an algorithm. It depends on how the code is written. Summing an array into one accumulator makes a single long chain. Keeping four partial sums and combining them at the end makes four independent chains that a wide core can overlap. (For floating point this changes the rounding, so compilers only do it when allowed.)

Measuring it

IPC = retired instructions ÷ cycles. Its reciprocal is CPI, when both are measured over the same instructions and the same interval. The explorer above only shows the execution window. It leaves out fetch, decode and retirement, so it isn't a whole-program IPC.

PredictFind the ready instructions each cycle.
  1. With W = 2, how many cycles do the independent, two-chain and one-chain workloads need?
    Show answer

    2, 2 and 4. Independent: A B, then C D. Two chains: A B, then C D (each depends on the previous cycle). One chain: A, B, C, D, one per cycle, with the second slot idle.

  2. In the one-chain workload, why can't B issue with A? Do more ALUs fix it?
    Show answer

    B needs A's result, which doesn't exist until the end of A's cycle. More ALUs don't help: the dependency, not the hardware, is the limit.

  3. Four independent loads, one load port, W = 4. What's the minimum number of cycles just to start them?
    Show answer

    4 cycles, one load per cycle through the single port. The idle ALUs can't start loads.

  4. A program retires 300 instructions in 200 cycles. What are IPC and CPI?
    Show answer

    IPC = 300 / 200 = 1.5, CPI = 0.67. A CPI below 1 is only possible with a superscalar core.

Before predicting IPC, name three things: which width you mean, which ports are compatible with the instructions, and which operands are ready.

Lesson 14

Rename values, schedule ready work

LimitationIn-order issue stops at the first blocked instruction, even when younger ones are ready. Reused register names create fake ordering constraints.
New mechanismRename each destination to a fresh physical register, then issue whichever instructions have their inputs ready.
New stateA rename map, a free list, physical registers with ready bits, and an issue queue.
CostLarge, power-hungry structures and complex recovery. The window of instructions is finite.

Three kinds of dependency, only one of them real

Look at the register names in a program and you'll find three relationships between instructions:

Renaming: names become versions

The core has many more physical registers than the ISA's 32 architectural names. A rename map records which physical register currently holds each architectural register's newest value. For each instruction, in program order:

  1. Look up each source in the map: "which physical register holds the value I need?"
  2. Take a free physical register for the destination, and update the map so later readers find it.

The order of those two steps matters: sources are read before the destination is remapped. Step through the example (M[x10] = 7, x11 = 20, x12 = 5):

Out-of-order issue: go around the blocked load

Now let the scheduler pick any ready instruction, oldest first, instead of only the next one in program order. Model: all five instructions are renamed and waiting before cycle 1. One instruction issues per cycle. The load issues in cycle 1 and its value is ready at the end of cycle 4. Adds take one cycle, and a result is usable the cycle after it's produced.

What new state this takes

StructureJob
Speculative rename mapThe newest physical register for each architectural name
Free listPhysical registers available to be allocated
Physical register file + ready bitsHolds many versions of values at once, and says which exist yet
Issue queue (reservation stations)Waiting instructions, each tagged with the physical registers it needs. They "wake up" when those become ready.

Extra physical registers don't give software more register names. They let more versions be in flight at once. Renaming can't break true dependencies, can't add memory bandwidth, and can't see past a full window: when queues or free registers run out, the front end stops. And the old physical register for x1 (p1) can't be freed the instant x1 is remapped, because older instructions may still need to read it, and recovery may need to restore the old mapping. That raises the question the next lesson answers: when does a result become official?

PredictRename on paper before stepping.
  1. After renaming all five instructions, which physical register does I2 read for x1, and which does I4 read? What is the final mapping of x1?
    Show answer

    I2 reads p20 (the load's result). I4 reads p22 (I3's result). The final speculative mapping is x1 → p22.

  2. Which dependencies remain after renaming, and which name conflicts were removed?
    Show answer

    Remaining RAW: I1→I2, I3→I4, I4→I5, I2→I5. Removed: WAW between I1 and I3 (both wrote x1), and WAR between I2 (reads x1) and I3 (writes x1).

  3. In the out-of-order schedule, in which cycle does each instruction issue? When is everything done, compared with in-order?
    Show answer

    I1 → 1, I3 → 2, I4 → 3, (nothing ready in 4), I2 → 5, I5 → 6. Done at the end of cycle 6. In-order: I1 → 1, I2 → 5, I3 → 6, I4 → 7, I5 → 8, done at the end of cycle 8.

  4. Can p1, x1's old physical register, be freed as soon as I1 remaps x1 to p20?
    Show answer

    No. An older instruction that reads x1 might still need p1, and if something goes wrong (a fault or misprediction) the core may need to roll the map back to x1 → p1. It's freed only when the instruction that replaced it retires.

Rename a sequence that reuses a destination register, and prove that every consumer still reads the right version of its input.

Lesson 15

Complete precisely, respect memory order

LimitationWork finishing out of order could expose results that should never exist, after a fault or a wrong guess.
New mechanismA reorder buffer that retires results in program order, and load/store queues that check memory addresses.
New stateROB entries (status, exception), a committed rename map, and store and load queues.
CostROB and queue area and energy. The oldest blocked instruction holds up retirement, and wrong speculation means replays.

Computed is not the same as accepted

Completion means an instruction has produced its value, or discovered a problem. Retirement (also called commit) means the machine officially accepts it into the architectural state. The reorder buffer (ROB) is a queue in program order. Instructions enter at the tail when renamed and leave from the head when retired. An instruction may retire only once it's at the head (everything older has retired) and it has completed without a fault.

This gives precise exceptions. If an instruction faults, the handler sees a machine where every older instruction has taken effect and neither the faulting instruction nor anything younger has, even if younger instructions already computed their results.

Try it: watch the ROB

This uses the out-of-order schedule from Lesson 14. Retirement is one per cycle, at the start of a cycle, using results completed by the end of the previous cycle. Committed registers x1–x4 start at 0. Switch the load to faults to see what "precise" buys you.

Notice two views of "x1". The committed x1 is 7 after I1 retires, then 24 after I3 retires. Meanwhile the speculative map already said x1 → p22 from the moment I3 was renamed, because any newly renamed instruction must read the newest version. Recovery copies the committed map back over the speculative one.

These two views are conceptual. Real out-of-order cores store and recover this state in different ways: some keep a separate retirement map, some checkpoint the rename map at branches, and none need a separate architectural register file. What every design must provide is the essential promise: precise, in-order architectural effects.

Memory dependencies: the one renaming can't see

Register dependencies are visible in the instruction bits. Memory dependencies aren't. Whether a store and a later load touch the same bytes depends on addresses computed at run time. If p turns out to equal A, L2 must see the store's 9. The core can make L2 wait until every older store address is known (safe but slow), or it can guess that they don't overlap, run L2 early, and check afterwards. Step through both outcomes:

Retiring a store doesn't mean other cores can see it yet. It may still wait in a store buffer before reaching the cache. "Retired" (architecturally committed for this thread) and "globally visible" are different events. How multiple cores observe each other's memory operations is the memory-consistency topic of the next unit, and a ROB alone doesn't settle it.
PredictTrack completion and retirement separately.
  1. In the successful run, which instructions have completed by the end of cycle 3, and how many have retired? Why?
    Show answer

    Completed: I3 and I4. Retired: none. I1 is at the head and hasn't completed, and nothing may retire past it.

  2. If the load faults at the end of cycle 4, what happens in cycle 5? Can x1 = 24 or x3 = 19 appear in the committed registers?
    Show answer

    The fault is at the ROB head, so all in-flight instructions are squashed and the handler starts. No: I3's 24 and I4's 19 were computed but never retire. The handler sees x1–x4 = 0, the state before I1.

  3. A younger load speculatively read 3 from A, and a dependent add produced 4. Then the older store's address resolves to A. What must happen, and why can't renaming prevent it?
    Show answer

    The core detects a violation, squashes the load, the add and anything younger, and replays. This time the load gets 9 (forwarded from the store queue) and the add produces 10. Renaming works only on register names written in the instruction. A memory overlap depends on addresses computed at run time.

  4. In the successful run, in which cycle does each instruction retire? Does retiring a store mean other cores can see it?
    Show answer

    I1 → 5, I2 → 6, I3 → 7, I4 → 8, I5 → 9. And no: a retired store may still sit in a store buffer before becoming visible to other cores.

Point to where speculative values live (physical registers, store queue), what keeps them reversible (committed map, ROB order), and which event makes them architectural (retirement).
