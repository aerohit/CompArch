Unit 4 · Lessons 16–19

Add parallelism

Unit 3 squeezed every drop of independence out of one instruction stream. This unit adds more: more instruction streams on more cores, more hardware contexts sharing one core, and more data elements per instruction. Each is a different kind of parallelism, and each brings a new problem. Copies can disagree, operations can appear in surprising orders, threads compete for shared resources, and array lengths don't divide evenly.

You'll be able to
Tell apart multiple cores, multiple hardware contexts and multiple vector elements. Explain how cached copies of shared memory stay coherent, why that still isn't enough to order operations, and how software establishes the ordering it needs.
Carries over
Caches and lines (Lesson 10), store buffers and retirement (Lesson 15), software threads and saved contexts (Lesson 7), issue ports and ILP (Lesson 13).
A note on models
Each explorer is an explicit teaching model. A coherence step is one completed transaction, an ordering step is one abstract event, an SMT step is one cycle, and a vector step is one group of elements. None of them simulates a commercial processor.
More hardware only helps if the algorithm exposes independent work and the communication doesn't eat the benefit. Keep that sentence in mind for every lesson here, and for GPUs next.

Lesson 16

Share memory across cores

LimitationOne core can only find so much independent work in one instruction stream, and making it faster costs disproportionate power.
New mechanismSeveral cores, each running its own thread, sharing one memory, with a coherence protocol keeping their private cached copies in agreement.
New stateA coherence state per cached line in every cache, plus sharer/owner tracking in the interconnect or a directory.
CostCoherence messages, invalidations, cache-to-cache transfers, and contention on shared caches and memory bandwidth.

More cores, one memory

A multicore chip puts several complete cores on one die. Each has its own PC, registers, pipeline and private caches, so each can run a different software thread at full speed. What they share is further out: usually a last-level cache, the on-chip interconnect, the memory controllers and the DRAM bandwidth. "Shared memory" means every core can address the same bytes. It doesn't mean every access costs the same, or that the caches are physically shared.

How much can more cores help? Amdahl's bound

Split a fixed task across P equally fast cores. If a fraction s of the work must run serially (setup, a final combine step, a part nobody parallelized), then even with perfect scaling the best possible speedup is

speedup ≤ 1 / (s + (1 − s) / P)

The new problem: copies that disagree

Suppose cores A and B have both cached the word x = 0. A writes x = 1 into its own cache. If B keeps reading its old copy forever, the two cores no longer share memory in any useful sense.

Cache coherence is the promise that for each single memory location, all cores agree on one order of writes and eventually see the latest one. The common way to deliver it is an invalidation protocol, with one rule:

Many readers, or one writer, per line, never both. Before a core may write a line, every other copy is invalidated. After that, a reader that misses gets the current data, even if it lives in another core's cache rather than in memory.

Coherence works on whole cache lines, not individual variables. Keep that in mind, because it causes false sharing below. It also says nothing about the order of writes to different addresses. That's the next lesson.

A deliberately small protocol: MSI

Each cache labels each line it knows about with one of three states:

StateMeaning in this cacheMay read?May write?
I InvalidNo usable copy. Old bits may physically remain, but must not be used.No: missNo
S SharedA clean, readable copy. Other caches may have one too.YesOnly after requesting ownership
M ModifiedThe only valid copy, possibly newer than memory.YesYes
Two cores with private write-back caches. One 16-byte line holds two 4-byte words, x and y (in the "separate lines" layout, y moves to its own line). Each transaction completes before the next begins: no evictions, transient states or simultaneous requests. A read that misses enters S, even if no one else has the line (that's MSI, not MESI). If the other cache holds the line in M, a read makes it supply the data and update memory, and both end in S. A write steals ownership: the data moves cache to cache, and memory may stay stale.

Try it: two caches, one line

Click reads and writes, or play a preset. Watch the states, where the current value actually lives, and the counters.

False sharing: different variables, same line

Run the false sharing preset with x and y in one line. A only ever touches x and B only ever touches y. They share no data, yet every write must take ownership of the whole line away from the other core: four ownership requests and three invalidations for four writes. Switch to separate lines and run it again. Each core takes its own line once and then hits in M: two requests and no invalidations.

PredictTrack permission, then data.
  1. In the textbook trace, after "A writes x = 1": what are A's and B's states, what does memory hold, and where is the current value?
    Show answer

    A = M, B = I, memory x = 0 (stale). The current value 1 lives only in A's cache. Coherence knows that, so it doesn't matter that memory is out of date.

  2. Next, B reads x. What value does B get, and what happens to both states and to memory?
    Show answer

    B misses, and A (in M) supplies 1 and writes it back. Both end in S, and memory now holds 1.

  3. Four alternating writes (A→x, B→y, A→x, B→y). Count ownership requests and invalidations with x, y in one line versus separate lines.
    Show answer

    One line: 4 requests, 3 invalidations. Separate lines: 2 requests, 0 invalidations, because after the first write each core keeps its own line in M.

  4. With 20% serial work and 4 ideal cores, what does Amdahl predict? What's the limit with unlimited cores?
    Show answer

    1 / (0.2 + 0.8/4) = 1 / 0.4 = 2.5×. With unlimited cores the limit is 1/0.2 = 5×.

  5. x is perfectly coherent. Why is that not enough to guarantee another thread sees a write to data before it sees ready = 1?
    Show answer

    Coherence talks about one location at a time: every core agrees on the order of writes to x. It says nothing about the order in which writes to two different locations (data, ready) become visible. That's a separate rule, the memory-consistency model, covered next.

For any trace, say who has permission to read or write each line, where the current data actually lives, and why two different variables can still fight over one line.

Lesson 17

Define ordering, then synchronize

LimitationCoherent caches still let different threads observe operations on different addresses in surprising orders.
New mechanismA memory consistency model that defines which results are legal, plus synchronization (atomics, acquire/release, locks, barriers) to demand the order you need.
New stateStore buffers, the modification order of atomic variables, lock ownership, waiting queues and barrier counts.
CostFences and atomics stall or drain buffers, contended atomics bounce lines between cores, and threads wait on each other.

Why the order can look strange: store buffers

Recall Lesson 15: a core can retire a store while the value is still sitting in its store buffer, waiting to be written to the cache where other cores can see it. Meanwhile the core keeps going, and a later load of a different address can complete right away. From another core's point of view, the load happened before the store.

Sequential consistency: the intuitive baseline

A memory consistency model is the rule that says which values loads are allowed to return. The most intuitive one is sequential consistency (SC): the result must look as if all threads' operations were shuffled into one global sequence that keeps each thread's own program order. Real CPUs and languages mostly allow more behaviours than SC, for speed. x86, ARM, RISC-V, C++ and Java each define exactly which ones.

Try it: can both threads read zero?

Start with x = 0, y = 0. Thread A does x = 1, then reads y into rA. Thread B does y = 1, then reads x into rB. Step the two threads in any order you like. In the store-buffer model you also decide when each buffer drains to memory. Every final (rA, rB) outcome you reach is recorded below.

Publishing data safely: release and acquire

The practical question is usually "how does a consumer know the producer's data is ready?" Consider a one-shot publication. ready starts false, one producer writes data = 42 and then sets ready = true, and data is never changed again. The consumer waits until it sees ready, then reads data.

Two subtleties. An acquire load that reads false establishes nothing: the relationship exists only with the specific store it read. And acquire/release says nothing about timing, so it doesn't promise the producer runs soon or that the wait ends. The compiler turns release and acquire into whatever instructions and fences the target CPU needs. On x86 they're often free, while on ARM and RISC-V they may need special instructions.

Lost updates, and the tools that fix different problems

Two threads each run counter = counter + 1. Even if each load and each store is individually atomic, the pair isn't:

ToolWhat it guaranteesWhat it doesn't
Atomic read-modify-write (fetch_add, compare-and-swap)One variable is updated indivisiblyConsistency across several variables
Mutex / lockOnly one thread runs a critical section at a time, and unlock → lock also synchronizes memoryThat threads are fairly scheduled. Contention serializes them.
Memory fenceConstrains the order of this thread's memory operationsThat other threads reach any particular point
Thread barrierEveryone reaches the phase boundary before anyone continues, and earlier work is visible after itProgress if some participants never arrive (deadlock)
sleep, volatileNothing about inter-thread ordering in C/C++Not a substitute for any of the above

Making every field of a structure individually atomic doesn't preserve an invariant that spans several fields ("balance equals the sum of entries"). That's what a lock is for. Every tool here adds shared state and waiting, so choose by the relationship your algorithm needs, then measure the contention.

PredictName the relationship before the hardware.
  1. With store buffers, why can rA and rB both be 0? Did any cache violate coherence?
    Show answer

    Both stores are still waiting in their buffers when both loads read memory, which still holds zeros. No coherence violation: each address still has a single history (0, then 1). Only the cross-address order looks strange.

  2. State the argument that rules out (0, 0) under SC.
    Show answer

    A's store → A's load (program order). A's load reads y = 0 → it precedes B's store. B's store → B's load (program order). B's load reads x = 0 → it precedes A's store. That's a cycle, so no single global order satisfies all four constraints.

  3. In the publication example, which event makes the ordinary read of data safe? Does an acquire load that reads false help?
    Show answer

    The acquire load reading the value written by the release store (synchronizes-with). A load that reads false establishes nothing, which is why the consumer loops until it actually sees true.

  4. Why can two atomic loads and stores still lose an increment? What does fetch_add change?
    Show answer

    Each load and each store is atomic, but another thread's load can slip between them, so both threads read the same old value. fetch_add makes the read-add-write one indivisible operation, so the increments are serialized and none is lost.

  5. Match each need to a tool: "one shared counter", "update three fields together", "all workers finish phase 1 before phase 2", "keep my stores in order relative to a later load". Does volatile solve any of them in C++?
    Show answer

    Counter → atomic RMW. Three fields → mutex. Phases → barrier. Store-load order → fence (or suitable atomics). volatile solves none of them in C++: it neither makes operations atomic nor orders them between threads.

Before talking about caches or buffers, identify the language-level synchronization relationship that makes the program correct: which store is read by which load, or which lock hand-off.

Lesson 18

One core, several hardware threads

LimitationOne instruction stream often leaves a wide core's issue slots empty, whether waiting on a dependency or a cache miss.
New mechanismHardware multithreading: keep several architectural contexts resident in the core and pick work from whichever has some ready.
New statePer-context PC, architectural registers (via separate rename maps), and control/exception state.
CostExtra context state and selection logic. Threads compete for ports, queues, caches and bandwidth, so each may run slower.

Three ways to share a core

In Unit 2, switching threads meant the OS saving and restoring registers: hundreds of instructions or more. Hardware multithreading instead keeps several hardware contexts physically resident, so switching between them costs little or nothing. Designs differ in when they switch:

What's duplicated, what's shared

The operating system sees each hardware context as a separate logical processor and schedules software threads onto them. A chip with 4 cores × 2 contexts shows the OS 8 logical processors, but it doesn't have 8 cores' worth of execution hardware. The OS can still juggle many more software threads than that, saving the inactive ones to memory exactly as in Unit 2.

Try it: two dependency chains, one core

Thread A runs x5 = x5 + 1 four times starting from 0. Thread B runs x5 = x5 + 10 four times starting from 100. Each is a chain: every add needs the previous result, and a result is usable the next cycle. Both threads use the name x5, but they're different contexts, so they're different registers.

Throughput, not latency

SMT can raise total throughput by using slots one thread would leave empty. It never promises lower latency for an individual thread. A thread running alone may finish sooner than when it shares a core with a sibling that competes for the same caches, queues and bandwidth. Two threads that are both limited by memory bandwidth mostly just fight each other. That's why enabling SMT isn't universally a win: it depends on the workload, on latency goals, and on the specific core. Sharing resources also leaks timing information between siblings, which matters for security isolation (Unit 2 mentioned this).

PredictCount ports and ready operations.
  1. Two ALU ports: how many cycles do the two chains take with one-thread-per-cycle selection, and with SMT? What are the final x5 values?
    Show answer

    One thread per cycle: 8 cycles (A finishes in cycle 7, B in 8). SMT: 4 cycles. Either way A's x5 = 4 and B's x5 = 140. Scheduling changes the timing, never the results.

  2. With a single ALU issue slot per cycle, why do both policies take 8 cycles? What's the limit?
    Show answer

    There are 8 adds and only one can start per cycle. The ALU issue capacity is the bottleneck. SMT can fill empty slots, but it can't make new ones.

  3. 4 physical cores with 2 hardware contexts each: how many logical processors does the OS see? Why isn't that 8 cores?
    Show answer

    8 logical processors, but only 4 sets of execution units, caches and pipelines. Pairs of logical processors share one core's resources.

  4. What must stay distinct between resident hardware threads, and how does switching between them differ from an OS context switch?
    Show answer

    Distinct: PC, architectural registers (their mappings) and control/exception state. May be shared: ports, queues, caches, predictors, bandwidth. An OS context switch saves and restores state through memory with software. Hardware contexts are all resident at once, and the core picks among them with no save/restore.

  5. Can adding an SMT sibling raise total throughput while making the original thread slower?
    Show answer

    Yes. The sibling uses previously idle slots, so total work per second rises. But it also takes cache space, queue entries and bandwidth the original thread was using, so the original thread's own progress can slow.

Lesson 19

One instruction, many data elements

LimitationScalar code repeats the same fetch, decode and schedule work for every element of an array, even though the operation is identical.
New mechanismSIMD / vector instructions: one instruction operates on a group of elements, with masks or a vector length for partial groups.
New stateWide vector registers, mask (predicate) registers, and a current vector length.
CostWider datapaths, more register bandwidth and power. Tails and reductions need care, and memory bandwidth can become the new bottleneck.

Scalar versus vector

For c[i] = a[i] + b[i] over many elements, scalar code runs two loads, an add, a store and loop bookkeeping per element. A vector instruction applies the same operation to a whole group of elements at once, so the control overhead is paid once per group. This is data-level parallelism, the third kind in this unit, and it's the direct ancestor of how GPUs work.

Four numbers that are easy to confuse

Fixed-width SIMD (x86 SSE/AVX, Arm NEON) bakes the register width into the instruction set. Scalable vector ISAs (Arm SVE, RISC-V V) let the same program run on hardware with different vector lengths. The loop asks "how many elements can you do now?" and uses the answer:

remaining = N
while remaining > 0:
  vl = set_length(remaining)hardware returns how many it will do (≤ its maximum)
  process vl elementsvector loads, add, store
  advance pointers by vl; remaining −= vluse the returned vl, never an assumed width

In RISC-V V, the maximum is VLMAX = VLEN × LMUL / SEW: register length times register grouping, divided by element width. With VLEN = 128 bits, LMUL = 1 and SEW = 32 bits, VLMAX = 4. That's an instruction-set quantity. It doesn't promise four physical lanes or a one-cycle instruction.

Try it: the tail problem

Ten elements don't divide into groups of four. The last group needs a mask that turns off the positions past the end. In our model, masked-off positions do no memory access at all: they neither read past the array nor write output. That matters. Loading past the end of an array and throwing the extra values away later is not equivalent, because it can touch memory that isn't yours.

Layout matters here too. Vector loads want the elements they combine to be contiguous, which favours a structure of arrays (all x's together, all y's together) over an array of structures. Gathers can load scattered addresses, but they don't make scattered memory traffic cheap. Once the arithmetic is vectorized, the bottleneck often moves to memory bandwidth.

PredictUse the explorer to check.
  1. Ten elements, width 4: how many groups, what's the last group's mask, and which outputs does it write?
    Show answer

    3 groups. The last covers positions 8–11 with mask 1 1 0 0, and it writes only c[8] = 117 and c[9] = 119. Positions 10–11 do no memory access.

  2. Compare position utilization at widths 4 and 8 for 10 elements. Is the lower one necessarily slower?
    Show answer

    Width 4: 10/12 = 83.3%. Width 8: 10/16 = 62.5%. Not necessarily slower. Width 8 needs 2 instructions instead of 3, and the real time depends on throughput per instruction, masks and memory behaviour.

  3. How many useful bytes cross the array boundary for 10 elementwise 32-bit additions? Why might actual memory traffic differ?
    Show answer

    12 bytes per element × 10 = 120 bytes. Actual traffic moves whole cache lines, can include bytes you don't use, may read the output line before writing it (write-allocate), and depends on what's already cached.

  4. VLEN = 128, SEW = 32, LMUL = 1: what's VLMAX? Does it tell you the number of physical lanes or the instruction latency?
    Show answer

    VLMAX = 4. It does not tell you lanes or latency. The hardware could process the 4 elements on 1, 2 or 4 lanes over several cycles.

  5. Why is a sum different from an elementwise add? Give a reason a compiler can't vectorize every loop by packing adjacent iterations.
    Show answer

    A sum combines values from different lanes, so it needs cross-lane (horizontal) communication or partial sums. A compiler can't pack iterations that depend on each other (a[i] uses a[i−1]), or arrays that might overlap without a runtime check, or floating-point sums where regrouping changes the result, unless it's allowed to.

Unit 4 · Summary

Putting it together

Suppose two software threads each add a 10-element slice of two arrays, on two different physical cores. Each uses the width-4 vector model. The output slices don't overlap, but each thread increments its own "done" counter, and the two counters sit in the same cache line.

Work it out, then open

Vector groups: 3 per thread, so 6 in total. Useful array traffic: 12 bytes × 20 elements = 240 bytes.

Coherence: the two counters are different variables in one line, which is false sharing. Each increment takes ownership away from the other core. Pad them onto separate lines.

Knowing the work is done: the coordinator should join both threads, or use a correct release/acquire publication (each worker release-stores its flag, and the coordinator acquire-loads until it reads it). Coherent caches alone aren't a correctness argument. The language's synchronization rules are.

Move both threads onto SMT siblings of one core and the estimate changes. Their contexts remain separate, but they now compete for that one core's vector units, front end and cache bandwidth.

Form of parallelismWhat is independent?What stays shared or limiting?
Instruction-level (Unit 3)Operations within one threadDependencies, ports, front end, queues
Multicore thread-level (Lesson 16)Instruction streams on different coresMemory bandwidth, shared caches, coherence, synchronization
Hardware multithreading / SMT (Lesson 18)Resident contexts on one coreExecution ports, queues, caches, front end
SIMD / vector data-level (Lesson 19)Element operations within one instructionVector throughput, masks, reductions, data supply

A real program can use all four at once, and none of them speeds anything up just by existing. The next unit carries these distinctions into GPUs, where they're pushed to the extreme: thousands of logical threads, grouped for lockstep SIMD-style execution, scheduled across many hardware contexts, and limited by the memory traffic that feeds them.
