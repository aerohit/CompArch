Understand GPUs

Unit 4 showed how cores, hardware contexts and vector lanes can work on different pieces of a problem at once. A GPU holds execution state for many logical threads and groups their instructions across lanes. When one group waits, another may have instructions ready to issue. This organization supports high throughput: completing many pieces of work per unit of time. Using it well requires enough independent work, efficient memory access patterns and coordination where threads share data.

Lesson 20

From an array loop to SIMT

LimitationA CPU vector instruction handles several elements, depending on the vector width and element size. A large array still requires many vector instructions, and one core has limited capacity to keep working while memory requests are pending.
New mechanismSIMT, single instruction, multiple threads. Each thread runs the same function on its own values; the hardware groups threads and issues an instruction for the group.
New stateEach thread has private values and an index. A streaming multiprocessor (SM) holds the registers, shared memory and scheduling state for the groups currently assigned to it.
CostThe chip needs storage for many thread contexts. Some lanes sit idle at array boundaries or when threads take different branches, and copying inputs to GPU memory can add transfer time.

One thread per element

Take the loop for (i = 0; i < N; i++) c[i] = a[i] + b[i];. Assume the input and output arrays do not overlap. The addition for c[5] then needs only a[5] and b[5]; it does not wait for c[4]. All N additions can therefore happen in any order. A CPU could split the loop across cores and vectorize each chunk (Lesson 19). In CUDA, NVIDIA's GPU programming model, a function launched on the GPU is called a kernel. This kernel describes the work for one element. Each logical thread executes the function for its assigned index:

__global__ void add_arrays(const float* a, const float* b, float* c, size_t n) {
  size_t i = size_t(blockIdx.x) * blockDim.x + threadIdx.x;
  if (i < n) c[i] = a[i] + b[i];
}
// launch (a, b, c are valid device pointers): unsigned threads = 64;
// if (n > 0) { size_t blocks = (n + threads - 1) / threads; // round up
// add_arrays<<<blocks, threads>>>(a, b, c, n); } // blocks must fit the device's grid limit

The __global__ qualifier marks the function as a kernel. The launch shown in the comments chooses a number of blocks and a number of threads per block; these two counts appear between the triple angle brackets. The arrays are assumed to be allocated in memory accessible to the GPU. Every thread receives its position within the launch: blockIdx.x names its block, blockDim.x is the number of threads in a block, and threadIdx.x is its position within that block. All indices start at 0. Multiplying the block number by its size, then adding the position within it, gives a unique array index. Because the launch rounds up to whole blocks, the guard if (i < n) keeps surplus threads from accessing beyond the arrays.

For N = 70 and 64 threads per block, block 0 handles indices 0–63 and block 1 starts at 64. Thread 5 of block 1 computes 1 × 64 + 5 = 69 and does the addition. Thread 6 computes 70 and fails the guard. The formula assigns work; it does not say where on the chip either block will run.

In SIMT (single instruction, multiple threads), the program describes individual threads, each with its own index, private values and control flow. The hardware issues instructions for groups of threads, usually using SIMD-style execution lanes. The thread model determines which values and branches belong to each thread; the lanes perform the operations for the participating threads.

Hardware capacity limits how many threads can run at once. A launch may create a million logical threads, but the GPU admits only the groups whose state fits on its processing units. These threads are resident: their state is held on the chip, available to the hardware scheduler. The hardware selects instructions from resident groups while the remaining groups wait for space.

How threads are grouped and placed on the GPU

In CUDA, a block is a group of threads that can cooperate through shared storage and synchronization. All the blocks in one kernel launch form a grid. NVIDIA hardware groups the threads within each block into warps of up to 32 threads, then assigns whole blocks to streaming multiprocessors (SMs). A thread's position within its warp is its lane, numbered from 0 to 31. The diagram shows how a grid's blocks use the finite space on those processing units.

Hardware limits still depend on the device: a CUDA warp has 32 lane positions, while AMD wavefront widths and compute-unit organization vary by architecture. During ordinary execution, a CUDA block runs on one SM. Several blocks can share that SM if their state fits; blocks awaiting space remain unscheduled.

Blocks must work regardless of their scheduling order. If block 0 waits for block 1 to signal it, block 1 might still be waiting for an SM slot. If all the slots are occupied by waiting blocks, the program cannot make progress: it has deadlocked. Separate kernels ordered in the same execution queue can provide a handoff across the whole grid (Lesson 24). The number of blocks that fit at once determines when this scheduling problem can occur.

Try it: map elements to blocks, warps and lanes

Follow one value through the machine

For an index within the array, thread i loads a[i] and b[i], adds them in a private register, and stores c[i]. Its neighbours in the warp run the same instructions on their own values: register r1 in lane 5 and r1 in lane 6 are different storage. A warp instruction describes the group's operation, but the hardware may carry it out over several cycles or on specialized units. Warp width specifies the grouping of threads; the instruction and hardware implementation determine how many physical ALUs execute it and how long it takes.

CUDA calls the CPU the host and the GPU the device. The CPU enqueues the launch by adding it to a queue of GPU work, and it can continue before the GPU finishes. To use the result on the CPU, the program must wait for completion and, when necessary, copy c back to host memory. Within an SM, a scheduler can issue an instruction from another resident warp while one waits for data. This can keep the execution units working when the other warp has a ready instruction. It does not remove dependencies within a thread: following one linked-list pointer to discover the next still requires sequential loads. Lesson 21 examines what limits the number of resident warps and what makes their instructions ready to issue.

PredictUse the explorer to check.
  1. N = 70 with 64 threads per block: how many blocks, launched threads and warps? How many lanes of block 1's first warp pass the guard?
    Show answer

    2 blocks, 128 threads, 4 warps (two 32-thread warps per block). Block 1 starts at global index 64, so only indices 64–69 pass i < 70: 6 lanes of its first warp. Its second warp has no useful lanes. Those 58 surplus threads exist; they just skip the guarded work.

  2. With 48 threads per block, thread 17 of block 2 has which global index, warp and lane? Why can't a partial warp borrow threads from the next block?
    Show answer

    Global index 2 × 48 + 17 = 113. Warp ⌊17 / 32⌋ = 0, lane 17 mod 32 = 17. CUDA forms warps from consecutive thread indices within each block. It does not combine the remaining threads of one block with threads from another; the next block starts its own warp numbering. A block also defines which threads cooperate through its shared memory and block-wide synchronization.

  3. Does launching 1,000 blocks mean 1,000 are resident at once, or that block 0 runs first?
    Show answer

    Neither. Only as many blocks as fit are resident; the rest wait. The scheduler promises no order by block number. A correct kernel works under any permitted schedule, and one where resident blocks wait for a not-yet-scheduled block can deadlock.

  4. Distinguish a thread's register value, a block's shared-memory value and an element of a global array.
    Show answer

    A register value belongs to one thread; the SM's register storage holds the values for its resident threads. Shared memory belongs to a block and lets its threads cooperate. A global array element has an address any block can reach. Threads that communicate through that array need synchronization to order conflicting accesses, as in Lesson 17.

  5. Why doesn't a 32-thread warp imply 32 physical ALUs per instruction, or a one-cycle latency?
    Show answer

    Warp width is a logical grouping. The instruction and hardware implementation determine the number of physical lanes used, how many cycles execution spans, and when the result becomes available. Those properties must be established separately from the warp's thread count.

Lesson 21

Keeping work ready on an SM

LimitationWhile a warp waits for a load, its scheduler needs another ready warp to issue an instruction. Within a divergent warp, only some lanes participate in each instruction.
New mechanismKeep many warps resident and issue from whichever is ready. Execute divergent paths under an active mask.
New stateDependency records (scoreboards) that track pending results, masks that select participating lanes, information for rejoining branch paths, and resource allocations for resident blocks.
CostRegisters and shared memory limit how many warps fit. Masked lanes do no useful work.

Resident, eligible, issued

Lesson 20 showed that an SM can hold several warps. A scheduler can issue an instruction from one warp while another waits, provided the first warp has ready work. Three terms describe the steps from keeping a warp on the SM to executing its next instruction:

  • A resident warp belongs to a block admitted to the SM. Its execution state and allocated registers remain on the SM while it waits.
  • An eligible warp can issue its next instruction now: the instruction is available, its operands are ready, the required execution pipeline can accept it, and no synchronization is holding it back.
  • An issued warp is one whose instruction the scheduler selects and sends to an execution pipeline. Other eligible warps may have to wait for a later issue slot.

A warp can be resident for hundreds of cycles without being eligible, for example while its next instruction waits for a load result. Occupancy is the number of resident warps divided by the SM's maximum resident-warp count. It measures capacity in use. Even at full occupancy, a scheduler can have no instruction to issue if all its warps are waiting.

Try it: what fits on a teaching SM

Our invented SM has room for at most 8 warps, 256 threads, 4 blocks, 8,192 registers (32-bit) and 16 KiB of shared memory. Suppose a block has T threads, each using R registers, and the block reserves S KiB of shared memory. At T = 64, that block occupies two warp slots, 64 × R registers and S KiB. We can divide each SM capacity by the corresponding block cost; the smallest whole-block count decides how many blocks fit:

warps_per_block = ⌈T / 32⌉
blocks = min(4, ⌊256 / T⌋, ⌊8 / warps_per_block⌋, ⌊8192 / (T × R)⌋, ⌊16 / S⌋)
occupancy = blocks × warps_per_block / 8
if S = 0 the block uses no shared memory: drop the ⌊16 / S⌋ term

This is the potential occupancy the resource limits allow. The achieved occupancy measured on a real run can be lower, for example when the grid has too few blocks to fill every SM, or near the end as blocks finish and nothing replaces them.

With T = 64, R = 32 and S = 4, four blocks fit: 8 warps, 100%. Double R to 64 and the register file only holds two blocks: 50%. Keep R = 32 but double S to 8 KiB and shared memory also allows only two blocks: 50%. Both configurations have 50% occupancy. Allowing more blocks to fit would require reducing register use in the first case or shared-memory use in the second.

Higher occupancy can increase memory work. Forcing the compiler to use fewer registers can admit more warps but cause spills: values that no longer fit in registers are stored to thread-private memory and reloaded, adding instructions and memory traffic. Reducing a block's shared-memory allocation can also admit more warps while leaving less room for data reuse. A change helps only if the additional ready work saves more time than the additional memory work costs.

Try it: hide latency by picking another ready warp

Start with just one warp executing LD → ADD → STORE. If its load issues in cycle 1 and takes four cycles, the ADD cannot use the value until cycle 5. Issue slots 2–4 sit empty. Other ready warps could fill those slots without shortening that first load.

The explorer uses one issue slot per cycle: an opportunity for the scheduler to send one instruction to an execution unit. A load issued in cycle c supplies its value at the start of cycle c + L, and an ADD supplies its result the next cycle. Among eligible warps, the scheduler chooses the lowest numbered. The model omits bandwidth and instruction-fetch delays. A warp counts as done when its STORE issues, without modelling when that store completes or becomes visible.

At L = 4, four warps can issue their loads in cycles 1–4. Warp 0's ADD issues in cycle 5 and its STORE in cycle 6; the scheduler then selects the other ready warps. All 12 issue slots are used. Counting each three-instruction sequence as one unit of work, four warps issue four units in 12 cycles (1/3 unit per cycle), compared with one warp's one unit in 6 cycles (1/6 per cycle). Throughput doubles by this measure, even though warp 3 takes longer to reach its STORE than it would alone. Every load still has the same four-cycle latency.

Try L = 16: more resident warps are needed to cover the longer wait. Real GPUs have multiple issue paths, other instruction latencies, and finite memory queues and bandwidth. Independent instructions within one warp can also fill gaps. Once a memory channel is saturated, however, issuing from more warps cannot make it transfer more bytes.

Try it: follow the active lanes through a branch

Issuing a warp instruction does not mean all 32 lanes participate. When lanes choose different branch paths, the warp must execute instructions from both paths. Each instruction has an active mask, whose set bits identify the participating lanes; lanes on the other path do no work for that instruction. As in Lesson 19, a compiler may instead predicate a short branch, issuing instructions with a per-lane condition that suppresses their effects where they are not needed.

Use the 8-lane model below to see the cost; CUDA warps have 32 lanes. Each lane starts with its lane number + 1. The true path does +10, ×2 (2 instructions); the false path does −1, ×3, +5 (3 instructions). A path with no active lanes is skipped.

If every lane in a warp chooses the same side, that warp runs only one path; other warps can choose differently. The warp avoids issuing instructions with lanes disabled by the other path, although the branch and the chosen path still take time. Grouping data so neighbouring lanes make the same choice can reduce this cost. Any speedup must also cover the cost of rearranging the data and any increase in memory traffic.

Communication within a warp needs synchronization. Diagrams with one shared program counter are a simplification. Starting with Volta, NVIDIA GPUs maintain a program counter and call stack for each thread and can let threads within a warp progress independently. Code that exchanges data between lanes must establish when the writes are ready for other lanes to read.

For example, a block of exactly one warp (32 threads, all active) exchanges values through shared memory:

__shared__ int slot[32];
int lane = threadIdx.x % 32;
slot[lane] = my_value;                // each lane writes its own slot
__syncwarp();                         // default full mask: all 32 lanes must reach it
int left = slot[(lane + 31) % 32];    // now safe to read a neighbour's slot

Without __syncwarp(), lane 5 could read slot[4] before lane 4 writes it. The call waits for its participating lanes and orders their shared-memory accesses, so each read here follows its neighbour's write. All 32 lanes in this example are active and reach the default full-mask call.

Every non-exited lane named in the mask must call __syncwarp with the same mask. Only the named lanes in that warp participate; __syncthreads coordinates the whole block. With independent thread scheduling, the hardware still groups participating threads from a warp to issue a common instruction. Instructions from different branch paths therefore issue for separate groups of active threads.

PredictCheck each with an explorer.
  1. On the teaching SM, what is the potential occupancy for T = 64, R = 64, S = 4? What limits it? What about R = 32, S = 8?
    Show answer

    Each block is 2 warps and needs 64 × 64 = 4,096 registers. The register file allows ⌊8192 / 4096⌋ = 2 blocks: 4 warps, 50%, limited by registers. With R = 32 and S = 8 KiB, shared memory allows ⌊16 / 8⌋ = 2 blocks: again 50%, now limited by shared memory.

  2. Why might cutting a kernel's register count raise occupancy and still make it slower?
    Show answer

    Values that no longer fit spill to thread-private memory, adding loads, stores, latency and traffic. Those costs can exceed the time saved by keeping more warps ready. Check the compiler's spill report and measure the kernel's execution time.

  3. In the scheduler model (L = 4), when can a load issued in cycle 2 first feed its ADD? How many cycles and filled slots for two warps?
    Show answer

    Its value is ready at the start of cycle 6. But in cycle 6 the lowest-numbered rule picks warp 0's STORE, so warp 1's ADD issues in cycle 7. Two warps take 8 cycles and fill 6 of 8 slots (75%). Warp 1 spends a cycle eligible but unselected.

  4. In the divergence model, one lane takes the true path and seven the false path. What is the utilization?
    Show answer

    Both paths run: 2 + 3 = 5 group instructions, 8 × 5 = 40 positions. Useful: 1 × 2 + 7 × 3 = 23. Utilization 57.5%, different from the 4/4 split's 50% because the paths have different lengths.

  5. A profiler shows high occupancy, but few eligible warps and little issue activity. Is adding more arithmetic units a demonstrated fix?
    Show answer

    No. These measurements show that resident warps are waiting, but do not identify the cause. Check whether instructions wait for dependent loads, previous arithmetic results, synchronization, or an execution pipeline that cannot accept more work. Memory traffic, bandwidth and stall reasons help distinguish these cases. More arithmetic units would help only if the corresponding execution capacity is the limiting factor.

When profiling a kernel, check how many warps are resident, how many are eligible, how often the scheduler issues an instruction, and how many lanes participate in each issued instruction.

Lesson 22

Make the memory traffic explicit

LimitationA warp with 32 active threads can request 32 addresses in one load instruction. Scattered addresses can require transfers that include many bytes the instruction does not use.
New mechanismCoalescing merges a warp's requests into as few fixed-size transfers as cover them. Shared memory is split into banks that serve lanes in parallel.
New stateThread-private registers and local memory, block-shared memory, global memory, and hardware-managed caches.
CostData layout affects both the bytes transferred from global memory and the number of requests a shared-memory bank must serve in turn.

Name the storage and who can see it

The array-add thread keeps its sum in a register and reads its inputs from a global array. Other kernels also need a place for threads in one block to exchange data. A memory space defines which threads can access its data; its physical storage determines how those accesses are served. The diagram shows both, including the caches between an SM and device memory.

StorageWho owns itWhat to remember

CUDA local describes thread-private visibility; it does not promise on-chip storage. A cache miss can require the same device-memory access as a global-memory load. Likewise, a global load that hits in a cache can be served without reading DRAM. AMD calls its corresponding shared scratchpad Local Data Share (LDS).

Try it: count sectors for one load instruction

Imagine 32 active lanes, each loading one 4-byte word: 128 useful bytes in all. If their words are contiguous and start on a 32-byte boundary, eight words fill each 32-byte sector, so four sectors cover the load. If the addresses spread out, the memory system must fetch more sectors to deliver the same 128 useful bytes.

In the explorer, lane l requests byte address base + 4 × stride × l. Each word is aligned, sectors are aligned 32-byte units, and all requested sectors initially lie outside the cache being modelled. Count distinct sectors touched by one load instruction.

That count can guide data layout. Suppose each record is two 4-byte floats, {x, y}, and a warp loads only x from 32 records. In an aligned array of structures, neighbouring x values are 8 bytes apart: 128 useful bytes occupy 8 sectors, or 256 sector bytes. With a separate, aligned x[] array—a structure of arrays layout—the x values are contiguous and occupy 4 sectors, or 128 sector bytes. If the kernel also needs y, compare both loads before choosing a layout.

This 32-byte sector model reflects recent NVIDIA GPUs. The table counts the sectors needed to serve one instruction's requests, assuming none of those sectors is already in the cache being modelled. Neighbouring warps may reuse the fetched sectors, and caches or request merging can reduce traffic farther down the memory hierarchy. The sector count therefore does not specify how many commands reach DRAM.

Try it: shared-memory banks

Shared memory is faster than a trip to device memory, but it has limited service capacity too. It is divided into banks. In our 8-bank, 8-lane model, bank w mod 8 holds 4-byte word w; each bank serves one distinct word per round. For example, word 0 and word 8 both map to bank 0. If different lanes ask for those two words together, that bank needs two rounds: a bank conflict. If they ask for the same word, the bank can broadcast it in one round.

Use the bank diagram to compare a column of an 8×8 tile (word stride 8) with the same tile padded to a row length of 9. The padding changes the addresses of successive values in that column, and therefore the banks that serve them. To evaluate another layout, compute the addresses an instruction actually requests and map each to its bank.

Code and storage choices change traffic at different places. Spilled register values add private-memory loads and stores. Poor coalescing fetches extra sector bytes; a cache hit may prevent some of those bytes from reaching DRAM. Shared-memory staging adds instructions but can avoid repeated global loads.

In the vector-add example, each input is used for one output, so staging it in shared memory would not avoid later global loads. Each result needs two 4-byte inputs and one 4-byte output, or 12 useful bytes per element. If memory bandwidth limits this kernel, adding arithmetic units cannot increase the rate at which those bytes arrive. Matrix multiplication, in the next lesson, uses the same inputs for multiple outputs and can benefit from staging them.

PredictCheck with the explorers.
  1. Stride 2, aligned base: how many sectors and sector bytes? What fraction is useful?
    Show answer

    Addresses 0, 8, 16, …, 248: each 32-byte sector holds four requested words. 8 sectors, 256 bytes for 128 useful: 50%.

  2. Stride 1: what changes when the base moves by 4 bytes? Why might a whole array's DRAM traffic differ from summing these per-warp counts?
    Show answer

    Bytes 4 to 131 now touch a fifth sector: 160 bytes, 80%. The next warp also needs that sector. If it remains cached, the next warp can reuse it without another DRAM read. Cache reuse and request merging can therefore make an array's DRAM traffic lower than the sum of its per-warp sector bytes.

  3. In the 8-bank model, compare rounds for word addresses l, 8l, 9l and the constant 0. Which uses broadcast?
    Show answer

    l: 1 round. 8l: 8 rounds, eight different words all in bank 0. 9l: 1 round, since 9l mod 8 = l. 0: 1 round, by broadcast of the one word.

  4. Why can a CUDA local-memory load cost far more than a register read? Does being thread-private put it on chip?
    Show answer

    Local memory is an address space with private visibility, backed by device memory and reached through the caches. A cache miss can require a device-memory access. A register read obtains the value directly from the SM's register file without issuing a local- or global-memory load.

  5. Two access patterns touch exactly the same sectors in a different lane order. Must their sector counts differ? Could the kernels still perform differently?
    Show answer

    The counts are equal: a permutation of lanes doesn't change the set of sectors. Whole kernels can still differ through cache reuse across instructions, dependencies, divergence, instruction count or bank conflicts.

Lesson 23

Reuse matrix entries in a shared tile

LimitationSeveral outputs in a matrix multiplication need the same input entries. Loading each entry separately for each use repeats global-memory requests.
New mechanismTiling: a block loads a small piece of each input into shared memory, then its threads reuse those entries to compute several outputs.
New stateShared tiles owned by the block, plus a private running sum in each thread's registers.
CostThe block's shared memory and registers can limit how many blocks reside on an SM. This simple loop uses two barriers per tile to prevent races.

Why matrix multiplication rewards reuse

In C = A × B, output C[r, c] is the dot product of row r of A and column c of B: multiply matching entries, then add the products. In symbols, C[r, c] = Σk A[r, k] × B[k, c], where Σ means sum over k. For example, C[0, 0] and C[0, 1] both use A[0, 0], then A[0, 1], and so on. Outputs in one row share A's row; outputs in one column share B's column. A block can load each needed input entry once and share it among the threads computing those outputs.

A tile is a small region of outputs computed together. One block owns a T × T tile of C. For T successive values of k, the block loads a T × T piece of A and a T × T piece of B into shared memory, where its threads can reuse them. It then replaces those pieces for the next T values of k. Each thread keeps its own output's running sum in a private register throughout.

Try it: a complete 2 × 2 tile, step by step

A is 2 × 4 and B is 4 × 2, so C is 2 × 2. Four threads in one block own its four outputs: thread (r, c) accumulates C[r, c]. Summing the products over k is a reduction: it combines several values into one. Here each output sums four products, so the reduction length is 4. The shared tiles have width 2, and the block processes k = 0, 1 in the first round, then k = 2, 3 in the second.

In each round, every thread loads one A entry and one B entry into shared memory. Four threads load eight words in total, then each thread uses some entries its neighbours loaded. Follow the loads, the two barriers, and one private sum in the stepper.

After the first tile (k = 0, 1) the partial sums are [[7, 10], [23, 34]]. Thread (0, 0), for instance, computes 1 × 1 + 2 × 3 = 7. The second tile (k = 2, 3) adds 3 × 5 + 4 × 7 = 43 to it, giving 50. The final result is [[50, 60], [114, 140]]. C's dimensions specify four outputs; the reduction length specifies the four products summed for each output.

Thread (0, 1) loads A[0, 1] = 2 into As[0][1] and B[0, 1] = 2 into Bs[0][1] during the first load phase. Computing its own C[0, 1] also requires values loaded by neighbours: As[0][0] = 1 and Bs[1][1] = 4. Its first partial sum is 1 × 2 + 2 × 4 = 10. A thread's load assignment supplies entries for several outputs, while computing one output uses entries supplied by several threads.

The two barriers protect different phases

__syncthreads() is a block barrier: threads that have not exited must reach the same barrier call before any can proceed. Shared-memory writes made before the barrier are visible to the participating threads after it. The tiled loop uses one barrier after loading to make the entries ready for all readers, and another after computing to let all readers finish before any thread replaces an entry:

Here is the kernel for square n × n row-major matrices. Row-major storage places the entries of each row next to one another, so entry (row, col) is at array index row × n + col. Assume C does not overlap either input array. Launch ⌈n / T⌉ × ⌈n / T⌉ blocks of T × T threads, with T small enough to satisfy the device's block and resource limits:

template<int T> __global__ void tiled_square(const float* A, const float* B, float* C, size_t n) {
  __shared__ float As[T][T], Bs[T][T];
  int x = threadIdx.x, y = threadIdx.y;
  size_t row = size_t(blockIdx.y) * T + y, col = size_t(blockIdx.x) * T + x;
  float sum = 0.0f;// private running sum
  for (size_t base = 0; base < n; base += T) {
    As[y][x] = (row < n && base + x < n) ? A[row * n + base + x] : 0.0f;
    Bs[y][x] = (base + y < n && col < n) ? B[(base + y) * n + col] : 0.0f;
    __syncthreads();// barrier 1: tile is loaded
    for (int k = 0; k < T; ++k) sum += As[y][k] * Bs[k][x];
    __syncthreads();// barrier 2: everyone finished reading
  }
  if (row < n && col < n) C[row * n + col] = sum;// guard only the store
}

At an edge tile, some source positions lie outside A or B. The corresponding threads put zero into shared memory instead of reading an invalid address; zero adds nothing to a sum. A thread whose own output lies outside C must still load its assigned tile entries, because another thread may need them. That is why the load-and-compute loop runs for every thread and only individual global accesses and the final store are guarded.

Every thread in this kernel executes the same two barriers on each round. If some threads that have not exited branch around __syncthreads(), the synchronization is invalid and may hang or produce incorrect results. A thread that has exited no longer participates in the barrier, but returning before its assigned loads can leave shared entries missing for other threads. Keeping edge threads in the loop preserves both the cooperative loads and the common barrier sequence. Production libraries often give each thread several outputs, use other tile shapes, and overlap loading with computing.

Which threads form a warp in a 2D block?

The tiled kernel uses 2D blocks, but warps are still formed from a linear numbering, with x varying fastest:

linear thread index = threadIdx.x + blockDim.x × threadIdx.y
warp = ⌊index / 32⌋, lane = index mod 32

Take a 16 × 16 block loading a tile of a float matrix A. Assume A starts on a 128-byte boundary, its rows are 1,024 floats (4,096 bytes) apart, and the tile starts at a column that's a multiple of 16. Warp 0 contains rows y = 0 and y = 1, with x = 0…15 in each. Each row's 16 floats occupy 64 contiguous, 64-byte-aligned bytes. Thus the warp's load touches 2 sectors per row, 4 in total for 128 useful bytes, even though the rows are 4 KiB apart.

The same warp writes As[y][x] into a shared tile with row length 16. Its 32 destinations are consecutive words, so with 32 banks (current NVIDIA GPUs) every lane reaches a different bank: one round. Row pitch, the spacing between row starts, and tile width determine these addresses; changing either can change the sector or bank count.

The compute phase has a different shared-memory pattern from the load phase. At one k, threads computing outputs in the same row all read As[y][k], so that one word can be broadcast to them. Neighbouring output columns read neighbouring Bs[k][x] words, which can be served by different banks. The bank count depends on the instruction's actual addresses; loading and computing with the same tile can produce different counts.

What a tile costs in resources

With one thread per output, a T × T tile uses T² threads per block. Its two T × T float input tiles take 2T² × 4 = 8T² bytes of shared memory before any double buffering. At T = 16, that is 256 threads and 2 KiB; at T = 32, 1,024 threads and 8 KiB.

In this mapping, the thread count is often the tighter constraint: 1,024 threads is a common per-block maximum. Production kernels commonly give each thread several outputs instead. Check the limits of the actual device. Lesson 24's “tile 64” is a traffic model, not a proposed 64 × 64-thread block.

Count the reuse

For one T × T output tile, let the reduction length K be a multiple of T. Each of the K/T rounds loads two T × T input tiles: (K/T) × 2T² = 2TK input words. At the end, the block writes T² outputs. Each output performs K multiplications and K additions. Counting each as one floating-point operation, or FLOP, gives 2T²K FLOPs. Dividing this work by the requested bytes gives the arithmetic intensity for these requests. With 4-byte words:

requested bytes = 4 × (2TK + T²)
FLOPs = 2T²K
intensity = TK / (4K + 2T) FLOPs per byte

For our example (T = 2, K = 4), the tiled version requests 16 input words and writes 4 outputs: 80 bytes for 32 FLOPs. Fetching both operands separately for every multiply-add would request 32 input words and write the same 4 outputs: 144 bytes for 32 FLOPs. A wider tile can raise arithmetic work per requested byte by reusing each loaded value more often.

These byte counts come from the program's load and store requests. Actual DRAM traffic can differ: a cache might serve repeated loads in the untiled version, while tiling adds instructions and barriers. The ratio 144 / 80 therefore does not predict a 1.8× speedup.

A double-buffered version keeps two sets of A and B input tiles, loading the next set while computing on the current one. Threads must wait for each buffer's loads to complete before reading it, and for its readers to finish before overwriting it. An asynchronous copy starts a transfer that may finish later; its completion must be established before using the data.

To estimate how these saved requests affect running time, compare arithmetic work with bytes moved across a particular memory boundary, such as DRAM. Lesson 24 makes that comparison and explains which quantities must be measured.

  2. Name one failure allowed by removing the barrier after loading, and a different one allowed by removing the barrier before the next load.
    Show answer

    Without barrier 1, a thread can read a tile entry before its neighbour has written it. Without barrier 2, a fast thread can overwrite an entry with the next tile's value while a slow thread is still reading the current one. The first orders writing before reading; the second orders reading before rewriting.

  3. Count input words, output words and FLOPs for the example. Why isn't 144 / 80 a measured speedup?
    Show answer

    Tiled: 16 input + 4 output words = 80 bytes, 32 FLOPs. Independent operand loads: 32 + 4 words = 144 bytes, a ratio of 1.8. It counts requested bytes. Caches can cut the naive version's physical traffic, and tiling adds instructions and barriers, so the time ratio must be measured.

  4. At an edge tile, why fill invalid positions with zero and still reach both barriers? What happens to invalid stores?
    Show answer

    Zero contributes nothing to a sum, and writing it into shared memory avoids reading an invalid source address. Threads whose output lies outside C may still load valid entries that other threads need. All threads in this kernel complete their assigned loads and follow the same two barriers so the shared entries are ready before use and remain intact until every reader finishes. Threads whose output lies outside C skip the final store.

  5. If T doubles in this one-thread-per-output kernel, how do threads and shared-memory bytes per block change? Does extra reuse guarantee higher speed or lower occupancy?
    Show answer

    Both are proportional to T², so doubling T makes each four times as large. More reuse can reduce repeated global requests, but the larger block may fit fewer times on an SM, or occupancy may stay unchanged if another limit dominates. T = 32 already uses 1,024 threads, a common block limit. Bank behaviour, edge waste, barriers and total time still need measurement. Neither faster execution nor lower occupancy follows automatically.

  6. Barrier 2 protects the tile from being overwritten by the next load. After the last tile, is barrier 2 still needed?
    Show answer

    The final iteration needs no barrier against a later tile load. There is no next load to overwrite As or Bs. Keeping the barrier on every iteration keeps the loop simple and uniform, but executes one unnecessary barrier per block. The kernel may skip it on the final iteration if all threads follow that same decision.

For every shared tile entry and every private sum, say who writes it, who reads it, and how long it must live. Explain each barrier with a concrete producer/consumer race.

From diagrams to a performance hypothesis

Lesson 23 cut the number of requested bytes, but a smaller byte count alone does not tell us how much faster the kernel can run. We need two rates: how quickly the GPU can perform the arithmetic, and how quickly the chosen memory boundary can supply the data.

Call the kernel's floating-point work W, counted in FLOPs as in Lesson 23. Call the bytes it moves across a named memory boundary, such as between the GPU's caches and DRAM, Q. Its arithmetic intensity is I = W / Q FLOPs per byte. Let P be the compute ceiling for this kind of arithmetic and β the bandwidth at that boundary. The work needs at least W / P seconds and the data movement at least Q / β seconds. Even if they overlap perfectly, the kernel cannot finish before the slower requirement:

performance ≤ min(P, β × I)
execution time ≥ max(W / P, Q / β)
ridge point = P / β// intensity where the two meet

The resulting limit is called the Roofline model because its performance graph has a sloping bandwidth ceiling and a flat compute ceiling. It gives a best-case bound on execution time. Dependencies, issue limits, synchronization or too little parallel work can make the actual run slower. Use ceilings that match the instructions and precision: a matrix-unit peak is not the compute ceiling for scalar addition. At intensities below the ridge point, memory movement sets the lower performance ceiling; above it, computation does. These are the model's memory-bound and compute-bound regions. A measured point below the sloped roof does not, by itself, prove that DRAM bandwidth is saturated.

Try it: a Roofline you can check by hand

Use a made-up device with P = 10 TFLOP/s for our arithmetic and β = 200 GB/s. These are decimal units: 1 TFLOP/s is 10¹² floating-point operations per second, 1 GFLOP/s is 10⁹, and 1 GB is 10⁹ bytes. Start with vector addition. In this explorer, every counted byte is assumed to cross the DRAM boundary exactly once, so requested bytes stand in for DRAM bytes; real caches can change that. The matrix presets use 1024 × 1024 inputs, 2n³ FLOPs and requested bytes 8n³/T + 4n², derived below. “Tile 64” describes the reuse used to count traffic, not a 64 × 64-thread launch.

Here is the matrix byte formula. If T divides n, there are (n/T)² output tiles. For one output tile, the reduction covers n positions and requests 2Tn input words: T A words and T B words at each position. Multiply by the number of output tiles to get 2n³/T input words, or 8n³/T bytes for 4-byte floats. Writing n² outputs adds 4n² bytes. This counts requested bytes with no reuse between output tiles; a cache may keep some of them from crossing DRAM.

For vector addition, one million float additions perform W = 10⁶ FLOPs and request Q = 12 × 10⁶ bytes, so I = 1/12 FLOP per byte. At the stated ceilings, computation takes at least 0.1 μs, while moving the bytes takes at least 60 μs. The longer memory requirement sets the time bound, giving a performance ceiling of about 16.7 GFLOP/s. Doubling P cannot shorten that 60 μs bound; doubling β could halve it in this model.

The ridge point, where the two ceilings meet, lies at P / β = 10 × 10¹² / (200 × 10⁹) = 50 FLOPs per byte. The vector add's 1/12 is far to its left. Reusing loaded values, as in tiled matrix multiplication, raises intensity by reducing Q for the same work W. Adding arithmetic merely to raise the FLOP count increases W and does not make the original task faster.

Add H = 10 μs of fixed overhead that does not overlap with the kernel. The modelled vector add takes 10 + 60 = 70 μs, an effective 10⁶ FLOPs ÷ 70 μs ≈ 14.3 GFLOP/s including H. A hypothetical version that halves its traffic would take 10 + 30 = 40 μs, a 1.75× speedup rather than 2× because the same 10 μs remains. These effective rates and the kernel-only ceiling describe different intervals. A measurement must specify which interval it covers.

Decide what "time" means

A kernel launch is normally asynchronous with respect to the CPU: the call submits work to a GPU stream and can return before that work finishes. Submission itself takes time, and the CUDA runtime may stall the host when resources are unavailable. Timing just the launch call therefore measures host-side submission, not how long the GPU takes to execute the kernel. Choose the interval that answers your performance question:

QuestionInclude in the interval
How long does this kernel run on data already on the device?The device work in one stream, bracketed by events; no allocation or copies
How long from input to usable output?Copies, launches, computation, dependencies and completion
How much work can a pipeline sustain?A steady-state batch with its intended overlap, divided by the work completed
cudaEvent_t start, stop;
cudaEventCreate(&start);  cudaEventCreate(&stop);   // timing enabled by default
cudaEventRecord(start, stream);
add_arrays<<<blocks, threads, 0, stream>>>(a, b, c, n);
cudaEventRecord(stop, stream);
cudaEventSynchronize(stop);                        // wait until the GPU passes 'stop'
float ms = 0;
cudaEventElapsedTime(&ms, start, stop);            // device time between the events
// check the return codes and cudaGetLastError() in real code

For device time, put the start event, kernel and stop event in the same stream, in that order. An event marks the GPU's progress through that stream; waiting for the stop event establishes that the preceding work has completed. Read the elapsed time only after that wait. Other work on the GPU can still stretch the interval, so record what else was running. For a pipeline that overlaps copies and computation, measure steady state after it has filled and before it drains. Divide the completed work by elapsed time to report throughput, or invert that ratio to report time per item.

Repeating the kernel R times and dividing the total can reduce timer-resolution error. It can also change the workload: later runs on the same data may hit in cache if the working set fits, and a slowly enqueueing CPU may leave gaps between launches. Report whether the data was warm or cold and inspect the timeline when the numbers surprise you.

Order dependent phases with streams and events

An algorithm may need every block to finish producing intermediate results before any block starts consuming them. Within an ordinary kernel, a block cannot assume that the other blocks are running; spinning until an unscheduled block signals it can deadlock. A kernel boundary supplies the ordering. With the ordinary launches shown below, work queued in one stream runs in order. A consumer kernel launched after a producer in that stream starts after the producer completes and sees its global-memory results. For the cross-stream example, assume s1 and s2 are independent streams:

produce<<<grid, block, 0, s>>>(buf);   // phase 1 writes buf
consume<<<grid, block, 0, s>>>(buf);   // same stream: starts after produce completes

// Across independent streams, add an explicit dependency:
produce<<<grid, block, 0, s1>>>(buf);
cudaEventRecord(done, s1);
cudaStreamWaitEvent(s2, done, 0);          // s2 waits for the event, the host doesn't
consume<<<grid, block, 0, s2>>>(buf);

In independent streams, launching the consumer without the event supplies no producer-to-consumer dependency: the consumer may start before the producer finishes. Recording the event after produce and waiting for it in s2 creates that dependency. The CPU can continue submitting work while s2 waits. CUDA's legacy default stream can impose implicit ordering with other streams; the explicit event makes the required dependency clear without relying on those rules.

Beyond ordinary blocks. CUDA also supports constrained forms of cooperation across blocks. A cooperative launch, on a supported device, limits the grid to the number of blocks that can reside concurrently for that kernel and launch configuration, enabling grid-wide synchronization. Thread-block clusters, on supporting hardware, group blocks that are scheduled together and can access each other's shared memory (distributed shared memory) with cluster-level synchronization. Both features have launch rules and size limits; neither guarantees simultaneous execution for arbitrary blocks. This unit assumes a discrete GPU with its own memory, reached by copies; Unit 6 covers integrated and coherent arrangements.

Measure a change against a stated hypothesis

  1. Check correctness first, against a reference, including sizes that aren't multiples of the block size.
  2. Record the setup: GPU model, compiler, launch configuration, precision, input shape, whether inputs start on the device.
  3. Warm up to complete one-time initialization and bring the device to its intended operating state. Collect repeated samples and report a representative value and its spread. Keep cold-cache and warm-cache results apart; warm-up can also leave data in caches.
  4. Profile to test a specific hypothesis. A profiler collects counters and timelines that describe execution. If an access pattern appears to waste sectors, inspect requests and bytes at the relevant cache level. If operands appear to hold up issue, inspect eligible warps and stall reasons. For low residency, inspect register and shared-memory allocation. For launch overhead, inspect the CPU/GPU timeline. Profiling may replay kernels, alter cache state and perturb execution, so collect baseline timings separately.
  5. Change one thing, such as layout, tile shape, block size or reuse, and predict which metric should move before you measure. A speedup with an unexpected metric change is still evidence, but of a different explanation.

  5. A kernel has 100% potential occupancy but is slow. Give two distinct hypotheses and the measurements that would tell them apart.
    Show answer

Divergence, barriers, instruction throughput and launch overhead are other candidates. A potential occupancy of 100% describes how many warps can fit, so it cannot distinguish these causes.

Before explaining a speedup, state the work, the byte boundary, the applicable ceiling, the measurement interval and the uncertainty.

Putting it together

Launch N = 70 float additions in two blocks of 64 threads, with every array starting on a 32-byte boundary. Predict the thread indices and active lanes, then count sectors for each load and store instruction.

Work it out, then open

Lanes: 4 warps with 32, 32, 6 and 0 lanes passing the guard. The launch creates 128 threads, of which 70 execute the addition.

Sectors per array: the two full warps touch 4 sectors each; the 6-lane warp touches 1; the empty warp makes no guarded access. This gives 9 sectors per array and a nominal footprint of 27 sectors = 864 bytes across the two loads and the store. The additions use 70 × 12 = 840 useful bytes, or 97.2% of that footprint. The calculation counts the 32-byte sectors touched by the instructions. Actual DRAM traffic also depends on the caches and on how the memory system handles stores.

Scale changes the likely limit. With N = 70, there are only two blocks, so most SMs on a larger GPU receive no work. With a million elements, there are many blocks to schedule, but each addition still does one FLOP for 12 useful bytes. Bandwidth may now limit speed; measurements must confirm it. Shared-memory staging would add work without reusing those inputs. Matrix multiplication gives a reason to stage data because many outputs need the same input values.
