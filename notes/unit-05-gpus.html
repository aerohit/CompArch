Understand GPUs

Unit 4 gave us three ways to overlap work: more cores, more resident hardware contexts, and more data elements per instruction. A GPU uses all three at once, at a scale no CPU attempts. It keeps thousands of logical threads resident, groups them so that one instruction drives many lanes, and pairs them with a memory system built for throughput rather than the latency of one thread. The interesting question isn't whether the hardware is fast. It's how a particular program supplies enough independent, well-organized work to keep that machinery busy.

You'll be able to
Map an array element to its block, thread, warp and lane. Calculate how many warps fit on a processing unit and what limits them. Explain how switching between ready warps hides latency, and what divergence costs. Count the memory sectors and bank conflicts an access pattern causes. Trace a tiled matrix multiply through both of its barriers. Bound a kernel's speed with the Roofline model and design a measurement that tests the bound.
Carries over
SIMD lanes, masks and tails (Lesson 19), hardware contexts that stay resident (Lesson 18), caches and lines (Lesson 10), synchronization and publication (Lesson 17).
A note on models
Every explorer is an explicit teaching model with its assumptions stated: an SM with invented capacities, a scheduler with one issue slot, 8-lane groups and 8 memory banks for legibility, a synthetic 10 TFLOP/s device. None of them describes a shipping GPU. Where real hardware differs, the text says so.
A GPU is fast when the program gives it many independent threads, grouped so neighbours take the same path and touch neighbouring addresses, doing enough arithmetic per byte. Each lesson below takes one of those conditions apart.

Lesson 20

From an array loop to SIMT

LimitationA CPU vector instruction handles several elements, depending on the vector width and element size. Millions of independent outputs still need a long sequence of instructions, and one core can only hide so much memory latency.
New mechanismSIMT, single instruction, multiple threads. The programmer writes one element's work as a thread; the hardware groups threads to share instruction issue.
New statePer-thread registers and indices, per-block shared memory, per-warp scheduling state, all held resident on a processing unit (an SM).
CostStorage for many contexts, lanes wasted by tails and divergent branches, and data that must be moved to where the threads run.

One thread per element

Take the simplest parallel loop there is: for (i = 0; i < N; i++) c[i] = a[i] + b[i];. No output depends on any other, so all N additions could happen in any order. On a CPU we'd split the loop across cores and vectorize each core's chunk (Lesson 19). A GPU programming model takes a different view: write the work for one element, and launch one logical thread per element. In CUDA:

__global__ void add_arrays(const float* a, const float* b, float* c, size_t n) {
  size_t i = size_t(blockIdx.x) * blockDim.x + threadIdx.x;
  if (i < n) c[i] = a[i] + b[i];
}
// launch (a, b, c are valid device pointers): unsigned threads = 64;
// if (n > 0) { size_t blocks = (n + threads - 1) / threads; // round up
// add_arrays<<<blocks, threads>>>(a, b, c, n); } // blocks must fit the device's grid limit

Every thread runs the same function, but each computes a different index from its position in the launch: which block it's in (blockIdx.x), how big blocks are (blockDim.x), and where it sits in its block (threadIdx.x). All indices start at 0. The launch rounds up to whole blocks, so there may be more threads than elements. The guard if (i < n) stops the extra ones touching memory that isn't theirs.

SIMT (single instruction, multiple threads) names this arrangement. The programmer thinks in threads, each with its own index and private values. The hardware groups threads to share instruction issue, and the arithmetic usually runs on SIMD-style lanes underneath. SIMT and SIMD aren't rival technologies: SIMT describes the programming and scheduling view, SIMD the execution resources.

A GPU thread is not a core. Launching a million threads doesn't mean a million run at once, or that there are a million of anything in hardware. Threads are logical units of work. They wait until a processing unit has room for them, and the unit keeps many of them resident and picks ready instructions from among them over time.

These are correspondences for reading diagrams, not interchangeable specifications. A CUDA warp is always 32 threads, but AMD's wavefront width and compute-unit organization vary by architecture, so don't translate NVIDIA numbers by swapping labels. A block runs entirely on one SM, and several blocks can share an SM if resources permit. A grid can be far larger than what fits on the GPU at once. Crucially, launch order is not execution order: a block must never wait for another ordinary block to make progress, because that block may not even be resident yet.

Try it: map elements to blocks, warps and lanes

Follow one value through the machine

Thread i computes its index, loads a[i] and b[i], adds them in a private register, and stores c[i]. Its neighbours in the warp run the same instructions on their own values: register r1 in lane 5 and r1 in lane 6 are different storage. A warp instruction describes the group's operation, but the hardware may carry it out over several cycles or on specialized units. "32 threads per warp" says nothing about how many physical ALUs execute a given instruction, or how long it takes.

The host CPU enqueues the launch and can carry on without waiting, so reading c back on the host needs an explicit completion step. What the GPU buys you is amortized instruction control across many lanes and enough parallel work to keep them busy. What it costs is context storage, data movement, inactive lanes and coordination. A long chain of dependent operations, such as following a linked list, doesn't become parallel just because it runs on a GPU.

PredictUse the explorer to check.
  1. N = 70 with 64 threads per block: how many blocks, launched threads and warps? How many lanes of block 1's first warp pass the guard?
    Show answer

    2 blocks, 128 threads, 4 warps (two 32-thread warps per block). Block 1 starts at global index 64, so only indices 64–69 pass i < 70: 6 lanes of its first warp. Its second warp has no useful lanes. Those 58 surplus threads exist; they just skip the guarded work.

  2. With 48 threads per block, thread 17 of block 2 has which global index, warp and lane? Why can't a partial warp borrow threads from the next block?
    Show answer

    Global index 2 × 48 + 17 = 113. Warp ⌊17 / 32⌋ = 0, lane 17 mod 32 = 17. Warps are formed within a block, and a block has its own shared memory and its own synchronization scope. Mixing blocks in one warp would break both. The next block starts its own warp numbering.

  3. Does launching 1,000 blocks mean 1,000 are resident at once, or that block 0 runs first?
    Show answer

    Neither. Only as many blocks as fit are resident; the rest wait. The scheduler promises no order by block number. A correct kernel works under any permitted schedule, and one where resident blocks wait for a not-yet-scheduled block can deadlock.

  4. Distinguish a thread's register value, a block's shared-memory value and an element of a global array.
    Show answer

    A register value belongs to one thread, even though all threads' registers live in one physical register file. Shared memory belongs to a block and lets its threads cooperate. A global array element has an address any block can reach. Being reachable doesn't make communication safe: races still need ordering.

  5. Why doesn't a 32-thread warp imply 32 physical ALUs per instruction, or a one-cycle latency?
    Show answer

    Warp width is a logical grouping. How many physical lanes execute an instruction, over how many cycles, with what latency, depends on the instruction and the implementation. The width alone gives you none of those timing facts.

Map an element to its block, thread, warp and lane, without confusing any of them with an SM or with a physical arithmetic unit.

Lesson 21

Capacity, readiness, and useful issue

LimitationA single warp waiting on memory leaves the SM idle for hundreds of cycles, and a branch that splits a warp leaves lanes idle.
New mechanismKeep many warps resident and issue from whichever is ready. Execute divergent paths under an active mask.
New statePer-warp readiness (scoreboards), active masks and reconvergence information, and per-block resource allocations.
CostRegisters and shared memory limit how many warps fit. Masked lanes do no useful work.

Resident, eligible, issued

Three words that are easy to blur, and shouldn't be:

  • A resident warp has been admitted to an SM and holds the resources it needs to stay there.
  • An eligible warp can issue its next instruction now: its operands are ready, the execution unit it needs is free, and no synchronization is holding it back.
  • An issued warp is the one actually selected in a given cycle.

A warp can be resident for hundreds of cycles without being eligible, typically while it waits for a load. Occupancy is the number of resident warps relative to the SM's maximum. It measures capacity in use, not useful work: an SM full of warps that are all waiting does nothing.

Try it: what fits on a teaching SM

Our invented SM can hold at most 8 warps, 256 threads, 4 blocks, 8,192 registers (32-bit) and 16 KiB of shared memory. A block has T threads, each needing R registers, and the block needs S KiB of shared memory. Every limit gives a maximum number of blocks, and the smallest one wins:

warps_per_block = ⌈T / 32⌉
blocks = min(4, ⌊256 / T⌋, ⌊8 / warps_per_block⌋, ⌊8192 / (T × R)⌋, ⌊16 / S⌋)
occupancy = blocks × warps_per_block / 8
if S = 0 the block uses no shared memory: drop the ⌊16 / S⌋ term

This is the potential occupancy the resource limits allow. The achieved occupancy measured on a real run can be lower, for example when the grid has too few blocks to fill every SM, or near the end as blocks finish and nothing replaces them.

With T = 64, R = 32 and S = 4, four blocks fit: 8 warps, 100%. Double R to 64 and the register file only holds two blocks: 50%. Keep R = 32 but double S to 8 KiB and shared memory also allows only two blocks: 50%. Same occupancy, different limiting resource, and therefore a different fix.

Occupancy is a means, not the goal. Forcing the compiler to use fewer registers can raise occupancy but cause spills: values that no longer fit in registers are stored to thread-private memory and reloaded, adding instructions and memory traffic. Smaller tiles can raise occupancy while increasing repeated loads. The objective is the shortest time to a correct result, not the highest occupancy percentage.

Try it: hide latency by picking another ready warp

A toy scheduler: one instruction issue per cycle. Every warp runs LD → ADD → STORE. A load issued in cycle c delivers its value at the start of cycle c + L. The ADD's result is ready the next cycle. Each cycle the scheduler issues from the lowest-numbered eligible warp. No bandwidth limits, no fetch delays.

Four warps complete four units of work in 12 cycles, so 1/3 unit per cycle. One warp completes one unit in 6 cycles: 1/6 per cycle. Aggregate throughput doubled in this example. Warp 0 still finishes at cycle 6, exactly as when it ran alone, but later warps wait their turn and finish later (warp 3 at cycle 12): throughput rose while some individual warps took longer. The number of warps needed grows with the latency: try L = 16. Real schedulers have several issue slots, pipelines with different latencies, and finite memory queues and bandwidth. Independent instructions within a warp help too. And no amount of ready warps can make a saturated memory channel deliver more bytes.

Try it: divergence wastes lanes

When lanes of one warp take different branches, each lane must still get its own result. The hardware runs the paths one after the other under an active mask: lanes not on the current path are switched off, as in Lesson 19. (For short branches the compiler may use predicated instructions instead; the lane accounting is similar.) Our model has 8 lanes for legibility, not CUDA's 32. Each lane starts with value lane + 1. The true path does +10, ×2 (2 instructions); the false path does −1, ×3, +5 (3 instructions). A path with no active lanes is skipped.

A branch that is uniform within each warp incurs no mixed-path serialization penalty in this model, even if different warps go different ways: each warp simply runs its one path. (The branch instructions themselves, and paths of different lengths, still take time.) So sorting or grouping data so that neighbours decide alike can help, though the regrouping has its own cost and can worsen memory access. Measure the whole change.

Don't treat a warp as implicitly synchronized. Diagrams with one shared program counter are a simplification. Since Volta, NVIDIA GPUs schedule threads within a warp independently, so threads of one warp must still use the documented synchronization primitives to communicate.
PredictCheck each with an explorer.
  1. On the teaching SM, what is the potential occupancy for T = 64, R = 64, S = 4? What limits it? What about R = 32, S = 8?
    Show answer

    Each block is 2 warps and needs 64 × 64 = 4,096 registers. The register file allows ⌊8192 / 4096⌋ = 2 blocks: 4 warps, 50%, limited by registers. With R = 32 and S = 8 KiB, shared memory allows ⌊16 / 8⌋ = 2 blocks: again 50%, now limited by shared memory.

  2. Why might cutting a kernel's register count raise occupancy and still make it slower?
    Show answer

    Values that no longer fit spill to thread-private memory, adding loads, stores, latency and traffic. More resident warps can't make up for that if the extra memory work dominates. Check the compiler's spill report, then time it.

  3. In the scheduler model (L = 4), when can a load issued in cycle 2 first feed its ADD? How many cycles and filled slots for two warps?
    Show answer

    Its value is ready at the start of cycle 6. But in cycle 6 the lowest-numbered rule picks warp 0's STORE, so warp 1's ADD issues in cycle 7. Two warps take 8 cycles and fill 6 of 8 slots (75%). Ready isn't the same as issued.

  4. In the divergence model, one lane takes the true path and seven the false path. What is the utilization?
    Show answer

    Both paths run: 2 + 3 = 5 group instructions, 8 × 5 = 40 positions. Useful: 1 × 2 + 7 × 3 = 23. Utilization 57.5%, different from the 4/4 split's 50% because the paths have different lengths.

  5. A profiler shows high occupancy, but few eligible warps and little issue activity. Is adding more arithmetic units a demonstrated fix?
    Show answer

    No. The warps are resident but not ready. Find out what they wait for: dependent loads, arithmetic latency, barriers or busy pipelines. Look at memory traffic and bandwidth, stall reasons and issue activity together. If operands aren't arriving, more ALUs just wait too.

Answer four questions separately for any kernel: does the work fit (residency), is it ready (eligibility), does it issue, and how many of the participating lanes do useful work?

Lesson 22

Make the memory traffic explicit

LimitationThirty-two threads issue 32 addresses with one load instruction. If those addresses are scattered, the memory system moves far more bytes than the program uses.
New mechanismCoalescing merges a warp's requests into as few fixed-size transfers as cover them. Shared memory is split into banks that serve lanes in parallel.
New stateSeveral memory spaces with different owners: registers, shared memory, local memory, global memory, plus hardware caches.
CostLayout now matters as much as instruction count: a bad stride can multiply the bytes moved, and a bad shared-memory pattern serializes lanes.

Name the storage and who can see it

StorageWho owns itWhat to remember
RegistersOne threadFastest working state, but it uses up the capacity that limits residency
Shared memory (AMD: LDS)One blockOn-chip scratchpad the program manages explicitly; needs coordination
Local memory (CUDA)One threadHolds spills and addressable private arrays; lives in device memory, possibly cached
Global memoryThe whole gridLarge address space; each access travels through the cache hierarchy
Hardware cachesManaged by hardwareReuse can cut traffic further out; not something the program owns

Two traps in the names. CUDA local means thread-private, not on-chip: a local-memory access can be as slow as a global one. And touching a global address doesn't prove a DRAM access: a cache hit is served earlier in the hierarchy.

Try it: count sectors for one load instruction

Model: one warp of 32 active lanes, each loading one aligned 4-byte word. Lane l asks for byte address base + 4 × stride × l. The memory system moves data in aligned 32-byte sectors, so the cost of the instruction is the number of distinct sectors it touches. Everything starts outside the cache we're modelling.

StrideBaseUseful bytesSectorsSector bytesUseful fraction
10 B1284128100%
14 B128516080%
20 B128825650%
80 B128321,02412.5%

The 32-byte sector model matches NVIDIA's description for recent GPUs, but it's a counting exercise for one instruction, not a DRAM command count. Neighbouring warps may use the sectors this one over-fetched, requests can merge further down the hierarchy, and caches change the byte count at each boundary. Layout is where this bites in real code: an array of structures spaces the same field of consecutive objects far apart (a large stride), while a structure of arrays makes it contiguous. Which is right depends on which fields are used together.

Try it: shared-memory banks

On-chip memory has limited ports too. Shared memory is divided into banks, each of which can serve one distinct word per round. Our model has 8 banks of 4-byte words and 8 requesting lanes: word w lives in bank w mod 8. If several lanes read the same word, it's broadcast in one round. Different words in the same bank are a bank conflict, served in successive rounds.

Traffic is a consequence of code and allocation. A spill adds loads and stores of private values. An uncoalesced access multiplies bytes at one boundary; a cache hit removes traffic at another; staging data in shared memory adds on-chip instructions but can cut repeated global loads. For vector addition, though, the useful bytes stay 12 per element (two 4-byte reads and one 4-byte write) however wide the machine. Once bandwidth limits the speed, more arithmetic units change nothing unless the algorithm reuses data. Lesson 24 turns that into a bound.

PredictCheck with the explorers.
  1. Stride 2, aligned base: how many sectors and sector bytes? What fraction is useful?
    Show answer

    Addresses 0, 8, 16, …, 248: each 32-byte sector holds four requested words. 8 sectors, 256 bytes for 128 useful: 50%.

  2. Stride 1: what changes when the base moves by 4 bytes? Why might a whole array's DRAM traffic differ from summing these per-warp counts?
    Show answer

    Bytes 4 to 131 now touch a fifth sector: 160 bytes, 80%. But the next warp needs that fifth sector anyway, so across the array the over-fetch is largely reused, and caches and request merging change the count further. Per-instruction sectors are one boundary's accounting, not the DRAM total.

  3. In the 8-bank model, compare rounds for word addresses l, 8l, 9l and the constant 0. Which uses broadcast?
    Show answer

    l: 1 round. 8l: 8 rounds, eight different words all in bank 0. 9l: 1 round, since 9l mod 8 = l. 0: 1 round, by broadcast of the one word.

  4. Why can a CUDA local-memory load cost far more than a register read? Does being thread-private put it on chip?
    Show answer

    Local memory is an address space with private visibility, backed by device memory and reached through the caches. Private doesn't mean on-chip. A register is read directly by the instruction, with no memory access at all.

  5. Two access patterns touch exactly the same sectors in a different lane order. Must their sector counts differ? Could the kernels still perform differently?
    Show answer

    The counts are equal: a permutation of lanes doesn't change the set of sectors. Whole kernels can still differ through cache reuse across instructions, dependencies, divergence, instruction count or bank conflicts. Equal traffic is one equal property, not equal speed.

For an access pattern, compute the useful bytes, the sector bytes and the bank-conflict rounds under stated rules, then say where each conclusion stops being valid.

Lesson 23

Reuse a tile, then coordinate its lifetime

LimitationIn matrix multiplication every input value is used many times. Loading it from global memory for every use wastes bandwidth.
New mechanismTiling: a block loads a small piece of each input into shared memory once, and all its threads reuse it from there.
New stateShared tiles owned by the block, plus a private running sum in each thread's registers.
CostShared memory and registers (so less residency), and two barriers per tile to keep threads from racing each other.

Why matrix multiplication rewards reuse

In C = A × B, each output is a dot product: C[r, c] = Σk A[r, k] × B[k, c]. Outputs in the same row of C all use the same row of A; outputs in the same column all use the same column of B. Loading both operands from global memory for every multiply ignores that. A tile is a sub-region processed together: one block computes a T × T tile of C. It loads a T × T piece of A and a T × T piece of B into shared memory, uses them for the next T values of k, then replaces them with the next pieces. Each thread keeps its running sum in a private register throughout.

Try it: a complete 2 × 2 tile, step by step

A is 2 × 4 and B is 4 × 2, so C is 2 × 2. One block of four threads owns the four outputs; thread (r, c) computes C[r, c]. The reduction dimension has length 4, handled in two tiles of width 2. In each load phase, thread (r, c) loads one entry of each shared tile, so four threads load eight words, and every thread then uses values its neighbours loaded.

After the first tile (k = 0, 1) the partial sums are [[7, 10], [23, 34]]. Thread (0, 0), for instance, computes 1 × 1 + 2 × 3 = 7. The second tile (k = 2, 3) adds 3 × 5 + 4 × 7 = 43 to it, giving 50. The final result is [[50, 60], [114, 140]]. Don't confuse C's two dimensions (2 × 2) with the reduction length (4).

Why two barriers?

__syncthreads() is a barrier: no thread in the block passes it until every thread has reached it. The tiled loop needs two per tile, and they protect against two different hazards:

Here is the kernel for square n × n row-major matrices, launched with ⌈n / T⌉ × ⌈n / T⌉ blocks of T × T threads:

template<int T> __global__ void tiled_square(const float* A, const float* B, float* C, size_t n) {
  __shared__ float As[T][T], Bs[T][T];
  int x = threadIdx.x, y = threadIdx.y;
  size_t row = size_t(blockIdx.y) * T + y, col = size_t(blockIdx.x) * T + x;
  float sum = 0.0f;// private running sum
  for (size_t base = 0; base < n; base += T) {
    As[y][x] = (row < n && base + x < n) ? A[row * n + base + x] : 0.0f;
    Bs[y][x] = (base + y < n && col < n) ? B[(base + y) * n + col] : 0.0f;
    __syncthreads();// barrier 1: tile is loaded
    for (int k = 0; k < T; ++k) sum += As[y][k] * Bs[k][x];
    __syncthreads();// barrier 2: everyone finished reading
  }
  if (row < n && col < n) C[row * n + col] = sum;// guard only the store
}

Notice how edges are handled. At an edge tile some positions fall outside the matrices. Those threads load a zero into the tile (zero adds nothing to a sum) instead of skipping the load, and every thread still reaches both barriers. Only the final store is guarded. Returning early instead would be wrong for two distinct reasons. First, that thread would never write its entries of the shared tile, so other threads would read whatever was left there. Second, CUDA allows __syncthreads() in conditional code only if every thread of the block takes the same path; when some threads skip a barrier that others reach, the kernel can hang or silently misbehave. The kernel is a teaching sketch: production libraries give each thread several outputs, use other tile shapes, and overlap loading with computing.

Count the reuse

For one T × T output tile with reduction length K (a multiple of T), the tiled algorithm requests 2TK input words from global memory and writes T² outputs, while doing T²K multiply-adds, which is 2T²K FLOPs (counting multiply and add separately). With 4-byte words:

requested bytes = 4 × (2TK + T²)
FLOPs = 2T²K
intensity = TK / (4K + 2T) FLOPs per byte

In our example (T = 2, K = 4): 16 input words plus 4 outputs = 80 bytes for 32 FLOPs. Loading both operands for every multiply-add separately would request 32 input words plus 4 outputs = 144 bytes for the same 32 FLOPs. Intensity grows with T: bigger tiles mean more reuse per byte. These are bytes the algorithm requests, not proven DRAM traffic: caches might rescue some of the naive version's repeats, and staging adds its own instructions and barriers. So 144 / 80 is not a guaranteed speedup.

A double-buffered version keeps two tiles, loading the next while computing on the current one. It then has to track, for each buffer, when it is filled and when it is safe to overwrite: the same two hazards, now overlapping in time. Asynchronous copies have their own completion operations; issuing a copy doesn't mean its data has arrived.

PredictTrace it by hand, then check with the stepper.
  1. What is the partial C after reduction indices 0 and 1, and the final C after 2 and 3?
    Show answer

    Partial [[7, 10], [23, 34]]; final [[50, 60], [114, 140]]. For example C[1, 1] = 5×2 + 6×4 + 7×6 + 8×8 = 10 + 24 + 42 + 64 = 140.

  2. Name one failure allowed by removing the barrier after loading, and a different one allowed by removing the barrier before the next load.
    Show answer

    Without barrier 1, a thread can read a tile entry before its neighbour has written it. Without barrier 2, a fast thread can overwrite an entry with the next tile's value while a slow thread is still reading the current one. The first orders writing before reading; the second orders reading before rewriting.

  3. Count input words, output words and FLOPs for the example. Why isn't 144 / 80 a measured speedup?
    Show answer

    Tiled: 16 input + 4 output words = 80 bytes, 32 FLOPs. Independent operand loads: 32 + 4 words = 144 bytes, a ratio of 1.8. It counts requested bytes. Caches can cut the naive version's physical traffic, and tiling adds instructions and barriers, so the time ratio must be measured.

  4. At an edge tile, why fill invalid positions with zero and still reach both barriers? What happens to invalid stores?
    Show answer

    Zero contributes nothing to a sum, and loading it avoids an invalid memory access. Every thread must still reach both barriers so the others can safely read and reuse the tile. Threads whose output lies outside C simply skip the final store.

  5. A larger tile cuts repeated global loads but doubles shared memory and lowers residency. Is it necessarily faster?
    Show answer

    No. It raises reuse, but also uses more registers and shared memory, admits fewer blocks, may change bank behaviour and leaves more idle work at the edges. Measure traffic, resource use, eligible warps, barrier stalls and total time.

For every shared tile entry and every private sum, say who writes it, who reads it, and how long it must live. Explain each barrier with a concrete producer/consumer race.

Lesson 24

Predict a limit, then measure the right interval

LimitationDiagrams explain mechanisms but don't say how fast a kernel can go, or whether a change helped.
New mechanismThe Roofline bound: performance is capped by compute or by bandwidth × arithmetic intensity, whichever is lower.
New stateA measurement plan: the work, the byte boundary, the ceilings, and the time interval being measured.
CostBounds are only as good as their assumptions, and timings mean nothing without a stated interval.

From diagrams to a performance hypothesis

Let W be the floating-point operations a kernel performs, and Q the bytes it moves across a named memory boundary (say, DRAM). Its arithmetic intensity is I = W / Q, in FLOPs per byte. Let P be the device's compute ceiling for that exact kind of arithmetic, and β its bandwidth at that same boundary. Then:

performance ≤ min(P, β × I)
execution time ≥ max(W / P, Q / β)
ridge point = P / β// intensity where the two meet

It's a maximum, not a sum, because computing and moving data can overlap. That's a best case: dependencies, issue limits, cache behaviour, synchronization and too little parallel work can all push a kernel below the roof. And the ceilings must match the kernel. A matrix-unit peak is the wrong ceiling for a scalar addition kernel, and a point below the sloped roof doesn't by itself prove DRAM bandwidth is saturated.

Try it: a Roofline you can check by hand

A made-up device: P = 10 TFLOP/s for our arithmetic and β = 200 GB/s (decimal units: 1 GB = 10⁹ bytes). These are teaching numbers, not any real product.

For one million float additions: W = 10⁶ FLOPs, Q = 12 × 10⁶ bytes (assuming those 12 MB cross the DRAM boundary exactly once), so I = 1/12 FLOP per byte. Compute time is 0.1 μs; memory time is 60 μs. The ceiling is about 16.7 GFLOP/s, over 500 times below the 10 TFLOP/s peak. Doubling compute changes nothing for this kernel; doubling bandwidth halves its bound. The ridge sits at 10 × 10¹² / 200 × 10⁹ = 50 FLOPs per byte. Moving a kernel toward it takes genuinely useful reuse (like tiling), not padding the FLOP count with pointless arithmetic.

Fixed costs matter more as the useful work shrinks. With H = 10 μs the vector add takes 10 + 60 = 70 μs. A hypothetical algorithm that halved its traffic would take 10 + 30 = 40 μs: a 1.75× speedup, not 2×, because the overhead didn't shrink.

Decide what "time" means

A kernel launch returns to the CPU as soon as the work is queued, usually long before the GPU finishes. Timing just the launch call measures submission, not execution. Choose the interval deliberately:

QuestionInclude in the interval
How long does this kernel run on data already on the device?The device work in one stream, bracketed by events; no allocation or copies
How long from input to usable output?Copies, launches, computation, dependencies and completion
How much work can a pipeline sustain?A steady-state batch with its intended overlap, divided by the work completed
cudaEvent_t start, stop;
cudaEventCreate(&start);  cudaEventCreate(&stop);   // timing enabled by default
cudaEventRecord(start, stream);
add_arrays<<<blocks, threads, 0, stream>>>(a, b, c, n);
cudaEventRecord(stop, stream);
cudaEventSynchronize(stop);                        // wait until the GPU passes 'stop'
float ms = 0;
cudaEventElapsedTime(&ms, start, stop);            // device time between the events
// check the return codes and cudaGetLastError() in real code

To time device work: record a start event in a stream, launch the work, record a stop event in the same stream, wait for the stop event, then ask for the elapsed time. Other work running on the GPU at the same time can stretch the interval. Repeating the kernel R times and dividing reduces timer-resolution error, but repeated runs on the same data find it in cache (report it as warm, not cold), and the batch can include gaps if the CPU enqueues slowly.

A disciplined experiment

  1. Check correctness first, against a reference, including sizes that aren't multiples of the block size.
  2. Record the setup: GPU model, compiler, launch configuration, precision, input shape, whether inputs start on the device.
  3. Warm up, collect repeated samples, and report a representative value and its spread. Keep cold-cache and warm-cache results apart.
  4. Profile to test a specific hypothesis. Too many sectors? Inspect requests and bytes at the relevant cache level. Waiting for operands? Inspect eligible warps and stall reasons. Low residency? Inspect register and shared-memory allocation. Launch overhead? Look at a CPU/GPU timeline. Profilers replay and perturb work, so take baseline timings separately.
  5. Change one thing, such as layout, tile shape, block size or reuse, and predict which metric should move before you measure. A speedup with an unexpected metric change is still evidence, but of a different explanation.
PredictCheck with the Roofline explorer.
  1. For 10⁶ float additions on the 10 TFLOP/s, 200 GB/s device: intensity, compute time, memory time and ceiling?
    Show answer

    I = 10⁶ / 12×10⁶ = 1/12 FLOP/B. W/P = 0.1 μs, Q/β = 60 μs. The bound is the larger, 60 μs, a ceiling of β × I ≈ 16.7 GFLOP/s. It assumes Q is the true byte count at that boundary, and no fixed overhead.

  2. What is the ridge intensity? Which bound changes if only compute capacity doubles?
    Show answer

    Ridge = 50 FLOPs/B. Doubling P halves the compute time (0.1 → 0.05 μs) and moves the ridge to 100, but the 60 μs memory time still decides the vector add. Doubling bandwidth would halve it to 30 μs.

  3. With H = 10 μs, compare the 12 MB vector add with a hypothetical 6 MB version. Why is the speedup less than 2?
    Show answer

    10 + max(0.1, 60) = 70 μs versus 10 + max(0.1, 30) = 40 μs: 1.75×. The fixed 10 μs didn't shrink. (Vector addition can't actually drop required bytes; the 6 MB case is hypothetical.)

  4. Why isn't timing the CPU's launch call enough? Describe an event-based measurement and one limitation of timing repeated work.
    Show answer

    The launch returns once the work is queued. Record start and stop events in the same stream around the work, wait for the stop event, then read the elapsed time, after a warm-up and with errors checked. Repeating the work makes later runs warm-cache, and the batch may include host-side enqueue gaps.

  5. A kernel has 100% potential occupancy but is slow. Give two distinct hypotheses and the measurements that would tell them apart.
    Show answer

    (1) Memory bandwidth is saturated: measure bytes at the relevant boundary and the achieved byte rate against β. (2) Dependency latency leaves few eligible warps: measure eligible warps, issue activity and stall reasons, possibly with bandwidth well below its ceiling. Divergence, barriers, instruction throughput and launch overhead are other candidates. Occupancy alone chooses none of them.

Before explaining a speedup, state the work, the byte boundary, the applicable ceiling, the measurement interval and the uncertainty.

Unit 5 · Summary

Putting it together

Launch N = 70 float additions in two blocks of 64 threads, with every array starting on a 32-byte boundary. Predict the thread indices and active lanes, then count sectors for each load and store instruction.

Work it out, then open

Lanes: 4 warps with 32, 32, 6 and 0 lanes passing the guard. Counting the launch as 128 additions would overstate the work.

Sectors per array: the two full warps touch 4 sectors each; the 6-lane warp touches 1; the empty warp makes no guarded access. That's 9 sectors per array, and 27 sectors = 864 bytes for the two loads and the store, against 70 × 12 = 840 useful bytes: 97.2% useful under this accounting. That's a nominal 32-byte-sector footprint, a coalescing count, not proof that 864 bytes crossed DRAM (stores in particular may be handled differently).

At a million elements the same kernel offers plenty of work to hide latency, but its intensity is 1/12 FLOP/B, so bandwidth is the likely limit. Only measurement can confirm what's actually busy. Staging the inputs through shared memory would add work with no benefit, because each element is used once. Matrix multiplication is different: its reuse is what makes tiling pay.
