Stanford CS149 · Lecture 7 companion

GPU architecture and CUDA programming

GPUs were built to draw triangles for video games. Because drawing means running the same small function on millions of pixels, they became enormously parallel, and then programmable enough to run almost anything data-parallel. This lecture traces that history, teaches CUDA, the language NVIDIA introduced in 2007 for programming GPUs directly, and then looks inside an NVIDIA V100 to see how CUDA's abstractions are actually implemented.

You'll be able to
Explain why GPUs have many SIMD, multithreaded cores. Write and read CUDA kernels: grids, blocks, threads, blockIdx/threadIdx, the host/device split and the three device memory spaces. Explain why shared memory and __syncthreads make the convolution example faster. Describe a V100 SM, warps and SIMT execution. Trace how a GPU's work scheduler assigns thread blocks to cores under resource limits, and explain why some CUDA programs can deadlock.
Background
Lecture 2 (SIMD, multithreading, the V100 SM) and Lecture 3 (SPMD, ISPC gangs and tasks). Unit 5 of these notes (Understand GPUs) covers occupancy, coalescing and tiling in more depth.

Keep asking the course's question: what does the abstraction promise, and what does this implementation happen to do? CUDA promises that thread blocks can run in any order, and that threads within a block run concurrently. NVIDIA GPUs implement that with a hardware block scheduler, and with warps of 32 threads executed in SIMD fashion. Warps aren't part of the CUDA programming model, but they decide performance.
Part 1 · From graphics to compute

How a graphics chip became a parallel computer

Why rendering produced this kind of hardware, and how people first bent it to other uses.

Section 1

What GPUs were originally designed to do: 3D rendering

A renderer takes a description of a scene (3D surfaces as triangle meshes, surface materials, lights, a camera) and produces an image. Real-time graphics represents every surface as a mesh of triangles, each defined by three vertices (points in space). The whole workload fits in two sentences:

  • Given a triangle, determine where it lies on screen, given the position of the virtual camera.
  • For every output pixel the triangle covers, compute the color of the surface at that pixel.

The second step is where the work is. What a surface looks like at a point depends on its material and the lights, and the world is full of different materials. So the color computation is a small program, a shader, written in a shading language such as GLSL:

uniform sampler2D myTexture;   // read-only, same for every pixel
uniform float3 lightDir;
varying vec3 norm;              // different at every pixel:
varying vec2 uv;                // think of these as the function's inputs

void myShader() {
  vec3 kd = texture2D(myTexture, uv);          // look up the surface color
  kd *= clamp(dot(lightDir, norm), 0.0, 1.0);  // darken by light angle
  return vec4(kd, 1.0);                        // this pixel's RGBA color
}

The syntax doesn't matter. What matters is that a shader is a pure function, invoked independently on a stream of inputs: once per pixel covered by a triangle, millions of times per frame, 60 or more frames per second. Pixels covered by several surfaces keep the output of the surface closest to the camera.

Section 2

From a graphics hack to a compute interface

Around 2001–2003, people noticed that GPUs were very fast processors for running the same computation in parallel on large collections of data. That's data parallelism, the model of the exotic supercomputers of the 1990s. And every year GPUs got faster, because more transistors meant more parallelism.

The hack

But the only way to run code on a GPU was to draw something. So, to run a function on every element of a 512 × 512 array:

  1. Set the output image size to 512 × 512, the array size.
  2. Draw two triangles that exactly cover the screen.
  3. Write your function as the fragment shader. The GPU runs it once per pixel, so once per array element.

Stanford's Brook language (2004) hid the hack behind a data-parallel abstraction: you wrote a kernel function over streams, and the Brook compiler translated it into graphics commands (like draw-triangles) and shader programs the GPUs of the day could run.

kernel void scale(float amount, float a<>, out float b<>) {
  b = amount * a;
}
float input_stream<1000>;    // stream declarations
float output_stream<1000>;
scale(scale_amount, input_stream, output_stream);  // map the kernel over the streams

Compute mode

Compare how programs reached the hardware before and after 2007:

It's the same way code runs on a CPU, where the OS loads a program, prepares an execution context and lets the processor fetch instructions, just with thousands of instances at once. CUDA, introduced with Tesla in 2007, is a C-like language for this compute interface. It's deliberately low-level: its abstractions closely match the capabilities and performance characteristics of GPUs (a small "abstraction distance").

Part 2 · CUDA abstractions

What a CUDA program means

Threads, blocks and grids; host and device; three kinds of device memory; and synchronization.

Section 3

A hierarchy of concurrent threads

Keep four questions in mind through this part. Is CUDA a data-parallel programming model? Is it a shared-address-space model, or message passing? And can you draw analogies to ISPC instances and tasks, or to pthreads?

"CUDA thread" doesn't mean what "thread" usually means. A CUDA thread presents a similar abstraction to a pthread: a logical thread of control with its own local variables. Its implementation is completely different, as Part 3 shows. When this page says "thread" in a CUDA context, it means a CUDA thread.

A CUDA program launches a grid of thread blocks, each containing many threads. IDs can be up to three-dimensional, which is convenient for problems that are naturally 2D or 3D. The lecture's example adds two 12 × 6 matrices:

// host code (runs on the CPU)
const int Nx = 12, Ny = 6;
dim3 threadsPerBlock(4, 3);
dim3 numBlocks(Nx/threadsPerBlock.x,
               Ny/threadsPerBlock.y);
// launches 72 CUDA threads:
// 6 thread blocks of 12 threads each
matrixAdd<<<numBlocks, threadsPerBlock>>>(A, B, C);
// device code (runs on the GPU)
__global__ void matrixAdd(float A[Ny][Nx],
                          float B[Ny][Nx],
                          float C[Ny][Nx]) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  int j = blockIdx.y * blockDim.y + threadIdx.y;
  C[j][i] = A[j][i] + B[j][i];
}

The launch is a bulk launch of many threads, and the call returns when all of them have terminated. Each thread computes its overall position in the grid from its position in its block (threadIdx) and its block's position in the grid (blockIdx). __global__ marks a kernel: device code that the host can launch.

The separation into host and device code is done statically by the programmer. Functions marked __device__ (like a helper doubleValue(x)) run on the GPU and can be called from kernels; ordinary functions run on the CPU.

Section 4

The CUDA memory model

The host and the device have distinct address spaces. Host code allocates device memory with cudaMalloc and moves data with cudaMemcpy:

float* A = new float[N];              // host memory
for (int i = 0; i < N; i++) A[i] = (float)i;
float* deviceA;
cudaMalloc(&deviceA, sizeof(float) * N);    // device memory
cudaMemcpy(deviceA, A, sizeof(float) * N, cudaMemcpyHostToDevice);
// deviceA[i] = ... here would be invalid: deviceA is not a pointer
// into the host's address space

Section 5

Example: 1D convolution, and why shared memory helps

Each output is the average of three neighbouring inputs: output[i] = (input[i] + input[i+1] + input[i+2]) / 3. Version 1 assigns one thread per output, and every thread reads its three inputs from global memory:

#define THREADS_PER_BLK 128
__global__ void convolve(int N, float* input, float* output) {
  int index = blockIdx.x * blockDim.x + threadIdx.x;  // thread-local
  float result = 0.0f;                                 // thread-local
  for (int i = 0; i < 3; i++)
    result += input[index + i];
  output[index] = result / 3.f;
}
// host: N = 1024 * 1024 outputs, input has N + 2 elements
convolve<<<N/THREADS_PER_BLK, THREADS_PER_BLK>>>(N, devInput, devOutput);

Neighbouring threads read overlapping inputs: input[5] is read by the threads computing outputs 3, 4 and 5. Version 2 has each block load its support region (the 130 inputs its 128 outputs need) into shared memory once, cooperatively, then compute from there:

__global__ void convolve(int N, float* input, float* output) {
  __shared__ float support[THREADS_PER_BLK+2];     // one copy per block
  int index = blockIdx.x * blockDim.x + threadIdx.x;
  support[threadIdx.x] = input[index];                 // each thread loads one
  if (threadIdx.x < 2)                                  // two threads load the extra 2
    support[THREADS_PER_BLK + threadIdx.x] = input[index + THREADS_PER_BLK];
  __syncthreads();                                    // barrier: all loads done
  float result = 0.0f;
  for (int i = 0; i < 3; i++)
    result += support[threadIdx.x + i];
  output[index] = result / 3.f;
}

The __syncthreads() call is essential. Without it, a thread could read support[threadIdx.x + 2] before the thread responsible for that element had written it. It's a barrier: no thread in the block continues until all have reached it. Unit 5, Lesson 23 of these notes explores the same pattern for matrix multiplication, including why tiled code sometimes needs a second barrier.

CUDA's synchronization constructs

  • __syncthreads(): a barrier across all threads in one block.
  • Atomic operations, such as float atomicAdd(float* addr, float amount), on both global and shared memory addresses.
  • Host/device synchronization: an implicit barrier across all threads when a kernel returns.

ExecutionBulk launch of many threads, in a two-level hierarchy: threads grouped into thread blocks

Part 3 · Implementation

How a GPU actually runs CUDA

Compilation, the thread-block scheduler, the V100 SM, warps, and what the scheduling rules allow and forbid.

Section 6

A million threads? What the implementation must decide

The convolution launch creates over 1 million CUDA threads in over 8,000 blocks. Will running it create a million copies of local variables and a million stacks? Eight thousand copies of the shared support array? Compare what pthread_create() or std::thread does: allocate a stack for the thread, and a control block so the OS can schedule it. Doing that a million times would be absurd.

Two more facts shape the answer. GPUs come in different sizes, from a mid-range part with 6 cores to a high-end one with dozens, and the same CUDA program should run on all of them unmodified. And none of the programs so far mention a number of cores. A CUDA launch is closer in spirit to a forall loop in a data-parallel model than to creating threads.

What the compiler records

A compiled CUDA device binary contains the program's instructions and its resource requirements. For the convolution kernel: 128 threads per block, B bytes of local data per thread, and 130 floats (520 bytes) of shared memory per block.

This is another instance of a design pattern that appears throughout the course: a fixed pool of workers pulling tasks from a queue. The problem is decomposed into sub-problems (blocks), and the workers (cores) take them one at a time. ISPC's task launch works the same way (one pthread per hardware thread, kept alive for the program), and so does a web server's thread pool (the number of threads depends on the number of cores, not the number of pending requests).

Section 7

Inside the NVIDIA V100: sub-cores, warps and SIMT

A V100 core is called a streaming multiprocessor (SM), and each SM is split into four sub-cores. One sub-core holds:

Warps

A group of 32 threads in a thread block is called a warp. Threads 0–31 of a block form one warp, 32–63 the next, and so on, so a 256-thread block becomes 8 warps. Each sub-core can hold up to 16 warps and interleave their execution, just like the hardware multithreading of Lecture 2.

Threads in a warp execute in SIMD fashion whenever they share the same next instruction. NVIDIA calls this SIMT (single instruction, multiple threads). If the 32 threads don't share an instruction (they took different branches), the warp executes the paths in turn with some threads masked off, and performance suffers: the divergence of Lecture 2.

A warp is like an ISPC gang, with one important difference. An ISPC gang is compiled into SIMD instructions ahead of time. CUDA code is compiled as scalar code for one thread; the GPU hardware dynamically checks whether the 32 threads of a warp share an instruction, and if so executes them together. Also, the warp isn't part of the CUDA programming model at all. It's an implementation detail of NVIDIA GPUs, though one that decides performance.

Section 8

Running a kernel: the block scheduler, step by step

The lecture traces the convolution kernel on a deliberately small, fictitious GPU with two cores. Each core can hold execution contexts for 384 threads (12 warps) and has 1.5 KB (1,536 bytes) of shared memory. Each block needs 128 threads' contexts and 520 bytes of shared memory, and N is large enough that the host launches thousands of blocks.

Notice that the program never mentioned cores. The same launch on a GPU with 80 larger cores would simply spread the blocks more widely. That's the payoff of the "blocks may run in any order" assumption: the hardware does the dynamic load balancing.

Section 9

What the scheduling rules allow, and what they forbid

Why must a whole block be resident at once?

Imagine a block of 256 threads on a core with room for only 128 threads' worth of contexts. Why not run threads 0–127 to completion, then 128–255? Because threads in a block may depend on each other. The simplest example is __syncthreads(): threads 0–127 would wait at the barrier forever for threads 128–255, which can't start until the first group finishes. So CUDA's semantics are that threads in a block run concurrently: when a block starts, all its threads exist and have register state allocated, and any runnable thread will eventually run. That imposes a scheduling constraint on the implementation.

Blocks: any order, but not necessarily independent

CUDA never promised that blocks are independent, only that the system may schedule them in any order. A histogram kernel where every thread does atomicAdd(&counts[A[i]], 1) on shared counters in global memory is perfectly valid: the atomics provide mutual exclusion, and the result is the same in any order. But what about this?

// thread block 0
// do stuff here
atomicAdd(&myFlag, 1);
// thread block 1
while (atomicAdd(&myFlag, 0) == 0)
  { }            // wait for block 0
// do stuff here

Persistent threads: taking scheduling into your own hands

An advanced style, "persistent threads", launches exactly as many blocks as the GPU can run at once (for the V100 and 128-thread blocks, 80 SMs × (32 × 64 ÷ 128) = 1,280), and has each block loop, grabbing chunks of work from a global counter with atomicInc until the work runs out. This circumvents the hardware block scheduler, and lets the programmer think of all CUDA threads as running at once. The catch: it assumes things about the implementation that CUDA never promised (that every launched block really runs concurrently), and the code is tied to a particular GPU's size.

So, is CUDA data-parallel, shared-address-space, or message passing? A little of each: the grid of blocks is in the spirit of the data-parallel model; inside a block it's SPMD with a shared address space; and host–device transfers look like message passing. Whenever you meet a parallel programming system, ask which semantics apply where.

Two last points. This lecture covered CUDA on the GPU's programmable cores, where a kernel launch is mapped onto cores by the hardware work scheduler. The GPU also still has its graphics pipeline interface, and much of its non-programmable hardware exists to accelerate that pipeline; it's more or less turned off when CUDA runs. And the SM's tensor cores, which supply hundreds of TFLOP/s for deep learning, come later in the course (Unit 6 of these notes introduces matrix units).

Review

Terms to know, and questions to test yourself

Shader
A pure function run once per vertex or pixel in the graphics pipeline.
GPGPU
General-purpose computation on GPUs, originally by disguising it as rendering.
Compute mode
The non-graphics interface: allocate and copy buffers, then launch N instances of a kernel.
Kernel
A __global__ function the host launches over a grid of threads.
Grid, block, thread
The launch's hierarchy: a grid of thread blocks, each containing threads, with 1–3D IDs.
Host, device
The CPU and its memory; the GPU and its memory, in a separate address space.
Shared memory
Fast on-chip memory shared by the threads of one block.
__syncthreads()
A barrier across all threads of a block.
SM, sub-core
A V100 core, split into four sub-cores that each issue one warp instruction per clock.
Warp, SIMT
32 threads the hardware executes together in SIMD fashion when they share an instruction.
Block scheduler
GPU hardware that assigns thread blocks to SMs as resources allow.
Persistent threads
Launching just enough blocks to fill the GPU and distributing work in software.
Test yourselfThe lecture's questions, plus a few more.
  1. matrixAdd launches <<<(3,2), (4,3)>>>. How many threads, and which (i, j) does thread (1, 2) of block (2, 1) compute?
    Show answer

    6 blocks × 12 threads = 72. i = 2 × 4 + 1 = 9, j = 1 × 3 + 2 = 5: element C[5][9].

  2. In convolution version 2, how many global loads does one block issue, versus version 1?
    Show answer

    130 (128 + 2 support elements) versus 3 × 128 = 384. The other reads hit shared memory.

  3. Why does the v2 kernel fit only two blocks per core on the fictitious GPU, even though the core has contexts for three?
    Show answer

    Shared memory: 3 × 520 = 1,560 bytes > 1,536 (1.5 KB). The threads would fit (3 × 128 = 384), but a block can't start without its shared allocation.

  4. How long does one warp's fp64 instruction occupy the fp64 units of a V100 sub-core?
    Show answer

    32 threads on 8 fp64 units: 4 clocks. (fp32: 32 on 16 units, 2 clocks.)

  5. Why can't a GPU run a 256-thread block as two halves, one after the other?
    Show answer

    Threads in a block may synchronize with each other, for example with __syncthreads(). The first half would wait at the barrier for the second half, which could never start: deadlock. So CUDA guarantees all threads of a block are resident together.

  6. Is the histogram-with-atomics kernel correct? Is the flag-spinning kernel?
    Show answer

    The histogram is correct: atomics give mutual exclusion and the result doesn't depend on block order. The flag program is incorrect: it works only if block 0 runs before, or at the same time as, block 1, and CUDA allows any order.
