Stanford CS149 · Lecture 3 companion

Latency, bandwidth, and the SPMD abstraction

Lecture 2 filled a chip with parallel hardware: many cores, wide SIMD units, many hardware threads. This lecture asks two questions about using it. First, can memory keep all that hardware fed? Often it can't, and that makes bandwidth, not arithmetic, the resource that decides performance. Second, how do we write programs for it? Using ISPC as the example, it separates a programming model's abstraction (what the program means) from its implementation (how the machine actually runs it).

You'll be able to
Distinguish latency from throughput with everyday and hardware examples. Explain why a throughput processor can be bandwidth-bound, and calculate how badly. Explain why, once enough requests are in flight, memory latency stops mattering and bandwidth takes over. Describe ISPC's SPMD model: gangs, program instances, programIndex, programCount, uniform, foreach. Trace how interleaved and blocked assignments map to SIMD instructions, and spot ISPC programs whose output is undefined.
Background
Lecture 2 (multi-core, SIMD, multithreading) and Lecture 1 (memory, latency, caches). Units 3–5 of these notes go deeper into pipelining, SIMD and GPUs.
Source
Follows the structure and examples of Stanford CS149 Parallel Computing, Fall 2023, Lecture 3, "Multi-Core Architecture Part II + Parallel Programming Abstractions" (Kayvon Fatahalian and Kunle Olukotun). The explanations, diagrams and explorers here are original study material, not a copy of the slides.
Two lessons. Bandwidth is the critical resource: modern processors can compute far faster than memory can deliver operands, so fast programs are the ones that fetch data rarely. And an abstraction is not its implementation: ISPC lets you think of many independent program instances, but the compiler runs them as the lanes of SIMD instructions on one core. Knowing both lets you predict what the machine will actually do.
Part 1 · Latency and bandwidth

Can memory keep up?

A thought experiment, a highway, some laundry, and a timeline that shows exactly when memory becomes the limit.

Section 1

A thought experiment: multiply two long vectors

Take two vectors A and B, each with millions of elements, and compute their element-wise product C = A × B. For each element i: load A[i], load B[i], multiply, store C[i]. There's no dependency between elements at all. It's the most parallel program imaginable. Is it a good fit for a throughput processor like a GPU?

Hold that thought. To answer it we need two precise ideas, latency and bandwidth, and a way to see how they interact. We'll come back to the numbers in Section 5.

Section 2

Latency versus throughput, in everyday terms

Latency is how long one task takes from start to finish. Throughput is how many tasks finish per unit of time. They're related but independent: you can often raise throughput without touching latency, and that's exactly what parallel hardware does.

The highway

The lecture's analogy: driving from San Francisco to Stanford, about 50 km. At 100 km/h the trip takes half an hour; that's the latency. Suppose only one car may be on the road at a time, and the next car leaves when the previous one arrives. Then the throughput is 2 cars per hour. How could we move more cars?

Only "drive faster" improved latency, and it's the hardest to keep doing (think of clock frequency in Lecture 1). The other two raise throughput by having more work in flight at once: more lanes (parallel hardware), or more cars per lane (pipelining).

Try it: laundry

Doing one load of laundry: wash (45 min), dry (60 min), fold (15 min). The latency of one load is 2 hours. With many loads, three strategies:

The slowest stage sets a pipeline's throughput. The lecture's last analogy makes that explicit: connect a pipe that carries 100 liters/second to one that carries 50 liters/second, and the system carries 50 liters/second. The narrowest part of a path is its bottleneck, and making any other part wider changes nothing.

Section 3

The same two ideas for memory

  • Memory latency (from Lecture 1): the time for the memory system to deliver one requested item, for example 100 clock cycles or 100 ns.
  • Memory bandwidth: the rate at which the memory system can deliver data to a processor, for example 20 GB/s.

The relationship is Little's law, which holds for any steady system: items in flight = throughput × latency. To get 8 items per second through a pipe where each item takes 2 seconds, 16 must be in flight at any moment. Memory systems reach high bandwidth exactly this way: many requests outstanding at once, each still taking the full latency.

"One operation per clock" is a throughput statement. Students often ask how a processor can finish a multiply in one clock. It doesn't. In a four-stage instruction pipeline (fetch, decode and register read, execute, write back), each instruction takes 4 cycles, but one finishes every cycle. Real pipelines vary by instruction and can be around 20 stages deep. Unit 3 of these notes builds one.
Section 4

When memory bandwidth limits the whole processor

Now apply the ideas to a real core. Many threads each repeat a sequence of three dependent instructions:

1X = load 64 bytes
2Y = add X + Xneeds X
3Z = add X + Yneeds Y

The core, as in the lecture: it executes one math operation per clock; it can issue a load in parallel with math; and memory delivers 8 bytes per clock, so one 64-byte load takes 8 clocks of transfer. There are plenty of hardware threads to hide latency, and the memory system allows a limited number of outstanding loads.

With the lecture's numbers, each load brings 64 bytes and feeds 2 math instructions, and memory delivers 64 bytes every 8 clocks. So in steady state the core can do at most 2 math instructions per 8 clocks: 25% utilization, however many threads it has. The memory channel, meanwhile, is busy 100% of the time. It can't transfer data any faster.

That's the lecture's key claim: in steady state, the core's utilization depends only on the rate of instructions and the rate of memory, not on memory latency or the number of outstanding requests, as long as there are enough requests in flight. Try it with the lecture's preset: raise the latency from 4 to 16 clocks and nothing changes. The explorer also shows the fine print. Keep going past 16 clocks and utilization drops, because 3 loads in flight are no longer enough to keep the channel busy (at 40 clocks it's about 12%). The "too few loads in flight" preset shows the extreme: with 1 load outstanding and a long latency, the channel sits idle between requests. Little's law says you can't reach full bandwidth without enough requests in flight: here, loads in flight × 64 bytes must cover (latency + transfer time) × bandwidth.

LimitFormula (per clock)What raises it
Compute1 math instructionMore ALUs, cores, SIMD lanes
Bandwidthmath per load × bandwidth ÷ bytes per loadMore bandwidth, or more math per byte loaded
Latency (Little's law)loads in flight × math per load ÷ (latency + transfer time)More outstanding requests (more threads, more independent loads)

The achieved rate is the smallest of the three. Adding ALUs helps only when compute is the smallest; adding threads only when latency is.

Section 5

Back to the thought experiment: bandwidth is the critical resource

Element-wise multiply performs three memory operations (two 4-byte loads and one 4-byte store: 12 bytes) for every one multiply. That ratio decides everything.

So the GPU runs this program at under 1% of its arithmetic capability, and the CPU at about 3%. Yet the GPU is still much faster, because its memory system delivers about 12 times more bytes per second, and bandwidth is all that matters here. This computation is bandwidth-limited: if processors request data faster than memory can supply it, the memory system can't keep up.

Modern GPUs push bandwidth up with high-bandwidth memory (HBM) stacked right next to the processor, such as the V100's 900 GB/s HBM2. But compute has grown even faster. Overcoming bandwidth limits is often the most important challenge in programming throughput-oriented systems. Performant parallel programs therefore:

  • Fetch data from memory less often. Reuse data the same thread loaded earlier (temporal locality), and share data between threads (cooperation) instead of each loading its own copy.
  • Prefer recomputing to storing and reloading. Arithmetic is close to free; memory traffic isn't.
  • Above all, access memory infrequently relative to the computation done.
PredictAnswer before opening.
  1. In the explorer's lecture preset, a thread does 2 adds per 64-byte load, and memory delivers 8 bytes per clock. What's the best possible ALU utilization? Does doubling the number of threads change it?
    Show answer

    64 bytes take 8 clocks and feed 2 adds: at most 2 useful clocks in 8, 25%. More threads don't help: they only add more requests to a memory channel that is already busy 100% of the time.

  2. How much bandwidth would the V100 need to keep all 5,120 ALUs busy on element-wise multiply?
    Show answer

    5,120 multiplies × 1.6 × 10⁹ clocks/s × 12 bytes ≈ 98 TB/s, more than 100 times the 900 GB/s it has. Efficiency is about 0.9%.

  3. Why does raising the latency from 4 to 16 clocks not change the lecture preset's utilization, while the "too few loads in flight" preset is very sensitive to latency?
    Show answer

    With enough loads outstanding, the memory channel is always busy, so only its transfer rate matters. With too few in flight (one load in that preset, or three loads once the latency exceeds 16 clocks), the channel waits out part of the latency between transfers. By Little's law the achieved bandwidth is (loads in flight × 64 bytes) ÷ (latency + transfer time), which falls as latency rises.

Part 2 · Abstraction vs. implementation

What a program means, and how it runs

Using ISPC to separate a programming model's semantics from the machinery that carries them out.

Section 6

The theme: abstraction versus implementation

The second half of the lecture has one theme, and the course returns to it constantly. Confusing the semantics of an abstraction with the details of its implementation is the most common source of confusion in parallel programming.

Abstraction (semantics)What do the operations of a programming model mean? Given a program and those meanings, what answer will it compute?
Implementation (scheduling)How will that answer actually be computed on a parallel machine? In what order do operations run? Which thread, execution unit or vector lane does each one?
Your goalGiven a program and knowledge of how its programming model is implemented, trace in your head what each part of the parallel computer is doing at each step.
The trapAssuming a guarantee the abstraction never made, because the implementation you happen to know gives it. Programs built on that assumption break on the next implementation.

The example is ISPC, the Intel SPMD Program Compiler, which you use in the first programming assignment. (Matt Pharr's blog series "The Story of ISPC" is a good read on why it was designed this way.)

Section 7

SPMD in ISPC: gangs of program instances

Recall Lecture 2's example: compute sin(x) with a Taylor series, sin(x) = x − x³/3! + x⁵/5! − …, for every element of an array. The C++ version is an ordinary loop over i. Here it is in ISPC:

export void ispc_sinx(uniform int N, uniform int terms,
                      uniform float* x, uniform float* result)
{
  // assume N % programCount == 0
  for (uniform int i = 0; i < N; i += programCount) {
    int idx = i + programIndex;
    float value = x[idx];
    float numer = x[idx] * x[idx] * x[idx];
    uniform int denom = 6;       // 3!
    uniform int sign = -1;
    for (uniform int j = 1; j <= terms; j++) {
      value += sign * numer / denom;
      numer *= x[idx] * x[idx];
      denom *= (2*j+2) * (2*j+3);
      sign *= -1;
    }
    result[idx] = value;
  }
}

The C++ main calls ispc_sinx(N, terms, x, result) like any function. What that call means is the SPMD (single program, multiple data) abstraction:

  • The call spawns a gang of ISPC program instances. All instances run the same ISPC function concurrently.
  • Each instance has its own copy of local variables (idx, value, numer above).
  • When the function returns, all instances have completed, and sequential C++ execution resumes.
ISPC keywordMeaning
programCountThe number of instances running simultaneously in the gang. The same for every instance (a uniform value).
programIndexThis instance's ID within the gang, 0 to programCount − 1. Different in every instance (a varying value).
uniformA type modifier: every instance has the same value, so one copy suffices. Purely an optimization; it isn't needed for correctness.

In ispc_sinx, the loop counter i is uniform: every instance steps through i = 0, 8, 16, … together. Each computes its own element idx = i + programIndex. So with programCount = 8, instance 0 handles elements 0, 8, 16, …, instance 1 handles 1, 9, 17, … This is an interleaved assignment of array elements to instances.

Section 8

Assigning work to instances: interleaved versus blocked

A second version divides the array into one contiguous block per instance instead:

// assume N % programCount == 0
uniform int count = N / programCount;
int start = programIndex * count;
for (uniform int i = 0; i < count; i++) {
  int idx = start + i;
  float value = x[idx];
  ...                      // same Taylor series as before
}

Both versions compute exactly the same results: the abstraction is satisfied either way. The difference is entirely in the implementation, and it's large. ISPC implements a gang with SIMD instructions: the gang size is the hardware's SIMD width (or a small multiple of it), and each instance is one vector lane. At each step of the loop, one vector instruction performs float value = x[idx] for all eight instances at once. What that instruction must do depends on which eight addresses the instances want.

Blocked is the natural choice for threads, interleaved for SIMD lanes. Across CPU cores, giving each thread a contiguous block is usually best, since each core streams through its own memory. Across the lanes of one SIMD instruction, it's the opposite: the lanes execute together, so you want neighbouring lanes to touch neighbouring addresses. Which is better depends on the implementation, not the abstraction.
Section 9

Raising the level of abstraction: foreach

Writing programIndex arithmetic by hand is error-prone. ISPC's foreach construct lets the programmer declare the parallel iterations instead:

export void ispc_sinx(uniform int N, uniform int terms,
                      uniform float* x, uniform float* result)
{
  foreach (i = 0 ... N) {
    float value = x[i];
    ...                      // same Taylor series, using x[i]
    result[i] = value;
  }
}

foreach says: these are the iterations the whole gang must perform, not each instance. The ISPC implementation takes responsibility for assigning iterations to instances. That assignment could be done in several valid ways, and the explorer above shows four: all iterations on instance 0 (valid but pointless), interleaved, blocked, or dynamic, where instances repeatedly grab the next unclaimed iteration from a shared counter with an atomic increment. (In practice ISPC uses an interleaved-style mapping, because it produces packed vector loads.)

In many simple cases, foreach lets you write a program almost as if it were sequential: "independently, for each element of the input array, do this." The next section shows where that "almost" matters.

Section 10

Reading ISPC programs carefully: semantics traps

Which of these programs is well defined?

// absolute_repeat
foreach (i = 0 ... N) {
  if (x[i] < 0)
    y[2*i] = -x[i];
  else
    y[2*i] = x[i];
  y[2*i+1] = y[2*i];
}
// shift_negative
foreach (i = 0 ... N) {
  if (i >= 1 && x[i] < 0)
    y[i-1] = x[i];
  else
    y[i] = x[i];
}

absolute_repeat computes the absolute value of each element of x and writes it twice into y. Each iteration writes only its own two slots, 2i and 2i + 1, so the result is the same in every order: well defined. shift_negative is different. Iteration i may write y[i − 1], which iteration i − 1 also writes. Which write lands last depends on the order the implementation happens to run the iterations in, so the output is undefined.

Computing a sum: the uniform/varying distinction

Summing an array exposes the uniform-versus-varying distinction. Two plausible attempts both fail to compile:

// sum_incorrect_1
float sum = 0.0f;
foreach (i = 0 ... N)
  sum += x[i];
return sum;   // returns uniform float

sum is varying: every instance has its own copy. The function must return one uniform float to C++. Which copy? It's a compile-time type error.

// sum_incorrect_2
uniform float sum = 0.0f;
foreach (i = 0 ... N)
  sum += x[i];
return sum;

sum is uniform: one copy for the whole gang. But x[i] differs per instance, so the gang would be trying to add eight different values into one variable in one step. Also a compile-time type error.

The correct version gives each instance a private partial sum, with no communication during the loop, then combines them with a cross-instance operation from ISPC's standard library:

export uniform float sum_array(uniform int N, uniform float* x) {
  float partial = 0.0f;                   // one per instance
  foreach (i = 0 ... N)
    partial += x[i];
  return reduce_add(partial);             // one uniform total
}

reduce_add is one of several cross-instance operations, the parts of ISPC where instances deliberately communicate:

OperationWhat it does
uniform int64 reduce_add(int32 x)Sum of x over all instances in the gang
uniform int32 reduce_min(int32 a)Minimum of a over all instances
int32 broadcast(int32 value, uniform int index)Every instance receives the value held by instance index
int32 rotate(int32 value, uniform int offset)Pass values around the gang by offset positions, wrapping at the ends
shift(value, offset)Like rotate, but values shifted past the end of the gang become 0

Try it: a tree reduction across the gang

These operations can express real cooperation. The lecture's example computes the product of eight numbers in lg 8 = 3 steps instead of 7: in each step, some instances multiply their value by a partner's value obtained with shift, and the number of useful partial products halves.

Section 11

How the gang is implemented, and what it doesn't give you

  • SPMD programming model: the programmer "thinks" that calling an ISPC function spawns programCount logical instruction streams, each with a different programIndex. The program is written in terms of that abstraction.
  • SIMD implementation: the ISPC compiler emits vector instructions that carry out the gang's logic, handling divergent ifs by masking lanes.
  • The semantics can be subtle, because uniform values and cross-instance operations let implementation details peek through the abstraction.

One consequence surprises people: everything shown so far uses only one core. On the four-core machines used in the course, the gang runs on one of them. To use all cores, ISPC has a second abstraction, the task, which launches work onto multiple threads and therefore multiple cores. (The first assignment explores it.) So the full picture is tasks across cores, gangs across SIMD lanes within each core: the same "multi-core × SIMD" combination as Lecture 2.

Section 12

How high should the abstraction go?

ISPC is deliberately a low-level language. By exposing programIndex and programCount, it lets the programmer control exactly which work and which data each instance handles. The price: you can write programs with undefined output (like shift_negative), or programs that are correct only for one particular programCount.

What if the language didn't expose instances at all?

  • Only foreach: remove programIndex and programCount. Now there's little reason to think about instances. Everything outside a foreach must be uniform values and uniform logic, because with no instance IDs there is nothing that could make one instance's value differ from another's.
  • No indexing at all: invoke a function once per element of a collection, like y = map(doWork, x). The programmer writes no loops and does no indexing. NumPy and PyTorch programmers work this way: Z = X + Y adds whole arrays, and the library decides how to parallelize.

Each step up hides more of the implementation, which makes it easier to write correct programs and harder to control performance. Later lectures return to these data-parallel models.

The lecture's summary: programming models provide a way to think about the organization of parallel programs. They provide abstractions that permit multiple valid implementations. Keep asking, for the rest of the course: which parts of what I'm seeing are the abstraction's promises, and which are just how this implementation happens to work?
Review

Terms to know, and questions to test yourself

Latency
Time for one operation or request to complete.
Throughput
Operations completed per unit time.
Memory bandwidth
The rate at which memory can supply data, in bytes per second.
Little's law
Items in flight = throughput × latency.
Bandwidth-bound
Execution limited by the rate memory can supply data, with compute units stalled.
Bottleneck
The stage with the lowest throughput, which sets the throughput of the whole path.
Abstraction vs implementation
What a programming model's operations mean, versus how a particular system carries them out.
SPMD
Single program, multiple data: one function run by many logical instances on different data.
Gang, program instance
The group of instances an ISPC call spawns; each instance is one logical stream with its own locals.
programCount / programIndex
The gang's size (uniform) and an instance's ID (varying).
uniform / varying
One value shared by the gang / a separate value per instance.
foreach
Declares iterations for the whole gang, leaving the assignment to the implementation.
Packed load vs gather
A vector load of contiguous addresses vs of arbitrary addresses; gathers cost more.
Cross-instance operation
A standard-library call that combines or moves values between instances: reduce_add, broadcast, rotate, shift.
ISPC task
ISPC's abstraction for multi-core execution; gangs alone use one core's SIMD.
Test yourselfThe lecture's questions, plus a few more.
  1. A car trip takes 30 minutes with one car on the road at a time. Adding three lanes raises throughput from 2 to 8 cars/hour. What happened to latency?
    Show answer

    Nothing: still 30 minutes. More lanes add parallelism, which raises throughput without changing any one car's trip.

  2. Laundry: wash 45 min, dry 60 min, fold 15 min. Pipelined, what's the throughput, and why isn't it one load every 40 minutes?
    Show answer

    1 load per hour. The dryer is the slowest stage, so a load can leave the pipeline only every 60 minutes. The pipeline's throughput is set by its bottleneck, not the average stage.

  3. Convince yourself: in steady state, with enough loads in flight, why is core utilization independent of memory latency?
    Show answer

    Once enough requests are outstanding, the memory channel is always transferring, so the rate at which data arrives is its bandwidth. Math can proceed only as fast as its operands arrive. Latency just shifts when each item arrives, not how many arrive per second.

  4. Why does the blocked sinx version need a gather while the interleaved version uses a packed load?
    Show answer

    At each step the eight instances access x[start + i] with starts that are N/8 apart, so the eight addresses are far apart. In the interleaved version they access x[i + 0 … i + 7], eight contiguous floats that one vector load can fetch.

  5. Why is shift_negative's output undefined, while absolute_repeat's isn't?
    Show answer

    In shift_negative, two different iterations can write the same element (y[i − 1] is written by iterations i − 1 and i), and foreach promises no order. In absolute_repeat every iteration writes only its own elements, 2i and 2i + 1.

  6. With only foreach (no programIndex or programCount), why must everything outside a foreach be uniform?
    Show answer

    Outside a foreach there's no per-instance information at all: no instance ID and no per-iteration variable. Every instance runs identical code on identical inputs, so every value is necessarily the same across the gang.
