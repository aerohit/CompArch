A modern multi-core processor

Why does a laptop chip have several cores, each with 8-wide vector units and two hardware threads, and why does a GPU take the same ideas to an extreme? This lecture answers with three ideas for executing more work in parallel, and one for coping with slow memory. It looks at them from a software engineer's point of view: what each one demands from your program.

You'll be able to
Explain multi-core, SIMD and hardware multithreading. Say what kind of parallelism each exploits and what the program must provide for each to pay off. Calculate the peak throughput of a real chip, and work out how many threads are needed to hide a given memory latency.
Background
Helpful: Units 1–4 of these notes (especially caches, superscalar execution, SMT and SIMD). This page recaps everything it needs, so it can be read on its own.
Source
Follows the structure and examples of Stanford CS149 Parallel Computing, Fall 2023, Lecture 2, "A Modern Multi-Core Processor" (Kayvon Fatahalian and Kunle Olukotun). The explanations, diagrams and explorers here are original study material, not a copy of the slides.
The whole lecture fits in one sentence. To run fast on a modern chip, a program must supply enough independent work for every core and execution unit, work that follows the same instruction sequence in groups (so SIMD lanes stay busy), and even more work than that so the chip can switch to something else while waiting on memory.
Part 0 · Review

What a processor does, and what memory is

A quick rebuild of the basic model, because every later idea modifies one of its three boxes.

Section 1

A program is a list of instructions

A compiler turns a C function into a sequence of machine instructions: loads, multiplies, adds, compares, jumps, stores. The processor's only job is to execute that sequence. The simplest useful processor has three parts:

Each clock, the processor fetches the instruction at the PC, decodes it, the ALU executes it, and the result goes back into a register (or memory). Then the PC advances. Unit 1 builds exactly this machine from gates.

Section 2

Instruction-level parallelism and superscalar cores

Instructions in a program are written in order, but many don't actually depend on each other. Draw an arrow from each instruction to every instruction that uses its result, and you get a dependency graph. Instructions with no path between them could run at the same time. That's instruction-level parallelism (ILP).

A superscalar processor exploits ILP automatically. It has several fetch/decode units and several ALUs, and out-of-order control logic that finds independent instructions in the stream and issues them together. It still has one execution context: this is parallelism within one instruction stream.

"Respecting program order" doesn't mean executing instructions strictly in sequence. It means the results must be exactly what sequential execution would produce: dependencies honoured, and visible state updated as if one instruction ran at a time. Unit 3's reorder buffer is how cores guarantee this.

The catch: real programs typically contain only a few independent instructions at a time. Beyond about 4-wide, extra issue width buys little for ordinary code. That's the wall the rest of this lecture climbs over.

Section 3

Memory: an array of bytes, implemented with caches

From the program's point of view, memory is one big array of bytes. Each byte has an address (its index), and a load or store names an address. That's the abstraction. The implementation is much more complicated, but it never changes what a program computes, only how fast.

A cache is small on-chip storage that keeps copies of recently used parts of memory. If an address is in the cache, loading it is fast. If not, the data must come from DRAM, which is slow. Caches work in fixed-size chunks called cache lines: a miss brings in the whole line containing the address.

Try it: a two-line cache

A 16-byte array and a tiny cache with 4-byte lines, fully associative, with LRU (least recently used) replacement. Choose 2 or 4 lines of capacity and step through an access sequence.

The hierarchy, and why it matters

Real machines stack several caches: small, fast L1 next to each core, larger and slower L2, a big shared L3, and then DRAM. The instruction "load address X into R0" may be served by any of them. Here's what that costs on an Intel Kaby Lake desktop CPU at 4 GHz:

PredictAnswer before opening.
  1. In "read array twice" with a 2-line cache, why is the second read of address 0x0 a miss? What about 0x4?
    Show answer

    After the first pass the cache holds only the last two lines, 0x8 and 0xC. Line 0x0 was evicted (least recently used) when 0x8 arrived, so 0x0 misses. Loading it evicts 0x8, the LRU line, and then line 0x4 is also gone (it was evicted when 0xC came in), so 0x4 misses too. Every line misses on the second pass: a textbook capacity problem.

  2. Would the answer change with 4 lines?
    Show answer

    Yes. 4 lines × 4 bytes = 16 bytes, the whole array. After 4 cold misses in the first pass, every access of the second pass hits.

Part 1 · Parallel execution

Three ways to do more work per clock

Superscalar execution ran out of steam. Here's what chip designers did with their transistors instead.

Section 4

The running example: sin(x) for a whole array

The lecture uses one program throughout. Compute sin(x) for each of N numbers using the Taylor series:

sin(x) = x − x³/3! + x⁵/5! − x⁷/7! + …

for i = 0 … N−1:one iteration per array element
  value = x[i]; numer = x[i]³; denom = 6; sign = −1first term x, then set up x³/3!
  for j = 1 … terms:add one more term each time
    value += sign · numer / denom
    numer ·= x[i]²; denom ·= (2j+2)(2j+3); sign = −signnext power, next factorial, flip sign
  y[i] = valuewrite the result

Compiled for a simple core, the program is one instruction stream that processes one element at a time. A superscalar core would find almost no ILP in the inner loop, so it would mostly run one instruction per clock. Let's see what else we could build.

Section 5 · Idea #1

Use the transistors for more cores

ProblemExtra transistors spent on one core (bigger caches, smarter out-of-order logic, better branch prediction) made single streams only slightly faster.
IdeaBuild several simpler cores instead, each with its own fetch/decode, ALU and execution context.
Program must provideMultiple instruction streams (threads), with enough independent work to give every core some.
CostEach simple core is slower on its own. Unparallelized code gets slower, not faster.

Before about 2005, most of a CPU's transistors went into making a single instruction stream run faster: out-of-order logic, a sophisticated branch predictor, a memory prefetcher, a large data cache. Only a small fraction was the ALU doing the actual arithmetic.

But the sin(x) program as written expresses no parallelism. It compiles to one instruction stream, which runs on one core. On the dual-core chip it now runs 25% slower than on the fancy single core. The hardware can't split a sequential program for you: someone has to state that the iterations are independent.

Expressing the parallelism

Option 1: threads. Create a second software thread and give it half the array. The main thread computes the other half, then waits for the helper to finish ("join"). With a C++ threading library that's a few lines. The programmer decides the split explicitly.

Option 2: declare independence. The lecture uses an imaginary forall loop, "for all i from 0 to N, in any order", which tells the compiler that iterations don't depend on each other. The compiler or runtime is then free to split them across cores itself. Real equivalents include OpenMP's parallel for, and the data-parallel languages you'll meet later in CS149 (ISPC, CUDA).

Section 6 · Idea #2

Share one instruction stream across many ALUs

ProblemEvery core pays for fetch/decode and control logic, but only has one ALU doing math.
IdeaSIMD (single instruction, multiple data): one fetch/decode drives many ALUs, all running the same instruction on different data.
Program must provideMany data elements that need the same instruction sequence: coherent execution.
CostWide registers and datapaths. When elements need different instructions, lanes sit idle (divergence).

Notice what sin(x) does. Every iteration runs the same instructions on a different x[i]. So why fetch and decode each instruction eight times for eight elements? Fetch it once, and send it to eight ALUs that each hold a different element. The cost of managing the instruction stream is amortized across all the ALUs.

To use this from C, the programmer (or compiler) rewrites the loop to step through the array 8 elements at a time. Each scalar operation becomes a vector operation, using "intrinsics": C functions that map directly to vector instructions. For Intel's AVX, _mm256_mul_ps(a, b) multiplies two vectors of eight floats. The Taylor series logic is unchanged. Every variable (value, numer, denom) simply becomes a vector of eight, and the loop's i advances by 8.

Instruction setVector width32-bit floats per instruction
Intel/AMD AVX2256 bits8
Intel AVX-512512 bits16
Arm NEON128 bits4

Where do the vector instructions come from? Three ways: the programmer writes intrinsics; the language's semantics allow them (like forall, which promises independence); or an auto-vectorizing compiler proves on its own that loop iterations are independent. In all three cases the SIMD instructions are chosen at compile time, and you can see them in the binary. That's called explicit SIMD.

Section 7

Conditional execution: what if lanes disagree?

SIMD assumes all lanes run the same instruction. But loop bodies contain if statements, and different elements can take different sides. Say each lane holds one t = x[i]:

if (t > 0):"then" side: 3 instructions
  t = t · t; t = t + 1; t = √t
else:"else" side: 2 instructions
  t = −t; t = t · 2
y[i] = teveryone meets again here

One instruction stream can't go both ways at once. So the hardware runs both sides, one after the other, with a mask. During the "then" side, lanes whose condition is false are switched off: they compute nothing, or their results are discarded. During the "else" side, it's the other way round. After the if, all lanes are active again. Click lanes to flip their condition:

How bad can it get? The worst case has only one of the 8 lanes doing work for most of the time. For example, if (i % 8 == 0) { very long computation } keeps a single lane busy while 7 idle, which is 1/8 of peak. It needs only one if.

Useful vocabulary

  • Coherent execution (instruction-stream coherence): many data elements need the same instruction sequence. It's necessary for SIMD to be efficient, and not necessary for multi-core, since each core has its own fetch/decode and can follow its own path.
  • Divergent execution: the lack of coherence, where lanes need different instructions.

Explicit versus implicit SIMD

On CPUs, the compiler emits vector instructions (explicit SIMD). Most GPUs work differently. The compiler emits a scalar program, the hardware always runs many copies of it together, and the hardware puts the copies executing the same instruction onto the SIMD lanes. This is implicit SIMD, also called SIMT (single instruction, multiple threads). GPU SIMD widths are typically 8–32, so badly divergent GPU code can run at 1/32 of peak.

Worked example: peak throughput of a real CPU

An Intel Core i7-7700K (Kaby Lake, 2017) has 4 cores. Each core has three 8-wide SIMD floating-point units (AVX2), and the chip runs at about 4.2 GHz:

4 cores × 3 units × 8 lanes × 4.2 × 10⁹ clocks/s ≈ 400 billion operations per second (≈ 400 GFLOP/s)

A single scalar stream on one core, doing one operation per clock, reaches 4.2 GFLOP/s, about 1% of that. The other 99% is available only to programs that are both multi-threaded and vectorized.

An NVIDIA V100 GPU (2017) has 80 SMs (its "cores"). Each SM has 64 FP32 SIMD lanes, and each lane can do a fused multiply-add (2 floating-point operations) per clock at about 1.53 GHz:

80 × 64 × 2 × 1.53 × 10⁹ ≈ 15.7 TFLOP/s at about 250 W

That's roughly 40× the CPU. The GPU's cores are simpler, and far more of its chip is ALUs. Section 12 looks inside one SM.

Part 2 · Accessing memory

Keeping all those ALUs fed

More ALUs make the memory problem worse, because they all stall together when data isn't there.

Section 9

Stalls, and two ways to shorten or hide them

A processor stalls when it can't run the next instruction because that instruction needs a result that isn't ready. The classic cause is a load that has to go all the way to DRAM: about 250 cycles on the Kaby Lake chip. A core that could have completed hundreds of vector operations does nothing.

Technique 1: caches reduce the length of stalls

When data was used recently, it's probably still in a cache, and a 4-cycle L1 hit replaces a 250-cycle DRAM trip. Caches work well when programs have locality (Section 3). They don't help the first time data is touched, or when the working set is larger than the cache.

Technique 2: prefetching hides stalls

Many CPUs watch the stream of addresses a program loads, spot patterns such as "each load is 64 bytes after the previous one", and fetch data into the cache before it's requested. When the program finally issues the load, it hits.

What if the data wasn't used recently and the next address is unpredictable? For example, x = some_function(); y = A[x];, where nobody can know x until it's computed. Caches and prefetchers can't help. We need a third idea.

Section 10 · Idea #3

Hide stalls by switching to another thread

ProblemLong, unpredictable memory stalls leave the ALUs idle, and caches and prefetchers can't always prevent them.
IdeaKeep several threads' execution contexts on the core. When one stalls, run another.
Program must provideMore independent work than there are ALUs, so there's always a runnable thread.
CostStorage for more contexts, and each thread takes longer to finish. Throughput goes up, per-thread latency goes up too.

Think of doing laundry. You don't stand at the washing machine for 40 minutes. You start a load and go cook dinner, and come back when the machine is done. A multithreaded core does the same with instruction streams. It holds, say, 4 execution contexts (4 hardware threads), each working on different elements. When thread 1 issues a load that misses, the core immediately starts issuing instructions from thread 2. By the time threads 2, 3 and 4 have all stalled, thread 1's data may have arrived.

The throughput trade-off. Look at thread 1: once its data arrives it is runnable, but it has to wait while threads 2–4 use the core. Multithreading makes each individual thread take longer in order to make the whole system finish more work per second. This is the defining choice of throughput-oriented processors like GPUs.

No free lunch: context storage

Every hardware thread needs its registers stored on the chip. That storage is finite, so a design must choose how to divide it: many small contexts (lots of threads, each with few registers, so lots of latency hiding) or a few large contexts (fewer threads, each with a big working set).

Interleaved versus simultaneous

Interleaved (temporal) multithreading: each clock, the core picks one thread and runs its instruction. That's the model in these diagrams. Simultaneous multithreading (SMT): each clock, the core can pick instructions from several threads and run them on different ALUs at once. Intel's Hyper-Threading, with 2 threads per core, is SMT. Either way, the core has the same number of ALUs. Multithreading doesn't add compute. It only helps keep the existing ALUs busy when some threads are waiting.

Section 11

How many threads does it take?

Consider a simple core that runs one scalar instruction per clock from one of its hardware threads. Each thread runs a loop: some arithmetic instructions, then a memory load whose data arrives after a fixed latency. The thread can't continue until it does. How busy is the core?

The rule falls out of the timeline. A thread computes for k cycles and then waits L cycles, so one period is k + L cycles. To fill the whole period, the core needs enough threads that their compute bursts cover it:

threads needed = ⌈(k + L) / k⌉ = ⌈1 + L / k⌉     utilization = min(1, T·k / (k + L))

Takeaway 1: a multithreaded core avoids stalls by running other threads' instructions while one waits. The memory latency itself doesn't change. It just stops costing utilization.

Takeaway 2: the more arithmetic a program does per memory access, the fewer threads it needs to hide the stalls. Latency is hidden by other threads' arithmetic.

    Show answer

    (4 + 20) / 4 = 6 threads. With 3: 3 × 4 / 24 = 50%.

  2. Adding an 8th thread to the 3-instruction / 12-cycle program: does anything get faster?
    Show answer

    Total throughput doesn't change, because the core is already 100% busy with 5 threads. And each thread gets slower, because it waits longer for its turn after its data arrives.

Section 12

All the ideas in one chip

Combine everything: multiple cores, each with SIMD ALUs, each running multiple hardware threads. Here's the lecture's fictitious chip:

A real CPU core: Intel Skylake / Kaby Lake

A GPU core: one NVIDIA V100 SM

GPUs are extreme throughput machines: many simple cores, very wide SIMD, and huge numbers of hardware threads. NVIDIA calls a core a streaming multiprocessor (SM), and a group of 32 threads executing together a warp.

Why so many threads? The V100's memory delivers about 900 GB/s through a 4096-bit HBM interface, with latencies of hundreds of cycles. Section 11's formula says programs with little arithmetic per load need many threads to hide that, so the V100 is built to hold 163,840 of them at once.

Section 15 · Going further

Every combination: what does it take to saturate the chip?

The lecture's closing slides assemble a processor one feature at a time: a second fetch/decode unit, wider execution units, more execution contexts, more cores. Each feature multiplies the chip's peak throughput. None of them multiplies the actual throughput unless the software supplies the matching kind of work. This section enumerates the combinations and states, for each one, exactly what "enough work" means.

The general recipe

For a chip with C cores, T contexts per core, issue width W, SIMD width S, and a workload doing k arithmetic instructions per load with memory latency L, saturation needs all of the following at once:

#RequirementQuantityHardware it feeds
1Independent instruction streams≥ C × Tevery context on every core
2Instructions per clock per coreW from ILP (one thread) or from W threads (SMT)fetch/decode + issue slots
3Instruction mixmatches the unit mix every clockscalar vs vector units
4Coherent data per vector instructionS elements, same control pathSIMD lanes
5Resident threads per core to cover stalls≥ m × (b + L) / b, where b = k / rALUs during memory waits
6Total independent work items≥ C × T × Sthe whole chip

In row 5, r is how many instructions one running thread issues per clock (1, or 2 with ILP on a 2-issue core). b = k / r is how long a thread's burst of arithmetic lasts before it stalls. m is how many threads must be running at once to fill the issue width: 1 normally, 2 on a 2-issue core in SMT mode when each stream has no ILP. For the simple core, this reduces to Section 11's ⌈(k + L)/k⌉.

Worked example: the Kaby Lake i7-7700K. 4 cores, 2 hardware threads each (Hyper-Threading, which is SMT). Each core can issue up to 4 scalar and 3 eight-wide vector instructions per clock.

To saturate its vector units you need: 8 threads (4 × 2), since fewer leaves contexts empty. Each clock, a core needs 3 vector instructions ready, drawn from its 2 threads, so the two streams together need about 3 independent vector instructions per clock: high ILP inside each stream. Every vector instruction needs 8 coherent elements, so at least 4 × 2 × 8 = 64 independent elements in flight, and many more in practice, because 2 threads per core hide very little memory latency. The data must mostly hit in cache. With only 2 contexts, this CPU relies on caches and prefetching, not threads, to cover DRAM latency.

That's why hand-tuned numeric libraries (BLAS, for example) unroll loops heavily, vectorize everything, carefully block data for cache, and run one thread per hardware context. Each is a separate requirement from the table above.

PredictThen set it up in the simulator.
  1. A superscalar (2-issue, scalar) core with 1 context runs a single dependency chain with no memory stalls. What's its utilization? What single change fixes it?
    Show answer

    50%. The chain supplies one instruction per clock, so one ALU idles. Fix it with ILP 2 (independent instructions in the stream). Adding a second context alone doesn't help in "one thread per clock" mode. It does help in SMT mode, where a second thread fills the other slot.

  2. A SIMD core with 4 contexts runs 4 vectorized threads with 3 arithmetic instructions per 12-cycle load. Is it saturated? What if the code is only 4/8 coherent?
    Show answer

    It needs ⌈15/3⌉ = 5 threads to hide the latency, so 4 threads give 80% issue utilization. At 4/8 coherence, each vector instruction does only half its lane-work, so the total is 40% of peak. The two losses multiply.

  3. A scalar+SIMD core (2-issue) runs vector-only code. What fraction of peak can it reach, and why?
    Show answer

    Peak is 1 + 8 = 9 lane-ops per clock, and vector-only code can use at most 8 (the scalar unit idles): 89% at best. To reach 100%, every clock needs one scalar and one vector instruction ready, such as address arithmetic and loop counters running alongside the math.

  4. You have 16 cores with 4 contexts each, but your program creates 8 threads. What fraction of the chip can possibly be busy?
    Show answer

    At most 8 of 16 cores have any work, so ≤ 50%. Even those 8 cores have only 1 of their 4 contexts filled, so they can't hide memory latency either. You'd want at least 64 threads (16 × 4), and in practice a lot more than that.

Review

Terms to know, and questions to test yourself

Instruction stream
The sequence of instructions one thread executes. Each needs its own execution context (registers, PC).
Superscalar
One core issuing several independent instructions from the same stream per clock, found automatically by hardware.
Multi-core
Several complete cores on one chip, each running its own instruction stream: thread-level parallelism.
SIMD
One instruction applied to many data elements across many ALUs, amortizing fetch/decode. Explicit (compiler emits vector instructions) or implicit (hardware groups scalar threads, as on GPUs).
Coherent control flow
Many elements following the same instruction sequence, which SIMD needs. Its absence is divergence, handled by masking lanes.
Hardware multithreading
Several execution contexts resident on one core so it can switch threads to hide stalls. Interleaved: one thread per clock. Simultaneous (SMT): several threads in the same clock.
Latency vs throughput
Time to finish one task versus tasks finished per unit time. Throughput processors accept higher per-thread latency to gain throughput.
Stall
A cycle where the core can't issue because the next instruction's inputs aren't ready, usually waiting on memory.
Test yourselfThe questions the lecture poses, plus a few more.
  1. A dual-core chip whose cores are each 25% slower than one fancy core runs the original sin(x) program. Is it faster or slower? What would make it faster?
    Show answer

    Slower (by 25%). The program is one instruction stream, so it uses one core. Split the array between two threads (or declare the loop independent with a forall-style construct) and the potential becomes 2 × 0.75 = 1.5×.

  2. Write the shortest code that makes 8-wide SIMD run at 1/8 of peak.
    Show answer

    One branch where only one lane in eight takes a long path: if (i % 8 == 0) { long computation }. For the whole long computation, 7 of 8 lanes are masked off.

  3. Why does coherent control flow matter for SIMD but not for multi-core?
    Show answer

    SIMD lanes share one fetch/decode, so they can only execute one instruction at a time. Each core has its own fetch/decode, so different cores can follow completely different paths at full speed.

  4. Compute the peak rate of a chip with 8 cores, two 16-wide FMA units per core, at 3 GHz (count an FMA as 2 FLOPs).
    Show answer

    8 × 2 × 16 × 2 × 3 × 10⁹ = 1.536 TFLOP/s.

  5. Does hardware multithreading make an individual memory access faster?
    Show answer

    No. The latency is unchanged. The core just runs other threads' work during it, so the latency stops lowering utilization. Each individual thread actually finishes later.

  6. How many independent data elements does a V100 need in flight for maximum latency hiding? Where does the number come from?
    Show answer

    80 SMs × 64 warps × 32 threads = 163,840.
