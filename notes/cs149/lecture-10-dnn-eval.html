Stanford CS149 · Lecture 10 companion

Efficiently evaluating deep neural networks

A trained neural network is just a program: a long chain of layers, most of which are big, regular loops of multiply-adds. This lecture asks how to run that program fast. The answers come from three directions at once: design networks that need less work, schedule the work well on the hardware (blocking, fusion, clever algorithms), and build hardware whose instructions do more useful math per unit of overhead.

Explain how operator fusion saves memory traffic, including the chunked-softmax trick behind fused attention. Explain why tensor cores and DNN accelerators exist.

The recurring question in this lecture: for this operation, what limits the speed — arithmetic or data movement? Convolutions and matrix multiplies do a lot of math per byte, so the job is to keep that intensity when implementing them (blocking, implicit GEMM). Element-wise operations do almost no math per byte, so the job is to stop them from making their own trips to memory (fusion).
Part 1 · What a DNN computes

Layers are loops of multiply-adds

Just enough about neural networks to see the computation that has to run fast.

Section 1

The efficiency challenge

Deep neural networks (DNNs) come in many topologies: VGG, ResNet, Inception, MobileNet and hundreds of variants, each a different arrangement of layers of different shapes. And they have to run on many kinds of device: server GPUs, phone CPUs, phone neural-engine chips, custom accelerators. The practical problem is the product of the two: for every network and every device, how do you get an implementation that uses the device well?

The lecture groups the answers into three strategies, which structure this page:

  1. Better algorithms. Design network topologies that reach the same accuracy with much less work (Section 4).
  2. Better software. Implement each layer efficiently: map it onto well-tuned matrix multiply, block it for the memory hierarchy, fuse operations together (Parts 2 and 3).
  3. Better hardware, and approximation. Use lower precision, and specialized instructions and chips that make the common operations cheap (Part 4).

This lecture is about evaluation (also called inference): running an already-trained network on new input. Training runs the same layers forward, then backward, and has similar computational character.

Section 2

Neurons, layers and matrix-vector products

A DNN is a big expression: a graph of simple operations. The lecture's warm-up example is a tiny one, max(max(0, a·b + c·d) + e·f + g·h, i·j). Every node is a multiply, an add, or a max. Real networks are the same kind of thing, only with millions of nodes arranged regularly.

The basic unit is a neuron. It takes inputs xi, computes a weighted sum plus a bias, and applies a simple nonlinear function f:

out = f( Σi xi·wi + b )        // f is often ReLU: f(v) = max(0, v)

The weights w and bias b are the parameters learned in training; for evaluation they're constants. Older networks used a sigmoid for f; modern ones mostly use ReLU (rectified linear unit), which just zeroes negative values.

A fully connected layer is a column of neurons that each see every input. Put each neuron's weights in one row of a matrix and the whole layer is one matrix-vector product:

The number of weights in a fully connected layer is (inputs × outputs). Connect every pixel of a 224 × 224 × 3 image to even 1,000 neurons and that's 150 million weights for one layer. That's why image networks use a different kind of layer.

Section 3

Convolution: local connections with shared weights

Two observations about images shrink the layer dramatically:

  • Locality. A useful feature at a pixel (an edge, a corner) depends on the pixels near it. So each output only needs to connect to a small window of the input, say 3 × 3. That's a locally connected layer.
  • Translation invariance. An edge looks the same wherever it is. So every output location can use the same weights. That's a convolution: a locally connected layer with shared weights. The weights are called the filter (or kernel).

Here is the lecture's 3 × 3 convolution of a single-channel image, written as plain C. With every weight 1/9, it's a box blur:

int WIDTH = 1024, HEIGHT = 1024;
float input[(WIDTH+2) * (HEIGHT+2)];   // 1-pixel border so the window never runs off
float output[WIDTH * HEIGHT];
float weights[] = {1/9., 1/9., 1/9.,
                   1/9., 1/9., 1/9.,
                   1/9., 1/9., 1/9.};

for (int j=0; j<HEIGHT; j++)
  for (int i=0; i<WIDTH; i++) {
    float tmp = 0.f;
    for (int jj=0; jj<3; jj++)
      for (int ii=0; ii<3; ii++)
        tmp += input[(j+jj)*(WIDTH+2) + (i+ii)] * weights[jj*3 + ii];
    output[j*WIDTH + i] = tmp;
  }

Different weights detect different things. The classic Sobel filters respond to horizontal or vertical changes in brightness, that is, to edges. Try them:

Convolution layers in a real network

Real inputs have several channels (3 for RGB; later layers have 64, 128, 512…). A filter spans all input channels, so a 3 × 3 filter on 64 channels is a 3 × 3 × 64 block of weights, and it produces one output channel. A layer applies K such filters, producing K output channels. The first layer of the 2012 AlexNet network, for example, applies 96 filters of size 11 × 11 × 3 to the image.

A layer's output is typically followed by ReLU and then pooling, which shrinks each channel, for example by taking the max of every 2 × 2 region (W × H becomes W/2 × H/2):

The costs follow directly from the loops. For an output of H × W pixels with K channels, from C input channels with R × S filters:

multiply-adds = H · W · K · C · R · S         // every output pixel, every filter, every weight
parameters    = K · C · R · S (+ K biases)    // independent of the image size
Section 4

Approach 1: design topologies that need less work

The first way to make evaluation fast is to change the network. Between 2014 and 2017 researchers found topologies that reach similar ImageNet accuracy with far less computation. The lecture's comparison (MADDs are multiply-adds per image):

NetworkYearTop-1 accuracyParametersMADDs per image
VGG-16201471.5%138 M15 B
GoogLeNet201570%6.8 M1.5 B
ResNet-18201673%*11.7 M1.8 B
MobileNet-224201770.5%4.2 M0.6 B

* 10-crop result; ResNet's single-crop results are similar to the other networks'.

That's about a 25× reduction in cost at similar accuracy (15 B / 0.6 B) in three years. For comparison, hardware roughly doubled in performance over the same period. ResNet's contribution was residual (skip) connections, which made deep networks trainable; its 34-layer version needs 3.6 billion FLOPs where VGG-19 needs 19.6 billion.

MobileNet's trick: depthwise separable convolution

A standard 3 × 3 convolution with C input and K output channels mixes space and channels in one step: every one of the K filters looks at a 3 × 3 × C window. MobileNet factors that into two cheaper steps:

  1. Depthwise: C separate 3 × 3 × 1 filters, one per input channel. Spatial filtering, no channel mixing.
  2. Pointwise: K filters of size 1 × 1 × C. Channel mixing, no spatial extent.

MobileNet's paper reports that about 95% of its multiply-adds are in 1 × 1 convolutions (which also hold 75% of its parameters; most of the rest are in the final fully connected layer). That matters for the next part: a 1 × 1 convolution is a matrix multiply with no rearrangement, and matrix multiply is the most optimized routine in numerical computing.

Fewer FLOPs isn't automatically less time. Depthwise convolutions do very little arithmetic per byte they read (each weight is used for one channel only), so on a GPU they tend to be bandwidth-bound. Count bytes as well as FLOPs.
Part 2 · Making convolution fast

Approach 2: implement layers efficiently

Turn convolution into matrix multiply, then make matrix multiply use the memory hierarchy well.

Section 5

The direct implementation: seven nested loops

A convolution layer applied to a batch of images, written directly (stride 1, no padding logic shown):

float input[BATCH][IN_H][IN_W][IN_DEPTH];          // input activations
float output[BATCH][IN_H][IN_W][NUM_FILTERS];      // output activations
float weights[NUM_FILTERS][FILTER_Y][FILTER_X][IN_DEPTH];
float biases[NUM_FILTERS];

for (int img=0; img<BATCH; img++)
  for (int j=0; j<IN_H; j++)
    for (int i=0; i<IN_W; i++)
      for (int f=0; f<NUM_FILTERS; f++) {
        float tmp = biases[f];
        for (int kk=0; kk<IN_DEPTH; kk++)      // sum over input channels
          for (int jj=0; jj<FILTER_Y; jj++)    // spatial convolution (Y)
            for (int ii=0; ii<FILTER_X; ii++)  // spatial convolution (X)
              tmp += weights[f][jj][ii][kk] * input[img][j+jj][i+ii][kk];
        output[img][j][i][f] = tmp;
      }

(The slide's version initializes tmp from biases[NUM_FILTERS], one past the end; it means biases[f].) There's a lot of reuse in this loop nest: every filter weight is used at every pixel of every image, and every input value is used by every filter and by up to 9 neighboring windows. Reuse is an opportunity: a value loaded into fast storage once can feed many multiply-adds. But the naive loop order doesn't exploit it well, and writing a fast version of seven loops for every layer shape by hand is hard. The standard move is to turn the problem into one that's already been solved.

Section 6

Convolution as matrix multiplication ("explicit GEMM")

GEMM (general matrix-matrix multiply) has had decades of tuning on every platform. To use it, rewrite the convolution: for each output pixel, copy the 3 × 3 window of input it needs into one row of a new matrix. Then every output pixel is a dot product of its row with the filter's 9 weights, and the whole convolution is a matrix-vector product. This rearrangement is called im2col ("image to columns"):

With more filters, the weight vector becomes a matrix with one column per filter. With more input channels, each row gets 9 values per channel, because a filter sums its response over all channels. The general mapping, using NVIDIA's symbols (batch N, input H × W × C, K filters of R × S × C, output P × Q × K):

The catch is the size of A. Each input value is copied into about R × S rows, so materializing A increases memory traffic by roughly a factor of R × S (9 for 3 × 3 filters) and needs a lot of extra storage. For the lecture's big example (N = 32, 256 × 256 images, 128 channels, 3 × 3 filters), the activations are 1 GiB in fp32, and the im2col matrix is 9 GiB.

A 1 × 1 convolution is the exception: its "window" is a single pixel, so A is just the activation tensor viewed as an (NHW × C) matrix, with no copying. That's why MobileNet's heavy use of 1 × 1 convolutions maps so well onto GEMM.

Section 7

Making GEMM fast: blocking

So how does a good GEMM work? Start with the obvious version:

float A[M][K], B[K][N], C[M][N];
// compute C += A * B
#pragma omp parallel for
for (int j=0; j<M; j++)
  for (int i=0; i<N; i++)
    for (int k=0; k<K; k++)
      C[j][i] += A[j][k] * B[k][i];

It has plenty of parallelism. Its problem is low arithmetic intensity: it doesn't exploit temporal locality. Every element of A is used N times and every element of B is used M times, but by the time the loop comes back to a value, it's long gone from the cache. For large matrices each multiply-add ends up fetching its operands from memory: 2 FLOPs for every 8 bytes, 0.25 FLOPs per byte.

The fix is blocking (tiling): compute a partial result for one block of C while the blocks of A and B it needs stay in cache.

for (int jblock=0; jblock<M; jblock+=BLOCKSIZE_J)
  for (int iblock=0; iblock<N; iblock+=BLOCKSIZE_I)
    for (int kblock=0; kblock<K; kblock+=BLOCKSIZE_K)
      // multiply one block of A by one block of B, accumulate into one block of C
      for (int j=0; j<BLOCKSIZE_J; j++)
        for (int i=0; i<BLOCKSIZE_I; i++)
          for (int k=0; k<BLOCKSIZE_K; k++)
            C[jblock+j][iblock+i] += A[jblock+j][kblock+k] * B[kblock+k][iblock+i];

With square b × b blocks, each block step loads 2b² values of A and B and does b³ multiply-adds: every value loaded is used b times. So the arithmetic intensity grows in proportion to the block size, roughly b/4 FLOPs per byte in fp32. The block size is limited by how much fits in fast storage.

That answers the lecture's self-check, "do you want as big a BLOCKSIZE as possible?" You want blocks big enough to get above the ridge point, and no bigger: the blocks must fit (with room for everything else in the cache), bigger blocks mean fewer independent blocks to spread across cores, and more padding waste at the edges of matrices whose sizes aren't multiples of the block. Notice also that the faster tensor-core arithmetic moves the ridge point right: the faster the math, the more reuse you need.

Blocking at every level, and vectorizing the block

A real implementation blocks hierarchically: blocks sized for the L2 cache, sub-blocks for L1, and finally tiny blocks held in registers. Each loop level matches one level of the memory hierarchy.

Inside the innermost block the code must also use SIMD. The lecture shows three ways, and the right one depends on the block's shape:

  1. Vectorize the i loop (across a row of C). Broadcast one element of A to all lanes (splat), multiply by a vector of B's row, accumulate into a vector of C. Good spatial locality in B, but the working set grows by the SIMD width. Needs a wide i dimension.
  2. Vectorize the k loop (a dot product). If the i dimension is small, pre-transpose the block of B so that a row of A and a "row" of Bᵀ are both contiguous, then use SIMD dot products.
  3. Compute a SIMD_WIDTH × SIMD_WIDTH tile of C in registers, with pre-transposed A and C blocks, so the innermost operations are independent of each other (no serial dependency on one accumulator).

Now look back at MobileNet's layer list: the matrix shapes change from layer to layer (112 × 112 images with 32 channels at the start, 7 × 7 images with 1,024 channels at the end). Different layers of one network may need different schedules, which is exactly why writing DNN libraries is hard work.

Section 8

Implicit GEMM, and giving the GPU enough work

Explicit GEMM pays for its convenience with that R × S blow-up in memory traffic. Implicit GEMM avoids it: the kernel is written as a GEMM over the virtual matrix A, but it computes each element's address in the activation tensor on the fly instead of reading a materialized copy.

  • A naive implicit GEMM just indexes into the input and weight tensors directly, with no blocking. Correct, but slow.
  • A good one materializes only one sub-block of the convolution matrix at a time, in the GPU's on-chip shared memory, then runs a well-tuned shared-memory GEMM on it. No extra off-chip storage, and no extra DRAM traffic: each input value is read from DRAM once per block and duplicated only inside shared memory.

This is Lecture 7's convolution example (load the tile plus its border into shared memory once, then compute from it) scaled up. NVIDIA's CUTLASS library provides the building blocks for writing such kernels: fast shared-memory GEMMs, warp-level GEMMs, iterators for loading blocks and indexing tensors, and reductions. It's for layers whose sizes haven't been heavily tuned in NVIDIA's cuDNN library.

A GPU needs a lot of parallel work

Recall the V100: 80 SMs, each running many warps, with tensor cores, a 6 MB L2 and 900 GB/s from 16 GB of HBM. To fill it, a layer needs lots of independent outputs. The lecture compares two convolution problems with 128 filters:

CaseOutputsOutput data (fp32)
N = 1 image, P = Q = 6464 × 64 × 128 × 1 = 524,2882 MB
N = 32 images, P = Q = 256256 × 256 × 128 × 32 = 268 M1 GB

Measured throughput tells the story. With small images and one image at a time the V100 reaches only about 20 TFLOPS on these convolutions; with larger images or bigger batches it climbs to around 85, and flattens there. Throughput also climbs with the number of input channels, and 1 × 1 filters stay well below larger filters: less work per output means less reuse. Batching is one of the most effective optimizations for inference throughput, at the price of latency, since you must wait for a batch of requests to arrive.

Section 9

Algorithmic improvements: FFT and Winograd

Blocking changes how data moves; these change how much arithmetic is done.

  • FFT convolution. Convolution in space is element-wise multiplication in the Fourier domain. The overhead is the FFT of the inputs and the inverse FFT of the outputs (O(N log N) each). The inverse transform is amortized over all input channels, since the channel sum can happen in the Fourier domain. Best for large filters.
  • Winograd convolution. A work-efficient way to compute several outputs of a small filter with fewer multiplies, by sharing partial products.

The lecture's 1D example: two outputs of a 3-tap filter, y0 = x0w0 + x1w1 + x2w2 and y1 = x1w0 + x2w1 + x3w2. Direct: 6 multiplies and 4 adds. Winograd's F(2, 3) algorithm:

m1 = (x0 − x2) · w0
m2 = (x1 + x2) · (w0 + w1 + w2)/2      // the filter factors depend only on w:
m3 = (x2 − x1) · (w0 − w1 + w2)/2      // precompute them once per filter
m4 = (x1 − x3) · w2
y0 = m1 + m2 + m3
y1 = m2 − m3 − m4

4 multiplies and 8 additions (4 to form the m's, 4 to combine them). Trading multiplies for adds pays off because multiplies are the more expensive operation, and the savings grow in 2D: for a 2 × 2 block of outputs of a 3 × 3 filter, Winograd needs 16 multiplies instead of 36, 2.25× fewer.

The additions in the transforms aren't free, and they change rounding. Winograd with larger output blocks saves more multiplies but loses numerical accuracy, especially in low precision. It's a trade-off, not a free lunch.

Libraries pick the algorithm for you

Vendors ship libraries with high-performance implementations of the key DNN layers: NVIDIA's cuDNN, Intel's oneDNN, Apple's and ARM's equivalents. cuDNN offers several algorithms for the same convolution (implicit GEMM, precomputed implicit GEMM, explicit GEMM, direct, FFT, tiled FFT, Winograd), because the fastest one depends on the layer's shape, and it can benchmark them to pick one.

Part 3 · Beyond one layer

Stop sending intermediate results through memory

Operator fusion, the fused-attention trick, and compilers that schedule for you.

Section 10

Memory traffic between operations: fusion

Consider a common sequence: convolution, then a per-element scale and bias, then a 2 × 2 max pool. Run as three separate library calls, each operation writes its whole output to memory and the next one reads it back. For the big example, that's a gigabyte written and read between each step.

But the scale-and-bias can be applied to each element right after the convolution computes it, and the max-pool output can be computed as soon as each 2 × 2 region of the conv output is done. Fusing the three into one kernel means the only memory traffic is the conv's input and the pool's output:

        ...
        output[img][j][i][f] = tmp*scale + bias;   // scale+bias fused: applied before the store

The explorer shows why fusion matters more every year. With slow fp32 arithmetic, the 3 × 3 convolution takes so long that the extra element-wise passes add only about 10%. Speed up the math with tensor cores, or use 1 × 1 convolutions with less math per byte, and those "cheap" element-wise kernels become a large share, or most, of the time. The faster the arithmetic, the more the data movement between operations dominates.

Exercisefrom the lecture
  1. How would you fuse the 2 × 2 max pool into the conv loop nest?
    Show one answer

    Reorder the loops so each iteration produces a 2 × 2 group of output pixels for a filter (step j and i by 2 and compute four tmp values). Take the max of the four (after scale and bias) and store one value into a half-size output array. The full-size conv output is never written to memory. In a blocked GPU kernel, make each tile's width and height even, so every pooling window lies inside one tile.

Section 11

A fusion trick for attention

Transformers, the sequence models behind large language models, take a sequence of tokens in and produce a sequence out (for example, predicting the next word). Their core is the attention module. With N tokens, each represented by a d-dimensional vector, the queries Q, keys K and values V are each N × d:

S = Q Kᵀ            // N × N: how much each token attends to each other token
P = softmax(S)      // softmax along each row of S
O = P V             // N × d

The trouble is S and P: they're N × N. For long sequences (thousands of tokens) the naive implementation needs N² space, and it writes S to memory, reads it back for the softmax, writes P, and reads it back for PV. Two matrix multiplies are fusion candidates, but the softmax in between looks like it's in the way: to normalize a row you need the max and the sum over the entire row.

For a row x, the numerically safe softmax is:

m(x) = maxi xi                   // subtract the max so exp never overflows
f(x) = [ e^(x1 − m(x)), …, e^(xB − m(x)) ]
l(x) = Σi f(x)i
softmax(x) = f(x) / l(x)

The key observation: softmax can be computed in chunks. Split x into [x(1) x(2)]. If you've processed chunk 1 and kept only its m and l, then when chunk 2 arrives:

m(x) = max( m(x(1)), m(x(2)) )
l(x) = e^(m(x(1)) − m(x))·l(x(1)) + e^(m(x(2)) − m(x))·l(x(2))

The old partial sum is just rescaled by e(old max − new max). Step through it:

Fused attention

Now fuse all three steps. Process Q in blocks of rows and K, V in blocks of columns/rows. For each pair of blocks: load Qi, Kᵀj, Vj; compute the block Sij = QiKᵀj; compute its row maxes, exponentials and row sums; multiply PijVj and accumulate into the output block Oi, rescaling what's already there by the same e(old m − new m) factors.

The memory saving is large. With N = 4,096 tokens, one attention head's S matrix is 4,096² ≈ 16.8 million values, 64 MiB in fp32, and a model has many heads and a batch of sequences. The price is a little extra computation: the output block must be rescaled each time the running max changes. Trading a few extra FLOPs for much less memory traffic is almost always a good deal on modern hardware. This is the idea behind FlashAttention (Dao et al., 2022).

Section 12

Fusion in frameworks, and lower precision

The old approach to fusion was for library writers to hard-code a few popular fused operations (TensorFlow shipped a fused batch-norm, for example). That can't keep up with the number of possible operation sequences. Modern systems let a compiler generate the fused implementation: cuDNN's "backend" API accepts a graph of operations and produces a single kernel for it, without runtime overhead or passing intermediate results through memory. If you've seen Halide, this is its compute_at scheduling directive: compute a producer's values inside the consumer's loop, just where they're needed. Many research and production compilers (TVM, XLA, Triton-based compilers, and others) try to schedule DNN operations automatically.

Low precision

Another trick is to use fewer bits for weights and activations. 16-bit and 8-bit values are common; research has gone as far as 1-bit (binary) networks. Halving the bits halves the memory traffic and storage, and lets hardware pack more arithmetic units into the same area and energy. Unit 5 of these notes covers the formats (fp16, bf16, int8) and what quantization does to accuracy.

Part 4 · Hardware

Hardware built for DNNs

Why GPUs are good at this, why they aren't ideal, and what specialized hardware changes.

Section 13

Why a GPU is a good platform, and why it isn't the ideal one

Why a GPU is good for DNNs. The heavy layers behave like dense matrix-matrix multiplication: high arithmetic intensity, massive data parallelism, regular SIMD-friendly control flow. GPUs are flop-rich, have high memory bandwidth for the parts that aren't compute-bound, and come with heavily optimized kernel libraries (cuDNN).

Why a GPU might be sub-optimal. A GPU is still a general-purpose programmable processor. For every multiply-add, it fetches and decodes an instruction, reads operands from a large register file, and manages warps. For a workload that is almost entirely multiply-adds, that's overhead you'd like to eliminate.

The first answer is to make each instruction do more work, amortizing the cost of instruction-stream processing over many operations:

  • fused multiply-add: a·x + b, 2 operations per instruction;
  • 4-component dot product: 8 operations;
  • 4 × 4 matrix multiply-accumulate A·B + C: 64 multiply-adds, 128 operations.
Section 14

Tensor cores, and dedicated DNN accelerators

NVIDIA's version of the big-instruction idea is the tensor core: a unit that executes a small matrix multiply-accumulate D = A·B + C as one warp instruction, with A and B in fp16 and accumulation in fp32. The A100 (Ampere) numbers from the lecture:

Per SMWhole GA100 GPU (108 SMs)Peak at 1.41 GHz
64 fp32 multiply-add ALUs6,912 ALUs6,912 × 2 × 1.41 G = 19.5 TFLOP/s
32 int32 ALUs3,456
4 tensor cores432 tensor cores312 TFLOP/s (fp16 in, fp32 accumulate)

Divide it out: 312 T / (432 × 1.41 G) ≈ 512 FLOPs per tensor core per clock, that is 256 multiply-adds per clock, the size of one 8 × 4 by 4 × 8 matrix multiply (8 × 8 × 4 = 256). The tensor cores deliver 16 times the fp32 ALUs' peak: one instruction starts 256 multiply-adds instead of 32, so far less of the energy goes to instruction processing, and the fp16 operands are half the width. (As Unit 5 stresses, the peak assumes matrix shapes and precisions that fit the unit; real layers get less.)

Going all the way: accelerators

If DNN evaluation is mostly matrix multiply, why keep general-purpose cores at all? A wave of DNN accelerators answers "mostly don't": Google's TPU, Apple's Neural Engine, the NPU in Huawei's Kirin phone chips, Graphcore's IPU, Intel's inference accelerators, Cerebras's wafer-scale engine, SambaNova's Cardinal. They differ widely, but share the lecture's themes: large arrays of low-precision multiply-add units, lots of on-chip storage to keep operands close (reuse!), and control that is coarse-grained rather than one instruction per operation. GPUs, meanwhile, have become accelerators themselves: Ampere-class and later GPUs devote a large share of their math throughput to tensor cores.

The whole lecture in one line: DNN evaluation is fast when every value brought on chip is used many times, and every instruction does a lot of math. Topology design reduces the math; blocking, implicit GEMM and fusion reduce the data movement; tensor cores and accelerators reduce the per-operation overhead.

Check yourself

Questionsanswer before revealing
  1. A convolution layer produces a 56 × 56 × 128 output from 64 input channels with 3 × 3 filters. How many multiply-adds and parameters (ignoring biases)?
    Show answer

    Multiply-adds: 56 × 56 × 128 × 64 × 9 = 231,211,008 (about 231 M). Parameters: 128 × 64 × 9 = 73,728. The parameter count doesn't depend on the image size.

  2. By what factor does a depthwise separable convolution reduce the work of a 3 × 3 convolution with 256 output channels?
    Show answer

    The cost ratio is 1/K + 1/(R·S) = 1/256 + 1/9 ≈ 0.115, so about 8.7× less work.

  3. Why does explicit im2col increase DRAM traffic, and how does implicit GEMM avoid it?
    Show answer

    im2col copies each input value into about R × S rows of the convolution matrix and writes that matrix to memory, then GEMM reads it: roughly R × S times the traffic. Implicit GEMM builds only one sub-block of that matrix at a time, in on-chip shared memory, so the duplication never reaches DRAM.

  4. In the blocked-GEMM model, three b × b fp32 blocks fit in 96 KB. What's the largest b, and the approximate arithmetic intensity?
    Show answer

    3 × b² × 4 bytes ≤ 98,304 gives b² ≤ 8,192, so b = 90 (90² = 8,100). Intensity ≈ b/4 ≈ 22 FLOPs per byte, just above the V100's fp32 ridge point of about 17.

  5. Use Winograd F(2, 3) with x = (1, 2, 3, 4) and w = (1, 1, 1). What are m1…m4 and the outputs?
    Show answer

    m1 = (1 − 3)·1 = −2; m2 = (2 + 3)·3/2 = 7.5; m3 = (3 − 2)·1/2 = 0.5; m4 = (2 − 4)·1 = −2. y0 = −2 + 7.5 + 0.5 = 6 = 1 + 2 + 3; y1 = 7.5 − 0.5 + 2 = 9 = 2 + 3 + 4.

  6. A row is processed in two chunks. Chunk 1 has m = 3 and l = 2.0. Chunk 2 has m = 5 and l = 1.5. What are the combined m and l?
    Show answer

    m = 5. l = e3 − 5 × 2.0 + e0 × 1.5 = 0.1353 × 2.0 + 1.5 ≈ 1.771.

  7. Why does fusing an element-wise operation into a convolution matter more when the convolution runs on tensor cores?
    Show answer

    The element-wise pass costs the same memory time either way (read and write the whole tensor). Tensor cores shrink the conv's compute time, so the unfused memory passes become a larger fraction of the total, and can dominate it.
