Stanford CS149 · Lecture 1 companion

Why parallelism? Why efficiency?

For decades, programs got faster every year without anyone touching them. Around 2005 that stopped. This lecture explains why it stopped, what chip designers did instead, and why the result forces every performance-minded programmer to think about parallelism and efficiency. That means thinking both about how to split work, and about how data moves.

You'll be able to
Define speedup and efficiency, and explain what limits them (communication, load imbalance). Describe what a processor does with a program, what instruction-level parallelism is, and why superscalar execution and clock-frequency scaling ran out. Explain the power wall. Describe memory as an address space, and explain latency, stalls, caches and the cache hierarchy.
Background
None required. This page builds everything it uses. Units 1–3 of these notes go deeper into the processor, and Lecture 2 continues directly from here.
Source

The lecture's argument in one breath. Single-thread performance used to double every ~18 months, thanks to higher clock frequencies and instruction-level parallelism. Both hit walls: ILP ran out, and higher frequency costs too much power. So chips now grow by adding more processing units, and specialized ones. Programs only get faster if they are written to use them, and use them efficiently, which mostly comes down to moving data efficiently.
Part 0 · The course's big ideas

What parallel computing is about

A definition, a measure of success, and three classroom experiments that reveal what gets in the way.

Section 1

A parallel computer, and how to measure it

A common definition: a parallel computer is a collection of processing elements that cooperate to solve problems quickly. Every word matters. Collection: there is more than one of them. Cooperate: they work on one problem together, which means they must divide the work and exchange results. Quickly: the whole point is performance. We use several processors because we want the answer sooner, and, as the course keeps stressing, because we want to get it efficiently, without wasting hardware or energy.

The basic measure of success is speedup:

speedup(P processors) = execution time using 1 processor ÷ execution time using P processors

If a job takes 60 seconds on one processor and 20 seconds on four, the speedup is 60 / 20 = 3×. The ideal is P× (four processors, four times faster), and real programs almost always fall short. A second measure tells you by how much:

efficiency = speedup ÷ P

Three times faster on four processors is 75% efficient: a quarter of the hardware's potential was lost somewhere. The rest of the course is about where it goes, and how to get it back. The lecture's three demos show the main culprits.

Measure against the best sequential program, not a parallel program run on one processor. The parallel version usually does extra work (splitting, combining, synchronizing), so its one-processor time is slower than a good sequential program's, and it would flatter the speedup.
Section 2

Three experiments: what limits speedup

The lecture opens with students acting as processors, cooperating to compute a sum. You don't need a classroom to see the same effects: the explorer below models it. A pile of N numbers is split between P processors. Each adds up its share (one time unit per addition), then the partial sums are combined. Combining means communicating: a partial sum has to be passed to someone else, which takes c time units per message, and then added in.

The class observed three things, and each has a preset below:

  1. Demo 1: communication limits speedup. Two "processors" split the work, but telling each other their partial sums took time. Sitting closer together (or letting them shout) made communication cheaper and improved the speedup.
  2. Demo 2: imbalance limits speedup. With four processors, some ran out of work and sat idle while others were still busy. The job isn't done until the last processor finishes. Distributing the work more evenly improved the speedup.
  3. Demo 3: communication can dominate. With the whole room helping on a problem with lots of communication relative to computation, most of the time went into passing values around. Adding processors can then make things slower.

Two structural lessons are visible in the explorer. First, the job's time is set by the slowest path, not the average: in Demo 2, three processors finish early and wait for the fourth. Second, how you combine results matters as much as how you split the work. If everyone reports to one processor, it receives P − 1 messages one after another. Combining in pairs, as a tree, needs only log₂ P rounds, because many pairs communicate at the same time. With 32 processors that's 5 rounds instead of 31 messages.

PredictAnswer before opening, then check with the explorer.
  1. With N = 32, c = 8 and the even split, is 2 processors faster than 1? By how much?
    Show answer

    One processor needs 31 additions: 31 time units. Two processors each add 16 numbers (15 additions), then one message (8) and one final addition (1): 15 + 8 + 1 = 24 time units. The speedup is 31 / 24 ≈ 1.29×, far from 2×. Communication cost 8 of those 24 units. With c = 1 it becomes 31 / 17 ≈ 1.82×.

  2. Why does adding processors eventually make Demo 3 slower?
    Show answer

    Doubling P halves each processor's share of the additions, but the combining work grows: more messages, each costing c. Once each share is tiny, nearly all the time is communication, and more processors add more of it. The best P balances the two costs.

Section 3

The course's three themes

Theme 1 · Parallel thinkingDesigning programs that scale: decompose the work into pieces that can safely run in parallel, assign the pieces to processors, and manage communication and synchronization so they don't limit speedup.
Theme 2 · How the hardware worksHow parallel computers implement the abstractions you program against, what each mechanism costs, and the design trade-offs: performance versus convenience versus cost.
Theme 3 · EfficiencyFast ≠ efficient. A program can run faster on a parallel machine while using that machine poorly. Is a 2× speedup on 10 processors good? That's 20% efficiency.
Why hardware mattersThe demos showed it: the machine's characteristics, such as the cost of communication, decide how fast a parallel program can go. You can't write fast parallel code while treating the hardware as a black box.

Theme 3 has two sides. The programmer's question is: am I using the capabilities this machine gives me? The hardware designer's question is: which capabilities should the chip have, given limits on silicon area, power and cost? A good speedup number alone answers neither. The lecture's example, a 2× speedup on a 10-processor computer, is a faster program that leaves 80% of the machine idle.

Part 1 · Why parallelism?

The free lunch, and why it ended

Why programmers could ignore parallelism for decades, and why they no longer can.

Section 4

Historical context: why avoid parallel processing?

From the mid-1980s to the early 2000s, the performance of a single processor running a single thread doubled roughly every 18 months. Over that period, one-thread performance improved by more than a thousandfold.

That had a surprising consequence: parallelizing your code was usually not worth the effort. Rewriting a program to use two processors was hard and might give you 1.8×. Doing nothing gave you the same speedup about a year later, when a faster chip arrived. Software got faster for free.

Where did those gains come from? Until about fifteen years before this lecture, there were two main sources of single-thread speedup:

  1. Instruction-level parallelism (ILP): the processor finds instructions in the program that don't depend on each other and runs them at the same time (superscalar execution).
  2. Higher clock frequency: the processor does its steps more times per second.

To see why both ran out, we first need a precise picture of what a processor does.

Section 5

What is a program, to a processor?

Here is a small C program: start with x = 1, and ten times replace x with x + x. It prints 1024. A compiler translates it into the language the processor understands: a list of machine instructions, each a simple operation such as "move this value", "add these two", "compare", "jump".

The lecture's analogy: a program is like a recipe. Each step is simple, the steps are carried out in order, and the result is only correct if they're followed as written. The processor is the cook. Unlike a cook, it follows a billion or so steps per second, without ever understanding what the dish is.

Notice how much of the compiled program is bookkeeping: moving values between memory and registers, counting the loop, jumping. The actual work, addl, is one instruction in nine inside the loop. An optimizing compiler would do much better, but the point stands: to a processor, a program is only a sequence of instructions, and speed means getting through that sequence faster.

Section 6

What does a processor do? It executes instructions

The lecture introduces a very simple processor with three parts. They are drawn the same way in every diagram in these notes:

  • Fetch/decode determines which instruction runs next and what it asks for.
  • The ALU (the execution unit) performs the operation an instruction describes. That may change values in the processor's registers or in the computer's memory.
  • The execution context holds the registers, which maintain the program's state: the values of the variables used as the inputs and outputs of operations.

Step through one instruction, add R0 ← R0, R1: "add the contents of register R0 to the contents of register R1, and put the result into R0".

A program runs by repeating this over and over, one instruction after another. The lecture's very simple processor executes one instruction per clock. Lecture 2's Section 0 has two simulators that run whole programs on this kind of processor, phase by phase.

Review: what is "state"? A program is a list of instructions. An instruction describes an operation for the processor to perform, and executing it usually modifies the computer's state. The state is the values of the program's data, stored in the processor's registers or in memory.
Section 7

Instruction-level parallelism: more than one instruction per clock

Take a tiny computation, a = x*x + y*y + z*z, with x, y and z in registers R0, R1 and R2. It compiles to five instructions:

1mul R0, R0, R0// x*x
2mul R1, R1, R1// y*y
3mul R2, R2, R2// z*z
4add R0, R0, R1// x*x + y*y
5add R3, R0, R2// … + z*z → a

Five instructions at one per clock take five clocks. Can we do better? The three multiplies don't depend on each other: none uses another's result. If the processor could perform two or three instructions at once, they could run together. The adds can't join them: instruction 4 needs the results of 1 and 2, and instruction 5 needs 3 and 4.

The number of instructions that can run at the same time is the program's instruction-level parallelism (ILP). Here it is 3 in the first step, then 1, then 1. However many instructions a processor can perform per clock, this program needs at least three clocks.

What does it mean for a parallel schedule to respect program order? Not that instructions run strictly one after another: then there would be no parallelism. It means the program's results must be exactly what sequential execution would produce. Every instruction must see the values that the instructions before it would have left. The naive setting in the explorer breaks this rule, and the answer is wrong.

Section 8

Superscalar execution, and its diminishing returns

Idea #1 of processor speedup: superscalar execution. The processor automatically finds independent instructions in the instruction sequence and executes them in parallel on multiple execution units. (Alternatively the compiler finds them at compile time and encodes the dependencies in the binary.) The programmer writes an ordinary sequential program, and the hardware finds the parallelism.

So why not build a 16-wide processor? Because ordinary programs don't contain that much ILP. Dependencies chain instructions together, branches make it hard to look far ahead, and the independent instructions near any point in the program run out quickly.

That's the first wall. Building wider processors costs more silicon and more power for almost no gain. For a deeper look at how a superscalar core finds ILP, including a larger dependency-graph example, see Lecture 2, Section 2 and Unit 3 of these notes.

Section 9

The power wall: why clocks stopped getting faster

The second source of speedup was clock frequency: more clock ticks per second means more instructions per second. Frequency rose steadily for decades and then, in the mid-2000s, stopped at around 3–4 GHz, even though chips kept getting more transistors. The reason is power.

A transistor consumes power in two ways:

  • Dynamic power, spent every time transistors switch: dynamic power ∝ capacitive load × voltage² × frequency. Raising the frequency raises power proportionally, but that's the mild part.
  • Static power, lost to leakage: transistors burn power even when they aren't switching.

The catch is that a transistor can only switch faster if it is driven at a higher voltage. The maximum frequency is determined by the core voltage. So pushing frequency up also pushes voltage up, and voltage enters squared. Together, power grows much faster than frequency: in the measurements the lecture shows, doubling the clock from 2.4 to 4.8 GHz multiplies power by roughly four. And power becomes heat, which has to be removed from a chip the size of a fingernail.

How much power is too much? The lecture lists typical thermal design power (TDP), the heat a cooling system must remove:

DevicePower
Mobile phone processor½–2 W
Apple M1 laptop chip13 W
Intel Core i9 10900K (desktop CPU)95 W
NVIDIA RTX 4090 GPU450 W
Standard microwave oven (for scale)900 W
World's fastest supercomputermegawatts

A desktop chip is already dissipating a sizeable fraction of a microwave oven's power. A phone has a budget a hundred times smaller. Power is a critical design constraint in every modern processor. So what should a designer do with a fixed power budget?

Spend the power budget on more, slower cores

Because power rises so steeply with frequency, running two cores at a lower frequency can deliver more total work than one core at a high frequency, for the same power. Try it: fix a power budget and see how fast each core can run as the core count grows.

That trade-off is the heart of the lecture: with power as the limit, the way to more performance is more processing units running in parallel, not faster ones. But a single-threaded program sees only the line, not the bars. It gets slower as the cores multiply.

Section 10

ILP tapped out, frequency stopped: no more free lunch

Put the two walls together and you get the picture in the lecture's chart of Intel CPU trends (after Herb Sutter's 2005 article "The Free Lunch Is Over"):

The consequence is the lecture's central claim:

  • The rate of single-instruction-stream performance scaling has fallen almost to zero. Frequency scaling is limited by power, and ILP scaling is tapped out.
  • Architects still get more transistors every generation, and now use them to build more execution units that run in parallel: more cores, wider vector units. They also build units specialized for a specific task, such as graphics, audio and video, or neural networks.
  • Software must be written to be parallel to see performance gains. No more free lunch for software developers.
Moore's law did not end in 2005. Transistor counts kept growing. What ended was the easy conversion of those transistors into single-thread speed. The transistors went into parallel hardware instead, so the performance is still there, but only for programs that ask for it in parallel.
Section 11

Parallel machines are everywhere

Every kind of computer, from a Raspberry Pi to the world's largest supercomputer, is now a parallel machine. The lecture's examples span five orders of magnitude:

What using it all is worth

The first programming assignment makes this concrete. A single-threaded C program, compiled with full optimization (-O3), runs on a quad-core Intel CPU. A version rewritten to use all the chip's parallel resources runs about 32–40× faster on the same chip.

Part 2 · Why efficiency?

Parallel is not enough

With power as the limit, the winning designs are the ones that get the most work per joule.

Section 12

Software must be efficient too: specialization

In modern computing, software must be more than parallel: it must also be efficient. Power is the binding constraint, from phones to datacenters, so the question is not only "how fast?" but "how much work per watt?". Modern systems answer it in two ways: many processing units, and specialized processing units. A unit built for one kind of task does that task with far less energy than a general-purpose core, because it skips the general machinery (fetching and decoding instructions, scheduling, large caches) and spends its energy on the arithmetic itself.

The same logic reaches datacenter scale. Google's TPU (Tensor Processing Unit) is a processor specialized for machine-learning computation, deployed in "pods" of many chips. The lecture shows a gallery of accelerators for deep neural networks: Google TPU, Huawei's Kirin NPU, Apple's Neural Engine, Graphcore's IPU, NVIDIA GPUs with Tensor Cores, Intel's inference accelerator, Cerebras's wafer-scale engine and SambaNova's chips. They were all designed for efficiency at one important workload.

The lecture's pivot: achieving efficient processing almost always comes down to accessing data efficiently. Arithmetic is cheap. Getting the operands to the arithmetic units, from memory, through caches, across chips, is where time and energy go. That is why Part 3 is about memory.
Part 3 · Memory

Accessing data efficiently

What memory is, why reaching it is slow, and how caches make it faster.

Section 13

What is memory? An array of bytes

A program's memory address space is simple to describe: memory is organized as an array of bytes, and each byte is identified by its address, its position in that array. (We assume memory is byte-addressable: every byte has its own address.) "The byte stored at address 0x10 has the value 128." "The byte stored at address 0x8 has the value 32."

The processor moves data between memory and registers with two kinds of instruction: a load copies a value from memory into a register, and a store copies a register's value into memory. Arithmetic happens only on registers.

Section 14

Memory latency, and stalls

Memory access latency is the time it takes the memory system to provide data to the processor after it asks: for example, 100 clock cycles, or 100 nanoseconds. (The lecture's human-scale version: ask someone across the room for a number, and it takes about 2 seconds to come back.)

Latency matters because of stalls. A processor stalls (can't make progress) when it can't run the next instruction in its instruction stream because that instruction depends on a previous one that isn't complete. Accessing memory is a major source of stalls, because memory access times are hundreds of cycles:

1ld r0, mem[r2]// load a
2ld r1, mem[r3]// load b
3add r0, r0, r1// needs both loads

The add can't execute until the data from both loads has arrived. Everything that happens before then is waiting.

Section 15

Caches: a faster implementation of the same abstraction

Memory is "just an array of values", and that abstraction never changes. But its implementation can be made faster. A cache is on-chip storage that keeps a copy of a subset of the values in memory. If an address is "in the cache", the processor can load or store it much more quickly than if the data resides only in DRAM.

A cache is a hardware implementation detail. It does not affect a program's output, only its performance. The program still sees one array of bytes.

Caches work at the granularity of cache lines: fixed-size, aligned chunks of memory. A miss brings in the whole line that contains the address. The lecture's example cache is tiny so you can watch it: 2 lines of 4 bytes each (8 bytes in total), with least recently used (LRU) replacement, which means that when the cache is full, the line that has gone unused longest is evicted.

The two examples show the two kinds of locality that make caches work:

  • Spatial locality. Loading one byte brings its whole line, which "preloads" the neighbouring addresses. In Example 1, the access to 0x0 misses, but 0x1, 0x2 and 0x3 then hit.
  • Temporal locality. Accessing the same address again soon hits, because it's still cached. In Example 1, the repeated accesses to 0x2 and 0x1 hit.

Misses come in kinds too. A cold miss is the first access to a line: nothing could have cached it yet. A capacity miss happens when the line was cached but had to be evicted because the cache is too small for everything the program is using. At the end of Example 2, 0x0 misses again even though it was read moments ago: the whole array is 4 lines, and the cache holds 2. Switch to 4 lines and that miss becomes a hit.

Caches reduce the length of stalls: they cut memory access latency whenever the processor accesses data it, or a neighbour, used recently. Processors run efficiently when their data is resident in caches. (Caches also provide much higher bandwidth than DRAM, a topic for later lectures.)

Section 16

The hierarchy: a complex implementation of a simple abstraction

On a modern computer, the implementation of the linear memory address space is complex. The instruction "load the value stored at address X into register R0" might involve a sequence of operations across several caches and DRAM. The common organization is a hierarchy of caches: level 1 (L1), level 2 (L2) and level 3 (L3). Small caches sit near the processor and have low latency; larger ones sit farther away and have higher latency.

Where a program's data lives decides how long its loads take. The explorer computes the average load latency from how often loads are found at each level:

PredictAnswer before opening.
  1. A loop's loads hit L1 99% of the time and otherwise go to DRAM. What is the average load latency?
    Show answer

    0.99 × 4 + 0.01 × 248 = 3.96 + 2.48 = 6.44 cycles. One load in a hundred missing to DRAM increases the average by about 60%.

  2. Does a cache ever change what a correct program computes?
    Show answer

    No. A cache is an implementation detail of the memory abstraction: loads always return the value the array-of-bytes model says they should. Caches change only how long that takes. (Multiple processors add subtleties here, called coherence and consistency, covered in later lectures.)

Summary

What to take away

  • Single-thread performance now improves very slowly. To run significantly faster, programs must use multiple processing elements or specialized hardware. That means knowing how to reason about, and write, parallel and efficient code.
  • Writing parallel programs is challenging. It needs problem partitioning, communication and synchronization, and knowledge of the machine's characteristics. Above all, you need to understand data movement.
  • Modern computers have tremendously more processing power than most programs use. A quad-core laptop CPU can run 30–40× faster than an optimized single-threaded program, if you use it efficiently.
Review

Terms to know, and questions to test yourself

Speedup
Time on 1 processor ÷ time on P processors. Ideal: P.
Efficiency
Speedup ÷ P: the fraction of the machine's potential actually used.
Load imbalance
Some processors have more work than others; the rest sit idle waiting for them.
Communication
Moving data (such as partial results) between processors. It costs time, and can dominate a parallel computation.
Instruction
One simple operation for the processor to perform. A program is a list of them.
State
The values of a program's data, held in registers and memory.
ILP
Instruction-level parallelism: the number of instructions that can run at the same time without changing the program's result.
Superscalar
A processor that finds independent instructions in one stream automatically and executes several per clock.
Power wall
Dynamic power ∝ C × V² × f, and higher f needs higher V, so faster clocks cost disproportionate power and heat.
Specialization
Hardware built for one kind of task (graphics, video, neural networks) to do it with much less energy.
Address space
Memory as an array of bytes, each identified by its address.
Latency
Time for the memory system to deliver requested data.
Stall
The processor can't run the next instruction because it depends on one that isn't complete, often a load.
Cache, cache line
On-chip storage holding copies of recently used memory, managed in fixed-size lines.
Spatial / temporal locality
Accessing addresses near recent ones / accessing the same addresses again soon. Both make caches effective.
Cold / capacity miss
A first access to a line / a line evicted because the cache was too small.
Test yourselfThe lecture's questions, plus a few more.
  1. Is a 2× speedup on a computer with 10 processors a good result?
    Show answer

    It's a faster program, but a poor use of the machine: 20% efficiency. Whether it's "good" depends on the goal. If the machine was otherwise idle and the answer was urgent, maybe. If you care about cost or energy, 80% of the hardware was wasted. Fast ≠ efficient.

  2. The program a = x*x + y*y + z*z has five instructions. Why can't any processor run it in fewer than three clocks?
    Show answer

    The dependency chain. The final add needs the first add's result, which needs a multiply's result: three steps that must happen in sequence, however many execution units there are.

  3. Why did processor clock frequencies stop increasing around 2005, even though transistors kept getting smaller?
    Show answer

    Power. Dynamic power scales with V² × f, and higher frequencies need higher voltage, so power, and heat, rise steeply with frequency. Chips hit the limit of what could be cooled. Leakage (static power) made it worse.

  4. Two loads followed by an add that uses both. The data is in DRAM (~248 cycles). Roughly how long does a processor that waits after every load take, compared with one that waits only when a value is used?
    Show answer

    Waiting after every load: 248 + 248 + 1 ≈ 497 cycles. Waiting only on use lets the loads overlap: 1 + 248 + 1 ≈ 250 cycles. Either way, the processor does 3 instructions' worth of work.

  5. In the 2-line cache, what sequence of addresses would miss on every access?
    Show answer

    Cycle through three or more lines, one byte each: 0x0, 0x4, 0x8, 0x0, 0x4, 0x8, … With LRU, each new line evicts exactly the line that's needed next. Try it with "your own".
